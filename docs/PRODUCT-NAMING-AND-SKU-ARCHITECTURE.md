## 1. Current SKU Structure

### 1.1 รูปแบบ "มาตรฐาน" ที่ระบบบังคับ ✅

```
parseSkuParts()  (views-main.jsx:3603-3607)
  regex: ^([A-Z]{1,3})(\d{2})(\d{3})$
  = [Prefix 1-3 ตัวอักษร][Variant 2 หลัก][Model 3 หลัก]   ความยาวรวม 6-8 ตัวอักษร
```

นี่คือรูปแบบเดียวที่ SKU builder (`AddProductView`) สร้างได้ และเป็นรูปแบบเดียวที่เครื่องมือวิเคราะห์
ส่วนใหญ่ (`nextModelForPrefix`, `productOwnerSkuPrefix_`, ABC review, owner bulk-assign) เข้าใจ

### 1.2 Prefix ที่ยืนยันความหมายจริง ✅ (มีแค่ 2 ตัว!)

| Prefix | ความหมาย | แหล่งยืนยัน |
|---|---|---|
| `OL` | มะกอก (olive) | `CLAUDE.md` "Business Rule: การสร้างรหัสสินค้า" — ตัวอย่างที่เจ้าของให้ไว้ตรง ๆ |
| `R` | กุหลาบ (rose) | เดียวกัน — `R01025`/`R10025`/`R19025` = กุหลาบแบบเดียวกัน 3 สี |

**ทุก prefix อื่นที่เจอในโค้ด — ไม่รู้ความหมาย**:
- `WL` — ยืนยันแค่ "มีอยู่จริง" (จากเคสบั๊กจริง ส.ค. 2026: `WL00002` โชว์ "หมด" ทั้งที่มีของ 41+240 —
  `CLAUDE.md` หัวข้อ `tests/qtyloc.test.js`) — **ความหมายทางธุรกิจไม่ปรากฏที่ไหนเลย**
- `L` — ยืนยันแค่ "มีอยู่จริงและมี Model number สูงถึง 263" (คอมเมนต์ `views-main.jsx:9186`:
  *"ไม่ควรดันเลข Model เช่น L ควรอยู่ 263 ไม่ใช่ 999"*) — แปลว่ามีสินค้าจริงในตระกูลนี้จำนวนมาก
  **แต่ไม่มีใครบันทึกไว้ว่า L ย่อมาจากอะไร**
- `HL` — ปรากฏเป็น placeholder ตัวอย่างในช่องค้นหา (`i18n.jsx:348`, `views-analytics.jsx:6747`:
  *"เช่น HL00170 หรือ ชื่อสินค้า..."*) — คนเขียน UI เลือกใช้เป็นตัวอย่างที่ "คุ้นตา" แปลว่าน่าจะเป็นรหัส
  ที่ใช้บ่อย/จำได้ง่าย — **แต่ก็ไม่มีความหมายบันทึกไว้เช่นกัน**
- prefix อื่น ๆ ทั้งหมดที่อาจมีอยู่จริง — **❓ ต้องข้อมูลจริง** (ไม่มีการ enumerate รายการ prefix ทั้งหมด
  ที่ไหนในระบบเลย — ไม่มี master, ไม่มี list, แม้แต่ในเอกสาร)

### 1.3 ตระกูลที่มีโครงสร้าง**ต่างจากมาตรฐานโดยสิ้นเชิง** ✅ — conflict เชิงโครงสร้างที่แท้จริง

**MTO (Made to Order)** ไม่ใช้ regex เดียวกันเลย:

```
mtoSkuPrefix_()  (views-quote.jsx:358-361)
  regex: ^([A-Z]+)(?=\d)     ← ไม่จำกัดความยาว prefix, ไม่มีสล็อต variant แยก
  ตัวอย่างจริงที่เจ้าของยืนยัน: BK001, BK002, …, PACKAGE001, PACKAGE002, …
```

รูปร่าง `BK001` = Prefix(`BK`) + เลข 3 หลัก **ไม่มี Variant slot เลย** ต่างจากมาตรฐานที่ต้องมี
`[Prefix][Variant2][Model3]` — และ `PACKAGE001` prefix ยาวถึง 7 ตัวอักษร (เกินขีดจำกัด 1-3 ของมาตรฐาน)

⚠️ **นี่คือ conflict ที่แท้จริง ไม่ใช่แค่ "ข้อมูลสกปรก"**: ระบบมี **2 ไวยากรณ์ SKU คู่ขนานกัน** ที่แยกกัน
ด้วย**หมวดหมู่** (`category.indexOf('Made to Order') >= 0`) ไม่ใช่แยกด้วยรูปแบบ SKU เอง — ถ้าหมวดของ
สินค้า MTO ตัวไหนถูกพิมพ์ผิด/เปลี่ยนโดยไม่ได้ตั้งใจ ระบบจะพยายามอ่าน SKU นั้นด้วย `parseSkuParts`
(มาตรฐาน) ซึ่ง**คืน `null` เงียบ ๆ** เพราะไม่เข้ารูปแบบ → หลุดจากทุกเครื่องมือที่พึ่ง prefix (ABC review,
owner auto-assign, ฯลฯ) โดยไม่มี error ให้เห็น — รูปแบบเดียวกับบั๊กที่ CLAUDE.md บันทึกไว้ซ้ำ ๆ ทั่วทั้ง
ระบบว่า "ไม่มี error ให้เห็น"

### 1.4 หมวดที่แปลว่า "ไม่มี SKU มาตรฐานเลย" ✅

`"ไม่มีรหัสสินค้า"` เป็น**หมวดหมู่จริง**ที่ระบบรู้จักและ**ตัดออกทุกจุดที่คำนวณอิงกับ prefix/SKU**
(`appsscript_complete.gs:8162`: `if (c === 'ไม่มีรหัสสินค้า') return false; // ไม่ใช่สินค้าจริง —
สั่งไม่ได้` · Part 1 §F.6 ของเอกสารก่อนหน้า: `stockAgg` นับรวมของกลุ่มนี้ด้วยเพราะยัง "เงินจม" อยู่จริง)

**แปลว่า**: มีสินค้าที่ขายจริง/มีสต็อกจริง **ที่ไม่เคยได้รับ SKU ตามมาตรฐานเลย** — เป็นความจริงข้อที่ 3
(ต่อจากมาตรฐาน + MTO) ของระบบ ไม่ใช่ edge case แปลก ๆ

### 1.5 สรุปตระกูล SKU ที่ยืนยันได้ (โครงสร้าง ไม่ใช่ปริมาณ)

| ตระกูล | รูปแบบ | ยังใช้งานอยู่จริง? | แหล่งยืนยัน |
|---|---|---|---|
| มาตรฐาน `[Prefix₁₋₃][VV][NNN]` | ✅ ใช้เป็น default ทุกการสร้างสินค้าใหม่วันนี้ | ✅ (SKU builder บังคับรูปแบบนี้เท่านั้น) | `AddProductView` |
| MTO `[Letters][NNN...]` (ไม่มี variant slot, prefix ไม่จำกัดยาว) | ✅ ใช้งานคู่ขนานตลอด (Sprint ล่าสุดเรื่อง MTO bundle) | ✅ | `views-quote.jsx:358` |
| ไม่มี SKU (`ไม่มีรหัสสินค้า`) | — (ไม่มีรูปแบบ) | ✅ ยังมีอยู่จริง มีมูลค่าสต๊อก | `appsscript_complete.gs:8162` |
| รูปแบบอื่นที่ไม่เข้า 3 ข้อบน (พิมพ์ผิด/เก่า/นำเข้าก่อนมีมาตรฐาน) | ไม่ทราบ | ❓ **ต้องข้อมูลจริง** | — |

### 1.6 สถิติ — ❓ ต้องข้อมูลจริง

คำถามที่ตอบไม่ได้เลยจากโค้ด (ระบุใน obj. 1 ตรง ๆ ว่าอยาก "Produce statistics"):
- มี prefix ทั้งหมดกี่ตัวในระบบจริง? แต่ละตัวมีสินค้ากี่ SKU?
- % ของสินค้าที่เข้ารูปแบบมาตรฐานเทียบกับ MTO เทียบกับ "ไม่มีรหัส" เทียบกับรูปแบบแปลกอื่น ๆ?
- prefix ไหนที่ "ตายแล้ว" (มีแต่สินค้าเก่า ไม่มีการสร้างใหม่เลยในรอบ 1-2 ปี)?
- มี prefix ที่ชนกันจริงไหม (คนละความหมายแต่ใช้ตัวอักษรเดียวกัน)?

→ ต้องมีสิทธิ์เข้าถึงชีต "ข้อมูลสินค้า"/"อัพเดทจำนวนสินค้า" จริง หรือรันเครื่องมือที่มีอยู่แล้วในระบบ
(`listProductCategories()`, `listCategoryBreakdown()` — GAS editor tools ที่ CLAUDE.md อ้างถึงว่า
"อ่านอย่างเดียว") แล้วส่งผลลัพธ์กลับมาให้วิเคราะห์ — **นี่คือคำถามข้อแรกในหัวข้อ 8**

## 2. Current Product Naming Structure

### 2.1 กติกาการตั้งชื่อ ณ จุดสร้าง — ✅ ยืนยันจากโค้ด

```js
// views-main.jsx:9372-9375
// ชื่อเต็มที่จะบันทึก = ชื่อ + สี + "ราคาส่ง" (เลขที่กรอก) เช่น "ยิปโซแห้ง เขียว 68"
const composedName = [name.trim(), colorName, wholesale > 0 ? String(wholesale) : ""]
  .filter(Boolean).join(" ");
```

โครงสร้างชื่อที่บันทึกจริง (ณ วันสร้าง) = **`[ชื่อฐาน] [ชื่อสี] [ราคาส่ง]`** ต่อกันด้วยช่องว่าง เดี่ยว
ตัดส่วนที่ว่างทิ้ง

### 2.2 แยกส่วนที่ "structured" vs "free text" จริง

| ส่วนของชื่อ | Structured จริงไหม? | รายละเอียด |
|---|---|---|
| ชื่อฐาน (`name`) | ❌ free text ล้วน | ผู้ใช้พิมพ์อะไรก็ได้ ไม่มี validation |
| ชื่อสี (`colorName`) | 🟡 **structured เฉพาะตอนสร้าง** | มาจาก `VARIANT_CODE_TO_NAME` lookup (99 รหัสสี) **เฉพาะเมื่อ** `variantSrc==="color"` — ต่อกันเป็น text แล้วจบ ไม่ผูกกลับไปหา code อีก |
| ราคาส่ง (ตัวเลขท้ายชื่อ) | ❌ เป็น text ที่ "บังเอิญเป็นตัวเลข" | ไม่ใช่ field จริง — เป็นแค่การต่อ string ผลคือ **ราคาปรากฏ 2 ที่**: ในชื่อ (text, แช่แข็ง ณ วันสร้าง) และใน `sellprice` (field จริง, sync ตาม ZORT ตลอด) |
| ขนาด/ลำดับ (โหมด `manual`) | ❌ **ไม่ปรากฏในชื่อเลย** | เมื่อ `variantSrc==="manual"` → `colorName=""` → ชื่อไม่มีร่องรอยว่า variant คืออะไร ข้อมูลนั้นมีอยู่แค่ใน 2 หลักตัวเลขของ SKU ที่**ไม่มีตารางแปลความหมาย** (ต่างจากสีที่มี `VARIANT_CODE_TO_NAME`) |
| วัสดุ (Material) | ❌ ไม่มีที่ไหนเลย | ไม่มี field, ไม่มีในชื่อ, ไม่มีใน SKU |
| แบรนด์/คอลเลกชัน | ❌ ไม่มีแนวคิดนี้ในระบบเลย | grep ทั้ง repo ไม่เจอ (คำว่า "brand" มีแค่ใน UI ของโลโก้ร้าน "Doomuenjing" ไม่เกี่ยวกับสินค้า) |

### 2.3 สิ่งที่ควรเป็น field แยก แทนที่จะฝังในชื่อ

- **ราคาส่งท้ายชื่อ** — ควรเป็น convention ของ**การแสดงผล** (คำนวณสดจาก `sellprice`/`wholesaleRatio_`
  ตอน render) ไม่ใช่ข้อความที่แช่แข็งตอนสร้างแล้วไม่มีวันอัปเดตตาม — วันนี้ถ้าราคาส่งเปลี่ยนทีหลัง
  (เช่นแก้ที่ ZORT) **ชื่อสินค้ายังโชว์ราคาเก่าตลอดไป** (เป็นความไม่สอดคล้องที่เกิดขึ้นแน่นอน ไม่ใช่แค่
  ทฤษฎี — ราคามีสิทธิ์เปลี่ยนได้เสมอหลังสร้าง)
- **ขนาด/ลำดับ (manual variant)** — ควรมี label เหมือนสีมี `VARIANT_CODE_TO_NAME` แทนที่จะเป็นตัวเลข
  ที่ไม่มีใครแปลได้นอกจากคนที่จำ business rule ของหมวดนั้นได้

## 3. Relationship between SKU and Name

### 3.1 ข้อมูลที่ซ้ำกัน (duplicated) ✅

| ข้อมูล | อยู่ใน SKU | อยู่ใน Name | ปัญหา |
|---|---|---|---|
| **สี** | ✅ Variant 2 หลัก (เมื่อ `variantSrc==="color"`) | ✅ ข้อความภาษาไทยในชื่อ | 2 แหล่งความจริงสำหรับข้อมูลเดียวกัน — **ไม่มีการเช็ค consistency ระหว่างกันเลย** หลังสร้างแล้ว ถ้าใครแก้ชื่อที่ ZORT ตรงๆ (ทางเดียวที่แก้ชื่อได้ — ดู Domain doc §E) ชื่อกับ SKU แยกทางกันได้ทันทีโดยไม่มีอะไรเตือน |
| **ราคาส่ง** | ❌ ไม่อยู่ใน SKU | ✅ ต่อท้ายชื่อ (แช่แข็ง) | ซ้ำกับ field `sellprice` จริง (ผ่านการคำนวณ ไม่ใช่ SKU) — ถือเป็น duplication ระหว่าง **ชื่อ ↔ field** ไม่ใช่ **SKU ↔ ชื่อ** โดยตรง แต่เป็นความซ้ำซ้อนเชิงข้อมูลแบบเดียวกัน |

### 3.2 ข้อมูลที่ขาด (missing) ✅

- **Size/ลำดับ** (โหมด manual) — อยู่ใน SKU (2 หลัก) แต่**หายไปจากชื่อโดยสิ้นเชิง** — ตรงข้ามกับสีที่ยัง
  มีชื่อกำกับ นี่คือความไม่สมมาตร: **แกน variant เดียวกัน (2 หลักในตำแหน่งเดียวกันของ SKU) ได้รับการ
  ปฏิบัติต่างกันโดยสิ้นเชิง**ขึ้นอยู่กับว่าใช้เป็นสีหรือขนาด — คนอ่านชื่อเพียวๆ (ไม่ดู SKU) จะไม่มีทาง
  รู้ว่าสินค้าตัวนี้ไซซ์ไหน
- **Product Type/ประเภท** — ไม่อยู่ทั้งใน SKU ชัดเจน (ต้องถอด prefix เอง ไม่มี label) และไม่อยู่ในชื่อ

### 3.3 ข้อมูลที่ไม่สอดคล้อง (inconsistent) ✅ — จุดที่ร้ายแรงที่สุดในเอกสารนี้ทั้งฉบับ

> **แกน Variant 2 หลักเดียวกันในโครงสร้าง SKU มีความหมาย 2 แบบที่ต่างกันโดยสิ้นเชิง** ขึ้นอยู่กับหมวด
> (สีจากตาราง 99 รหัส **หรือ** ขนาด/ลำดับที่พิมพ์เอง) — **และไม่มีข้อมูลที่ไหนบันทึกไว้ว่าหมวดไหนใช้
> ความหมายไหน**

หลักฐานยืนยันจากคำพูดของเจ้าของเองใน `CLAUDE.md` บรรทัด 495:

> *"หมวดไหนใช้กฎอะไร ยังไม่มี mapping ตายตัว ให้ถามผู้ใช้กลับทุกครั้งที่ไม่แน่ใจ **(ผู้ใช้เองก็จำหมวด
> ไม่ครบ)**"*

**แม้แต่เจ้าของร้านเองยังจำไม่ครบว่าหมวดไหนใช้กฎอะไร** — นี่ไม่ใช่ปัญหาเชิงเทคนิคที่แก้ด้วยโค้ดได้ฝ่าย
เดียว แต่คือหลักฐานที่หนักแน่นที่สุดว่า **โครงสร้างข้อมูลปัจจุบันพึ่งความจำของมนุษย์ในจุดที่ไม่ควรพึ่ง**
— เป็นเหตุผลสนับสนุนที่ชัดเจนที่สุดสำหรับการทำ registry (หัวข้อ 4-6)

## 4. Business Semantics — เทียบกับ hierarchy ที่เสนอ

เจ้าของเสนอ: `Category → Product Family → Variant → Model → Color → Size → SKU`

### 4.1 แม็ปทีละชั้นกับของจริงในระบบวันนี้

| ชั้นที่เสนอ | มีจริงในระบบไหม? | สภาพจริงวันนี้ |
|---|---|---|
| **Category** | ✅ มีจริง | free text, 17+ ชื่อจริงยืนยันได้จาก `PRODUCT_OWNER_ASSIGN_PLAN_` (ใบ, ใบบูช, ใบไม้แขวน, กิ่งไม้, ต้นไม้, Realtouch, ดอกไม้, บูช, ของตกแต่ง, แจกันแก้ว, กระถางPS, เรซิ่นและอื่นๆ, ดอกหญ้า, กุหลาบหิน, ผลไม้ผักกิ่งผลไม้, ไม้แซมไม้ประดับ, สายเลื้อย, อุปกรณ์สำนักงาน) — ไม่มี master แต่**เป็นชั้นบนสุดถูกต้องแล้ว** |
| **Product Family** | ❌ **ไม่มี entity** — แต่**มีอยู่จริงในทางปฏิบัติ**แบบไม่มีชื่อ | สิ่งที่เรียก "แบบเดียวกันหลายสี" (`R01025`/`R10025`/`R19025` = Prefix+Model เดียวกัน) **คือ Family อยู่แล้ว** เพียงแต่ไม่เคยถูกเก็บเป็น record — ต้อง scan ทุก SKU ใหม่ทุกครั้งที่ต้องการรู้ (`designInfo`/`designMatches` ใน `AddProductView` ทำแบบนี้อยู่ตอนนี้ — คำนวณสดทุกครั้ง ไม่มี cache/entity) |
| **Variant** | 🔴 **มีแต่ overloaded** (ดู §3.3) | 1 field ความหมาย 2 อย่าง ไม่มี discriminator |
| **Model** | ⚠️ **ชนกับความหมายเดิม** | วันนี้ "Model Number" (3 หลักท้าย SKU) **คือตัวที่ทำหน้าที่ "Family identity"** (running ต่อ*แบบ*ไม่ใช่ต่อ*สี*) — ในลำดับที่เจ้าของเสนอ Model อยู่ **ใต้** Variant ซึ่งกลับข้างกับที่ระบบใช้จริงวันนี้ (Model กำหนดว่าอยู่ "แบบ" ไหน *ก่อน* จะเลือกสี ไม่ใช่ตามหลังสี) — ⚠️ **ต้องเจ้าของยืนยันว่า "Model" ในความหมายที่ต้องการคืออะไร** (คำถาม §8) |
| **Color** | 🟡 มีจริงแต่เป็นส่วนหนึ่งของ Variant ที่ overload | ตาราง 99 รหัสมีจริง (`VARIANT_COLOR_CODES`) — ควรถูกยกเป็นแกนอิสระ ไม่ปนกับ Size |
| **Size** | ❌ **ด้อยที่สุดในทั้งโดเมน** | ไม่มี master, ไม่มีชื่อกำกับ, เป็นแค่ตัวเลขดิบที่พิมพ์เองแบบอิสระ ไม่มีความสอดคล้องข้ามหมวด |
| **SKU** | ✅ มีจริง แต่ทำหน้าที่ผิดชั้น (§4.2) | เป็นทั้ง identity + ตัวเข้ารหัสความหมาย + barcode พร้อมกัน |

### 4.2 ปัญหาเชิงสถาปัตยกรรมที่ลึกที่สุด: **SKU วันนี้ *คือ* ตัว model ข้อมูล ไม่ใช่ *ผลลัพธ์* ของมัน**

```
วันนี้:   [กรอกฟอร์ม] ──ประกอบ string──► SKU  (SKU = ที่เก็บความหมายเพียงที่เดียว)
                                          │
                          ต้องการรู้ Family? → ต้อง parse SKU ทุกครั้ง (parseSkuParts)
                          ต้องการรู้ Type?   → ต้อง parse prefix ทุกครั้ง
                          ต้องการรู้ Color?  → ต้อง parse variant + join กับตาราง 99 รหัส

เสนอ:     [Type][Family][Color/Size] ──► เก็บเป็น field จริง ──► SKU = *เรนเดอร์* จากข้อมูล (หรือ opaque)
```

ผลของการที่ SKU เป็นตัวเก็บความหมายเพียงที่เดียว: **แก้ไขความหมายไม่ได้โดยไม่แก้ identity** — ถ้าพบว่า
สินค้าตัวหนึ่งถูกใส่ prefix ผิดหมวดหลังสร้างไปแล้ว (พิมพ์ `OI` แทน `OL` เช่น) **แก้ไม่ได้เลยโดยไม่สร้าง
SKU ใหม่** (= สินค้าใหม่ใน ZORT, ตัดขาดประวัติการขาย/สต็อกเดิม) — เป็นต้นทุนแฝงที่ไม่มีใครเห็นจนกว่าจะ
เจอเคสจริง

## 6. Compare Multiple Architectures

### Option A — Refine Current SKU Philosophy (แก้ของเดิมให้แน่นขึ้น)

**แนวคิด**: คง `[Prefix][Variant2][Model3]` ไว้เหมือนเดิมทุกตัวอักษร แต่ผูก Prefix เข้ากับ Product Type
Registry จริง (ตามที่ออกแบบไว้แล้วใน `PRODUCT-DOMAIN-ARCHITECTURE.md` §K) + เพิ่มฟิลด์ `variantRule`
ต่อ type (แก้ปัญหา §3.3 ทันที — ระบบรู้เองว่าหมวดนี้ variant=สีหรือขนาด ไม่ต้องพึ่งความจำคน)

| มิติ | ผล |
|---|---|
| ข้อดี | เปลี่ยนน้อยที่สุด · SKU เดิมทุกตัวยังใช้งานได้เป๊ะ ไม่ต้อง migrate สักตัว · พนักงานที่อ่าน SKU เป็น (เช่น "R19025 = กุหลาบขาว") ยังใช้ทักษะเดิมได้ต่อ (สำคัญมาก — ผู้ใช้หลักเป็นแรงงานที่ไม่ถนัดเทคโนโลยีตามที่ระบุใน `CLAUDE.md` หัวเอกสาร) |
| ข้อเสีย | **ไม่แก้ปัญหาแกน** — SKU ยังเป็นทั้ง identity+ความหมายพร้อมกัน (§4.2) · reclassify สินค้าที่ผิดยังทำไม่ได้โดยไม่สร้าง SKU ใหม่ · "Family" ยังไม่มี entity จริง ยัง derive สดทุกครั้ง |
| Migration | 🟢 **ต่ำ** — ไม่แตะ SKU เดิมสักตัว เพิ่มแค่ config layer |
| Impact ZORT | ไม่กระทบ (รูปแบบ SKU เดิมเป๊ะ) |
| Impact Search | ไม่เปลี่ยน |
| Impact Analytics | ดีขึ้นเล็กน้อย (group ตาม Type จาก registry แทน regex เดา) |
| Impact Supplier | Registry มี defaultSupplier ต่อ type ได้ |
| Impact Product Creation | ง่ายขึ้น (เลือก Type จาก list แทนพิมพ์ prefix เอง) แต่ SKU ที่ได้หน้าตาเหมือนเดิมทุกประการ |

### Option B — Product-Family-Driven (ยก Family เป็น entity จริง)

**แนวคิด**: เพิ่ม **Product Family เป็น record จริง** (ไม่ใช่แค่ Prefix+Model ที่ derive สด) — 1 Family
= 1 แบบสินค้า มี id/ชื่อ/รูปหลัก/ราคาฐาน/Type ของตัวเอง ส่วน SKU ยังคงหน้าตาเดิม
(`familyId(=Prefix+Model) + VariantCode`) เพื่อความเข้ากันได้กับ ZORT/barcode/พนักงาน

| มิติ | ผล |
|---|---|
| ข้อดี | ปิดช่องว่างที่ใหญ่สุดที่เจอในเอกสารนี้ (Family "มีอยู่จริงแต่ไม่มีตัวตน" — §4.1) · เปิดฟีเจอร์ที่ทำไม่ได้วันนี้: ดูทุกสีของแบบเดียวกันโดยไม่ต้อง scan ทุก SKU สด, รายงานยอดขายระดับ "แบบ" ไม่ใช่แค่ระดับ SKU · SKU ยังสั้น อ่านง่าย เข้ากับ barcode/ป้ายเดิมได้ |
| ข้อเสีย | ต้อง backfill Family record ให้สินค้าเดิมทั้งหมด (แต่**ทำอัตโนมัติได้** — derive จาก SKU text ด้วย logic ที่มีอยู่แล้ว `parseSkuParts`, ไม่ใช่เดามั่ว) · ยังไม่แก้ปัญหา Variant overload เต็มที่ถ้าไม่ทำคู่กับ Option A (ในทางปฏิบัติ B ควรเป็น "A + Family entity" ไม่ใช่คนละสาย) |
| Migration | 🟡 **กลาง** — entity ใหม่ + backfill script ที่ derive ได้อัตโนมัติจากข้อมูลเดิม (ไม่ต้องเดา ไม่ต้องกรอกมือ) |
| Impact ZORT | ไม่กระทบโดยตรง (Family อยู่ฝั่ง ERP เท่านั้น ZORT ยังเห็นแค่ SKU เหมือนเดิม) |
| Impact Search | ดีขึ้นชัดเจน — ค้นหา "ทุกสีของแบบนี้" ได้จริงจากข้อมูล ไม่ใช่คำนวณสดทุกครั้ง (`designMatches`/`designInfo` วันนี้ทำแบบ ad-hoc client-side ทุกครั้งที่เปิดฟอร์ม) |
| Impact Analytics | ดีขึ้นมาก — ยอดขายระดับแบบ ไม่ใช่แค่ระดับสี |
| Impact Supplier | Family เก็บ default supplier ได้แม่นกว่าระดับ Type |
| Impact Product Creation | โหมด "สีใหม่ของแบบเดิม" (มีอยู่แล้ววันนี้) เปลี่ยนจาก "ค้นหา+parse SKU ใหม่ทุกครั้ง" → "เลือก Family ที่มีอยู่แล้ว" — UX เดิม แต่ backend แน่นขึ้น |

### Option C — Fully Normalized Product Registry

**แนวคิด**: SKU กลายเป็น **surrogate key ล้วน ๆ** (ไม่ต้องมีความหมายอะไรเลย) ทุกความหมายทางธุรกิจ
(Type/Family/Color/Size/Category/Supplier/Owner) อยู่เป็น field จริงบน Product record · Barcode แยก
เป็นฟิลด์ของตัวเอง (ปกติ = SKU เหมือนเดิม แต่ไม่ผูกตายตัวอีกต่อไป)

| มิติ | ผล |
|---|---|
| ข้อดี | ยืดหยุ่นสุด — reclassify สินค้าได้โดยไม่แตะ identity เลย · รองรับทุกฟีเจอร์อนาคตที่ Domain doc §H ระบุว่าทำไม่ได้วันนี้ (Versioning, Templates, Bundles, multi-supplier) ได้สะดวกที่สุด · ตรงกับสถาปัตยกรรม PIM มาตรฐานทั่วไป |
| ข้อเสีย | **SKU จะไม่มีความหมายให้อ่านด้วยตาอีกต่อไป** — สูญเสียความสามารถ "เห็น SKU แล้วรู้ทันทีว่าเป็นอะไร" ซึ่งพนักงานคลัง (รวมแรงงานต่างด้าวที่ CLAUDE.md ระบุว่าเป็นผู้ใช้หลัก) อาจพึ่งพาอยู่ในการทำงานประจำวัน — เป็นต้นทุนการฝึกอบรม/ปรับตัวที่แท้จริง ไม่ใช่แค่ทฤษฎี · งานเปลี่ยนแปลง UI มากที่สุดในทั้ง 3 ทาง · SKU เดิมที่พิมพ์ป้ายจริงไปแล้วหลายพันชิ้นยังต้องใช้ได้ตลอดกาล (ทำได้ — แค่ต้องตั้งใจออกแบบไม่ให้ invalidate ของเก่า) |
| Migration | 🔴 **สูงสุด** — แต่**ไม่จำเป็นต้อง regenerate SKU เดิมสักตัว** ถ้าออกแบบให้ "field ใหม่คือ source of truth ไปข้างหน้า, SKU เดิมยัง grandfather เข้ามาด้วย ETL ครั้งเดียว" (ไม่ใช่ invalidate ของเก่า) |
| Impact ZORT | ไม่กระทบ (barcode/sku field ยังใช้งานแบบเดิมได้) |
| Impact Search | ดีที่สุด — ค้นหาตาม field จริง (สี/ขนาด/ประเภท) ไม่ต้องพึ่ง regex parse SKU ที่เปราะ (ทุกจุดที่เรียก `parseSkuParts`/`mtoSkuPrefix_`/`productOwnerSkuPrefix_` วันนี้จะยุบเหลือแค่ field lookup — ตัดความเสี่ยง "SKU ไม่เข้ารูปแบบ = หลุดเงียบ ๆ" ทั้งหมวดหมู่ ซึ่งเป็นรูปแบบบั๊กที่ CLAUDE.md เจอซ้ำ ๆ ตลอดทั้งเอกสาร) |
| Impact Analytics | ดีที่สุด |
| Impact Supplier | สะอาดที่สุด — Supplier เป็น FK บน Product เหมือน Owner ที่มีอยู่แล้ว |
| Impact Product Creation | ต้องปรับ UI มากสุด (ฟอร์มแบบมีโครงสร้างเต็ม) — **แต่ตรงกับ target flow ที่ออกแบบไว้แล้วใน Domain doc §L พอดี** (Search→Type→auto-prefix→generate→validate→save) ไม่ใช่งานเพิ่มใหม่ที่ไม่เกี่ยวกัน |

### 6.1 คำแนะนำ (ข้อเสนอของสถาปนิก — ยังไม่ใช่การตัดสินใจ)

**เสนอ Option B เป็นทิศทางระยะยาว** ด้วยเหตุผล:

1. **ปิดช่องว่างที่ใหญ่ที่สุดที่พบจริงในการสืบสวนนี้** (§4.1 — Family มีอยู่จริงในทางปฏิบัติแต่ไม่มี
   ตัวตนเป็นข้อมูล) โดยไม่แลกกับสิ่งที่ผู้ใช้พึ่งพาอยู่ (SKU อ่านออกได้)
2. **Migration ทำอัตโนมัติได้จริง** ไม่ใช่แค่ทฤษฎี — logic ที่ derive Family จาก SKU (`parseSkuParts`)
   มีอยู่แล้วในระบบ แค่เปลี่ยนจาก "คำนวณสดทุกครั้ง" เป็น "คำนวณครั้งเดียวแล้วบันทึก"
3. **เป็นก้าวที่ไม่เสียของถ้าจะไป Option C ทีหลัง** — เมื่อ Family เป็น entity จริงแล้ว การแยก
   "identity" ออกจาก "ความหมาย" เพิ่มเติม (สู่ Option C) จะง่ายขึ้น ไม่ใช่ทำงานซ้ำ
4. **Option A เพียงอย่างเดียวไม่พอ** — ไม่แก้ปัญหาแกนที่พบว่าร้ายแรงที่สุด (§3.3, §4.2) แค่ทำให้ปัญหาเดิม
   มีโครงสร้างรองรับมากขึ้นเฉย ๆ

⚠️ **นี่คือมุมมองสถาปัตยกรรม/ความเสี่ยงเทคนิคล้วน** — ไม่รู้ว่าพนักงานพึ่งการอ่าน SKU มากแค่ไหนจริง ๆ
ในงานประจำวัน (ข้อมูลนี้ไม่มีในโค้ด) ถ้าพึ่งมากจริง น้ำหนักจะเอียงไปทาง Option A/B มากกว่า C ชัดเจน —
เป็นคำถามที่ต้องเจ้าของตอบ (หัวข้อ 8)

## 7. Migration Strategy — สมมติมี SKU อยู่แล้วหลักพัน ไม่สร้างสินค้าใหม่

### 7.1 ข้อจำกัดที่เป็น "hard constraint" ไม่ใช่แค่ความสะดวก

**SKU ที่มีอยู่แล้วถูกพิมพ์เป็น**บาร์โค้ดจริง**ติดอยู่ที่ตำแหน่งจัดเก็บ/สินค้าจริงในโกดังแล้ว**
(`LabelPrintView`, ระบบพิมพ์ QR/บาร์โค้ดที่มีอยู่แล้วในแอป) — **การเปลี่ยน SKU ที่มีอยู่ = ป้ายจริงใช้
ไม่ได้ทันที** ไม่ใช่แค่ปัญหาฐานข้อมูล เป็นปัญหาโลกจริงที่ตามไปแก้ป้ายกระดาษหลักพันใบไม่ได้ในทางปฏิบัติ
→ **ทุกทางเลือก (A/B/C) ต้องไม่แตะ SKU string ที่มีอยู่แล้วเลย**

### 7.2 Backward compatibility

- SKU เดิมทุกตัวยังคง**valid ตลอดไป** ทั้งใน ZORT และ ERP — ไม่มี "แปลง SKU เก่าให้เป็น SKU ใหม่"
- ที่ "เปลี่ยน" คือ**เมทาดาทาที่แนบอยู่ข้าง ๆ** (Family/Type/Color/Size เป็น field ใหม่ที่เพิ่มเข้ามา)
  ไม่ใช่ตัว SKU string เอง

### 7.3 Coexistence ระหว่าง migration

- backfill ข้อมูลใหม่ (Family/Type/Color) จาก SKU เดิมด้วย logic ที่**มีอยู่แล้ว** (`parseSkuParts` +
  `VARIANT_COLOR_CODES`) — รันครั้งเดียวเป็น ETL ไม่ใช่ทุก request (ต่างจากวันนี้ที่ derive สดตลอด)
- ส่วนที่ backfill อัตโนมัติไม่ได้ (variant=สีหรือขนาด? "ไม่มีรหัสสินค้า"? รูปแบบแปลก?) — **ปล่อยว่างไว้
  ชัดเจนว่า "ยังไม่จัดหมวด" แทนการเดา** แล้วโชว์เป็นคิวให้คนตรวจทีหลัง — ใช้ pattern เดียวกับเครื่องมือ
  ที่มีอยู่แล้วในระบบ (`previewZortDeletedProducts`, `previewProductOwnerAssign` — **preview ก่อนเขียน
  จริงเสมอ**, เป็น convention ที่ codebase ยึดถือทุกจุดที่มีความเสี่ยง)

### 7.4 Phases ที่เสนอ (ไม่ผูกมัด — รอ owner ยืนยัน priority)

```
Phase 0 — Product Type Registry (ทำอยู่แล้วตามแผน Domain doc §K) — เป็นฐานของทุก phase ถัดไป
Phase 1 — Backfill Product Family จาก SKU ที่เข้ารูปแบบมาตรฐาน (อัตโนมัติ, ความเสี่ยงต่ำ)
Phase 2 — Backfill Color จาก Variant digit (เฉพาะ type ที่ registry บอกว่า variantRule=color)
Phase 3 — คิวตรวจสอบด้วยมือ: MTO, "ไม่มีรหัสสินค้า", SKU ที่ parse ไม่ผ่าน, variant ที่กำกวม
          (size vs color) — ขนาดของคิวนี้ ❓ ต้องข้อมูลจริงถึงจะรู้
Phase 4 (ถ้าเลือกไป Option C ในอนาคต) — สินค้าใหม่เริ่มต้องกรอก field ครบก่อนได้ SKU
          สินค้าเก่ายังทำงานผ่าน SKU เดิมได้ตลอดไปโดยไม่ต้อง migrate เพิ่ม
```

### 7.5 Risks

| ความเสี่ยง | คำอธิบาย | ทางลด |
|---|---|---|
| Backfill script สรุปผิดเงียบ ๆ | รูปแบบบั๊กที่ CLAUDE.md เจอซ้ำที่สุดในทั้งระบบ ("ไม่มี error ให้เห็น") | บังคับ preview-before-write เสมอ (pattern ที่มีอยู่แล้ว) |
| 2 แหล่งความจริงพร้อมกันระหว่าง coexistence | โค้ดเก่าอ่านจาก SKU สด, โค้ดใหม่อ่านจาก field backfill — ถ้าไม่ sync จะเห็นค่าต่างกันคนละที่ | ต้องมีแผนย้าย caller ทีละจุดให้ครบ ไม่ปล่อยให้ 2 เส้นทางอยู่คู่กันถาวร |
| แก้ "ความผิดพลาดเดิม" โดยเปลี่ยน SKU string | เจอ prefix พิมพ์ผิด (เช่น OI ที่ควรเป็น OL) แล้วอยากแก้ที่ SKU ตรง ๆ | **ห้าม** — แก้ที่ field เมทาดาทา (Type/Family) เท่านั้น ของจริงในโกดังหาไม่เจอถ้า SKU เปลี่ยน |
| ประเมิน scope ผิดเพราะไม่มีข้อมูลจริง | ทั้งเอกสารนี้เขียนจากโค้ด ไม่มีตัวเลขจริงกำกับ risk/effort | ต้องขอข้อมูลจริงก่อนเริ่ม implement (หัวข้อ 8 ข้อ 1) |

## 8. Questions for the Owner

> ไม่มีข้อไหนในนี้ที่เดาคำตอบ — ทุกข้อคือสิ่งที่โค้ดตอบไม่ได้จริง ๆ

1. **[บล็อกทุกอย่างในหัวข้อ 1]** ขอสิทธิ์ดูข้อมูลสินค้าจริง (export/แชร์ชีต หรือรันเครื่องมือที่มีอยู่แล้ว
   เช่น `listProductCategories()`/`listCategoryBreakdown()` ใน GAS editor แล้วส่งผลลัพธ์มาให้) — ไม่มี
   สิ่งนี้ สถิติ/ความถี่/prefix ที่ "ตายแล้ว" ตอบไม่ได้เลย เป็นแค่การอนุมานจากโค้ด
2. Prefix ที่ยืนยันความหมายได้มีแค่ `OL`/`R` — prefix อื่นทั้งหมด (`WL`, `L`, `HL`, ที่เหลือ) มีความหมาย
   ว่าอะไร? มี list เต็มอยู่ที่ไหนสักที่ (แม้จะเป็นแค่ในหัวเจ้าของ) ไหม?
3. **"Model" ในลำดับชั้นที่เสนอมา** (`Family→Variant→Model→Color→Size`) หมายถึงอะไรกันแน่? — วันนี้
   "Model Number" (3 หลักท้าย SKU) ทำหน้าที่เป็น**ตัวระบุ Family** (มาก่อนสี ไม่ใช่ตามหลัง) ถ้า "Model"
   ที่ต้องการหมายถึงสิ่งอื่น (เช่น รุ่นการผลิต/การสั่งซื้อ) ต้องอธิบายเพิ่มเพราะไม่ตรงกับที่ระบบใช้อยู่
4. Size (โหมด manual variant) — เป็น list จำกัดที่ควรมีตาราง master เหมือนสี (99 รหัส) ไหม หรือเป็น
   free-form จริง ๆ ที่ไม่มีทางกำหนดตายตัวได้?
5. `"ไม่มีรหัสสินค้า"` — ตั้งใจให้มีสินค้าที่ไม่มี SKU มาตรฐานอยู่ถาวรไหม หรืออยากให้ทุกตัวมี SKU จริง
   ในที่สุด (เป็น backlog ที่ต้องเคลียร์)?
6. มี SKU กี่ตัวโดยประมาณที่**พิมพ์เป็นป้ายบาร์โค้ดจริงติดอยู่ที่ของ/ชั้นวางแล้ว**? (กำหนดว่าข้อจำกัด
   "ห้ามแตะ SKU เดิม" หนักแน่นแค่ไหนในทางปฏิบัติ — ถ้ามีน้อยกว่าที่คิด อาจมีทางเลือกเพิ่ม)
7. ต้องการให้ SKU **อ่านออกด้วยตา**เป็นข้อกำหนดที่แตะไม่ได้ (พนักงานคลังต้องมองแล้วรู้ทันที) หรือการสแกน
   บาร์โค้ดครอบคลุมงานหน้างานเพียงพอจนยอมให้ SKU เป็นรหัสไร้ความหมาย (Option C) ได้?
8. MTO (`BK`/`PACKAGE`) ที่มีโครงสร้างต่างไปเลย — ตั้งใจให้เป็นคนละระบบตลอดไป (ตรงกับที่ MTO ถูกแยก
   ปฏิบัติต่างจากสินค้าทั่วไปอยู่แล้วในหลายจุดของระบบ) หรืออยากรวมเข้า Product Type Registry เดียวกัน
   ในระยะยาว?
9. ระหว่าง Option A / B / C — ทิศทางไหน "รู้สึกถูก" มากที่สุดตอนนี้ (แม้ยังไม่ต้องล็อกรายละเอียด) —
   คำตอบนี้จะกำหนดว่า Product Type Registry (งานที่รอออกแบบต่อ) ควรออกแบบเผื่อทางไหนไว้ล่วงหน้า
