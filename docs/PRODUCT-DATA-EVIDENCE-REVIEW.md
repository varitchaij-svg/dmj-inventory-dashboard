## 1. File/Data Structure Inspection

### 1.1 ข้อเท็จจริงเกี่ยวกับไฟล์

- **ไม่ใช่ Excel จริง** — ไฟล์เป็น **CSV, UTF-8** (`file` command ยืนยัน) แม้ผู้ใช้เรียกว่า "Excel file"
  — ไม่มี "sheet" หลายแผ่น (CSV มีได้แผ่นเดียวเสมอ) ✅
- **จำนวนแถวทั้งหมด**: 5,905 บรรทัดในไฟล์ (รวม 2 แถวหัวตาราง) = **5,903 แถวข้อมูล** ✅
- **โครงสร้างหัวตารางผิดปกติ**: แถวที่ 1 คือ `สินค้า,,,,,,,,,,,` (ดูเหมือนหัวข้อรายงาน "สินค้า" ที่
  merge cell ข้ามคอลัมน์ ไม่ใช่ header จริง) — **แถวที่ 2 คือ header จริง** ✅

  ตัวไหนคือคลังไหน** — ทดสอบด้วยขนาดตัวเลขเฉลี่ย (`col_A` เฉลี่ย 13.2 vs `col_B` เฉลี่ย 20.9) ไม่ชี้ขาด

### 1.3 ปัญหา `#` (idx) — ไม่ใช่ตัวนับที่เชื่อถือได้

### 1.4 "(ทดสอบ)" ในหัวคอลัมน์ชื่อสินค้า — สัญญาณเตือนที่ต้องรายงานตรง ๆ

หัวคอลัมน์ที่ 2 เขียนว่า **"ชื่อสินค้า (ทดสอบ)"** = "Product Name **(TEST)**" ✅ — คำนี้ปรากฏใน**หัว

❓ **UNRESOLVED — สำคัญมาก**: ถ้าข้อมูลนี้เป็นข้อมูลทดสอบ (ไม่ใช่ catalog การขายจริง) **ทุกข้อสรุป

## 2. SKU Structure — วิเคราะห์จริง

### 2.1 สัดส่วนรูปแบบ SKU (จาก 5,747 แถวที่มี SKU) ✅ DATA-EVIDENCED

| รูปแบบ | จำนวน | % | regex ที่ใช้ทดสอบ |
|---|---|---|---|
| **มาตรฐาน** `[Prefix 1-3][Variant2][Model3]` | 5,171 | **90.0%** | `^([A-Z]{1,3})(\d{2})(\d{3})$` (จาก `parseSkuParts`, views-main.jsx:3604) |
| ตัวเลขล้วน (บาร์โค้ดสไตล์ EAN) | 14 | 0.2% | `^\d+$` |
| ตัวอักษร+ตัวเลข แต่ไม่ตรงสัดส่วน 2+3 | 183 | 3.2% | `^[A-Z]+\d+$` (ไม่ตรง regex มาตรฐาน) |
| อื่น ๆ (มีอักขระผสม/suffix ตัวอักษร) | 379 | 6.6% | ไม่เข้า pattern ไหนเลย |

**90% เข้ารูปแบบมาตรฐาน — สูงกว่าที่คาดไว้ในเอกสารก่อนหน้า** (ซึ่งเขียนแบบไม่มีตัวเลขกำกับ) แต่ **10%
ที่เหลือ (576 แถว) ไม่ใช่จำนวนน้อยที่มองข้ามได้** — เท่ากับสินค้าเกือบ 600 ตัวที่เครื่องมือทุกชิ้นที่พึ่ง
`parseSkuParts` (ABC review, owner auto-assign, ฯลฯ) **จะ parse ไม่ผ่านและตกหล่นเงียบ ๆ**

### 2.2 กลุ่ม "ตัวอักษร+ตัวเลขแต่ไม่ตรงสัดส่วน" — เผยรูปแบบใหม่ที่ไม่เคยรู้จัก ✅

Prefix ที่พบในกลุ่มนี้ (ความยาว 1-7 ตัวอักษร!) พร้อมความถี่:

```
VASE(20)  FLOWER(20)  BK(20)  BQ(20)  LP(20)  TREE(20)  VG(20)
GMD(13)  OE(10)  G(6)  P(3)  OL(2)  OASIS(2)  TAPE(2)  PACKAGE(1)  BO(1) ...
```

🔵→✅ **ยืนยัน `BK`/`PACKAGE`** ที่ CLAUDE.md อ้างว่าเป็น MTO prefix จริง — **ยกระดับจาก CODE-EVIDENCED
เป็น DATA-EVIDENCED** พร้อมตัวเลขจริง (BK=20 รายการ, PACKAGE=1 รายการที่พบในตัวอย่างนี้)

⚠️ **การค้นพบใหม่ที่ไม่เคยมีในเอกสารไหนมาก่อน**: prefix อย่าง `VASE`, `FLOWER`, `TREE`, `VG`(vertical
garden?), `OASIS`(โฟมปักดอกไม้), `TAPE`(เทปพันก้าน) เป็น**คำภาษาอังกฤษเต็มคำ ไม่ใช่รหัสย่อสายพันธุ์**
— แสดงว่ามี**อนุสัญญาการตั้ง SKU แบบที่ 3** อยู่คู่ขนาน (นอกจาก "มาตรฐานสายพันธุ์" กับ "MTO") คือ
**"อุปกรณ์/ของใช้ประกอบ" ที่ตั้งชื่อ prefix เป็นคำเต็มภาษาอังกฤษแทนรหัสย่อ** — เป็น**ไวยากรณ์ที่ 3**
ที่ไม่มีเอกสารไหนพูดถึงมาก่อนเลย ✅

⚠️ **`OL` (prefix เดียวที่ CLAUDE.md ยืนยันความหมายชัดที่สุด) มีรูปแบบไม่ตรงมาตรฐานปนอยู่ 2 ตัวอย่าง**
(`OL0211`, `OL0111` — 4 หลักแทนที่จะเป็น 2+3=5 หลัก) — **แม้แต่ prefix ที่ "เป็นต้นแบบ" ที่สุดในเอกสาร
ก็ยังไม่ตรงมาตรฐานเองบางส่วน** ✅

### 2.3 กลุ่ม "Other" — พบกลไกเข้ารหัสขนาดแบบที่ 2 ✅

ตัวอย่างเช่น `G00391S`/`G00391L`, `G00340L`/`G00340S`, `PS00007L` — มี**ตัวอักษรต่อท้ายหลังตัวเลข**
(S/L/M/A/B/C) ที่ **ไม่ใช่ variant digit ในตำแหน่งมาตรฐาน** — ดูเหมือนเป็น **S=Small, L=Large** ที่ผูก
กับ SKU เดิมด้วย suffix แทนที่จะฝังในตำแหน่ง variant 2 หลัก

⚠️ **นี่คือกลไกเข้ารหัส "ขนาด" แบบที่ 2 ที่ต่างจากที่พบใน §2.4** — ธุรกิจนี้ใช้**อย่างน้อย 2 วิธี**ที่ต่าง
กันโดยสิ้นเชิงในการสื่อความหมาย "ขนาด": (ก) ใช้ตำแหน่ง variant digit ปกติ (เช่น `01`=S, `02`=L สำหรับ
prefix `ORL`) และ (ข) suffix ตัวอักษรต่อท้าย (เช่น `G00391S` vs `G00391L`) — **ไม่มี field ไหนบอกว่า
prefix ไหนใช้กลไกไหน** ✅ **นี่คือ conflict เพิ่มเติมจากที่ระบุไว้ใน `PRODUCT-NAMING-AND-SKU-
ARCHITECTURE.md` §3.3 เดิม — ตอนนั้นรู้แค่ "variant ambiguous" ตอนนี้รู้ว่ามีถึง 2 กลไกจริง**

### 2.4 หลักฐานยืนยัน "variant digit = ขนาด" (ไม่ใช่สี) ในบางกลุ่ม ✅

จากตัวอย่างต้นไฟล์: `ORL02009`="ใบกล้วยไม้ **L** 118" · `ORL01009`="ใบกล้วยไม้ **S** 58" — variant
digit `02`→L (ใหญ่), `01`→S (เล็ก) — **ยืนยันด้วยข้อมูลจริงว่าธุรกิจนี้ใช้ตำแหน่ง variant ปกติเป็น
"ขนาด" ในบางกลุ่มสินค้าจริง ไม่ใช่แค่ทฤษฎี** — ตรงกับที่ `CLAUDE.md` ระบุไว้ (บางหมวดใช้ variant เป็น
ขนาด/ลำดับแทนสี) แต่ตอนนี้มีตัวอย่างจริงยืนยันแล้ว 🔵→✅

### 2.5 Prefix ที่ "หน้าตาคล้ายกัน แต่ความหมายต่างกันโดยสิ้นเชิง" — พบเคสจริง 3 ตัว ✅✅✅

| Prefix | จำนวน SKU จริง | หมวดหมู่จริง | ชื่อสินค้าตัวอย่าง | ความหมาย |
|---|---|---|---|---|
| `OL` | 16 | ใบ | "มะกอกออลิฟ", "ช่อมะกอก" | มะกอก (olive) — ตรงกับ CLAUDE.md |
| `OR` | 134 | ดอกไม้ | "ออนซิเดียม ขาว", "ไอริส ม่วง" | กล้วยไม้/ไอริส (orchid-type flower) — **คนละความหมายกับ OL** |
| `ORL` | 15 | ใบบูช/ใบ | "ใบกล้วยไม้ 98", "ใบกล้วยไม้ L 118" | ใบกล้วยไม้ (orchid LEAF) — **คนละความหมายกับทั้ง OL และ OR** |

⚠️ **นี่คือหลักฐานที่เป็นรูปธรรมที่สุดในเอกสารทั้งฉบับสำหรับความเสี่ยง "prefix พิมพ์ผิด/สับสน"** — 3
prefix ที่ตัวอักษรคล้ายกันมาก (`OL`/`OR`/`ORL`) แทนสินค้าคนละกลุ่มโดยสิ้นเชิง (มะกอก vs กล้วยไม้ดอก vs
ใบกล้วยไม้) — พนักงานพิมพ์ผิด 1 ตัวอักษรมีโอกาสสูงที่จะได้ prefix ที่ **valid แต่ผิดความหมาย** ไม่ใช่
error ที่เห็นชัด ✅

### 2.6 Prefix ที่ครอบคลุมมากกว่า 1 หมวดหมู่ — ขัดแย้งกับสมมติฐาน "1 prefix = 1 category" ✅✅✅

**60 จาก 112 prefix มาตรฐาน (53.6%) ปรากฏใน**มากกว่า 1 หมวดหมู่** — สูงกว่าครึ่งหนึ่งของ prefix ทั้งหมด

ตัวอย่างที่รุนแรงที่สุด: prefix **`L` ครอบ 8 หมวดหมู่พร้อมกัน**:

```
L → ใบบูช(188) · ใบ(138) · ดอกไม้(37) · ใบไม้แขวน(3) · Realtouch(2) ·
    ไม้แซมไม้ประดับ(2) · กิ่งไม้(2) · ไม่มีรหัสสินค้า(1)
```

§K.1** — เอกสารนั้นตั้งคำถามไว้ว่า "Product Type ควรเป็นระดับหมวดกว้าง (แบบ A) หรือแทนที่ prefix

## 3. Product Naming Structure — วิเคราะห์จริง

### 3.1 ยืนยัน convention "ต่อราคาส่งท้ายชื่อ" ด้วยข้อมูลจริงขนาดใหญ่ ✅✅

- **5,658 จาก 5,903 แถว (95.8%)** มีตัวเลขต่อท้ายชื่อสินค้า — เป็น convention ที่ใช้จริงเกือบทุกแถว
  ไม่ใช่แค่ทฤษฎีจากโค้ด `composedName` (views-main.jsx:9374) ✅

### 3.2 การพิสูจน์สูตร `RETAIL_MULT = 1.25` ด้วยข้อมูลจริง — ผลลัพธ์ที่ชัดเจนที่สุดในเอกสารนี้

เทียบ **ตัวเลขท้ายชื่อ ÷ col_C (ราคาที่สันนิษฐานว่าเป็นราคาขาย)** ในทุกแถวที่เทียบได้ (5,424 แถว):

```
อัตราส่วน 0.80  →  4,723 แถว (87.1% ของแถวที่เทียบได้)
```

`0.80 = 1 ÷ 1.25` **ตรงกับสูตร `sellprice = wholesale × RETAIL_MULT(1.25)`** (views-main.jsx:9369)
**เป๊ะ** ✅✅ — นี่คือหลักฐานที่แข็งแรงที่สุดในเอกสารทั้ง 4 ฉบับที่เขียนมา (รวมฉบับนี้) เพราะ:
1. **ยืนยัน 2 อย่างพร้อมกัน**: (ก) `col_C` คือราคาขายจริง (ข) ตัวเลขท้ายชื่อคือราคาส่งจริงที่พนักงานพิมพ์
2. **ยืนยันว่าตัวคูณ 1.25 ถูกใช้จริงในสเกล 87% ของข้อมูล** ไม่ใช่แค่โค้ดที่เขียนไว้เฉย ๆ
3. ส่วนที่เหลือ 13% ที่ไม่ตรง 0.80 พอดี — น่าจะเป็นสินค้าที่ราคาถูกแก้ที่ ZORT ตรง ๆ หลังสร้าง (ชื่อ
   ไม่ได้อัปเดตตาม ราคาปัจจุบันเปลี่ยนไปแล้ว) — **ยืนยัน pattern "ชื่อกับราคาแยกทางกันได้" ที่ระบุไว้ใน
   `PRODUCT-NAMING-AND-SKU-ARCHITECTURE.md` §2.3 ด้วยตัวเลขจริง** (13% ของ ~5,400 แถว ≈ 700 แถวที่
   ราคาในชื่อไม่ตรงกับราคาจริงปัจจุบันแล้ว)

### 3.3 ไม่มี "material/brand/collection" ในชื่อจริง ✅

สุ่มตรวจชื่อจริงหลายร้อยตัวอย่างระหว่างการวิเคราะห์ (ดู sample ใน §2) — ไม่พบรูปแบบที่บ่งชี้ material/
brand/collection เลย สอดคล้องกับที่ `PRODUCT-NAMING-AND-SKU-ARCHITECTURE.md` สรุปไว้จากโค้ด — **ยกระดับ
จาก CODE-EVIDENCED เป็น DATA-EVIDENCED (เชิงลบ — ไม่พบหลักฐานว่ามีสิ่งเหล่านี้ในทางปฏิบัติ)**

## 6. Contradictions กับเอกสารสถาปัตยกรรมก่อนหน้า — สรุปตรง ๆ ตามที่สั่ง

|---|---|---|
| `PRODUCT-DOMAIN-ARCHITECTURE.md` §K.1 | ตั้งคำถามว่า Product Type ควรเป็นระดับหมวดกว้าง (1 หมวด=1 prefix) หรือคงสายพันธุ์ย่อย | **54% ของ prefix ครอบมากกว่า 1 หมวดอยู่แล้ว** — การ map "1 Type = 1 Category = 1 Prefix" ตามตัวอย่างที่เจ้าของยกมา **ต้องจัดระเบียบข้อมูลเดิมใหม่ ไม่ใช่แค่บันทึก config** |
| `PRODUCT-DOMAIN-ARCHITECTURE.md` §F | หน่วยนับ "ชิ้น" fix พอไหม เป็นคำถามเปิด | **มีหน่วยอื่นอยู่แล้วจริง 199 รายการ** — คำตอบคือ "ไม่พอ" ระบบมีความหลากหลายของหน่วยอยู่แล้วในทางปฏิบัติ |

| `PRODUCT-NAMING-AND-SKU-ARCHITECTURE.md` §1.4 | หมวด `"ไม่มีรหัสสินค้า"` ≈ "สินค้าที่ไม่มี SKU มาตรฐาน" | **เป็นคนละกลุ่มกัน** — แถวไม่มี SKU ส่วนใหญ่ (155/156) มี category **ว่างเปล่า** ไม่ใช่ label "ไม่มีรหัสสินค้า" และเป็นสินค้าคนละประเภท (เฟอร์นิเจอร์/อุปกรณ์ ไม่ใช่ดอกไม้) |

## 7. Recommended Correct Domain Model (ลักษณะที่ evidence บอก — ยังไม่ออกแบบ schema)

> ตามที่สั่ง — **นี่ไม่ใช่การออกแบบ Product Type Registry** เป็นเพียง "ลักษณะที่ข้อมูลจริงบอกว่า domain
> model ที่ถูกต้องต้องรองรับ" เพื่อให้งานออกแบบขั้นต่อไปไม่พลาดสมมติฐาน

1. **Prefix ↔ Category ต้องเป็นความสัมพันธ์แบบ many-to-many หรือต้องมีขั้นตอน "จัดระเบียบใหม่"
   อย่างชัดเจน** — จะสมมติว่าเป็น 1:1 ไม่ได้จากข้อมูลปัจจุบัน (54% ของ prefix ขัดแย้งกับสมมติฐานนี้)
2. **ต้องรองรับอย่างน้อย 3 "ตระกูล SKU"**: มาตรฐาน (90%), MTO/อุปกรณ์ประกอบแบบคำเต็ม (3.2%+), อื่น ๆ ที่
   มีปัญหาเชิงประวัติศาสตร์ (6.6%) — ไม่ใช่แค่ 2 ตระกูลตามที่เข้าใจไว้เดิม (มาตรฐาน vs MTO)
3. **ต้องมีที่เก็บ "แถวที่ไม่ใช่สินค้าขาย"** (ค่าธรรมเนียม เช่น DELIVERY/Fee, และเฟอร์นิเจอร์/อุปกรณ์
   สำนักงานที่ปนอยู่ใน catalog) แยกออกจาก "สินค้าไม่มีรหัส" (`ไม่มีรหัสสินค้า` category) อย่างชัดเจน
   — ปัจจุบันทั้งสองกลุ่มถูกปนกันโดยไม่มี field แยก
4. **Barcode ต้องเป็น field อิสระจริง ไม่ใช่ derived=SKU เสมอ** — มีสินค้าจริง (โดยเฉพาะกลุ่ม `V`-prefix)
   ที่ barcode เป็นตัวเลขยาวแยกต่างหาก (น่าจะเป็นบาร์โค้ดสินค้าที่ผลิตจริง/นำเข้า)
5. **หน่วยนับต้อง configurable ไม่ fix "ชิ้น"** — มีอย่างน้อย 11 หน่วยที่ใช้งานจริงแล้ว
6. **Variant/Size ต้องรองรับได้มากกว่า 1 กลไกการเข้ารหัส** (embedded digit + suffix letter) หรือ
   ตัดสินใจรวมเป็นกลไกเดียวพร้อม migration path สำหรับของเดิมที่ใช้อีกแบบ
7. **Tag ต้องแยกอย่างน้อย 3 มิติ** (ซัพพลายเออร์ / สถานะความสด / รหัสล็อต-รุ่น) ไม่ใช่ 2 มิติตามที่
   ออกแบบไว้เดิม — การแยกด้วยภาษา (Thai/non-Thai) เพียงพอสำหรับมิติ "สถานะ" (`≤ 3 เดือน` เท่านั้นที่
   เป็นภาษาไทยจริง) **แต่ไม่พอสำหรับแยกซัพพลายเออร์ออกจากรหัสล็อต** (ทั้งคู่เป็น non-Thai เหมือนกัน)
8. **ต้องมีนโยบายจัดการ "prefix ที่คล้ายกันแต่ความหมายต่างกัน"** (`OL`/`OR`/`ORL` เป็นตัวอย่างจริงที่
   พิสูจน์แล้ว) — Registry เพียงอย่างเดียวไม่ป้องกันการพิมพ์ผิดที่ได้ prefix ที่ valid แต่ผิดความหมาย
   เว้นแต่จะมีการเตือน/ยืนยันเพิ่มตอนเลือก

## 8. Questions for the Owner

1. **[สำคัญที่สุด]** หัวคอลัมน์ "ชื่อสินค้า **(ทดสอบ)**" (§1.4) — ข้อมูลชุดนี้เป็นข้อมูลทดสอบหรือข้อมูล
   จริง 100%? ถ้าเป็นข้อมูลทดสอบบางส่วน/ทั้งหมด ทุกตัวเลขในเอกสารนี้ต้องตีความใหม่
2. คอลัมน์ `col_A`/`col_B` (header เดิมเป็น "0"/"0") — ตัวไหนคือคลัง (W0002) ตัวไหนคือหน้าร้าน (W0001)?
   หรือเป็นความหมายอื่นที่ไม่ใช่ 2-คลังตามที่ระบบเข้าใจ?
3. **156 แถวที่ไม่มี SKU** (เฟอร์นิเจอร์/อุปกรณ์/ค่าธรรมเนียม ปนอยู่ใน catalog) — ตั้งใจให้อยู่ใน
   ระบบเดียวกับสินค้าขายไหม หรือควรแยกออกไปเป็นคนละ catalog (เช่น "ทรัพย์สิน/อุปกรณ์ภายใน" แยกจาก
   "สินค้าขาย")?
4. `NAMETAG` ที่ปรากฏ 1,262 ครั้งในคอลัมน์ Tag — มีความหมายทางธุรกิจอะไรไหม หรือเป็นค่า default/บั๊ก
   ของระบบ export ที่ควรมองข้าม?
5. Prefix `V` ที่ barcode ต่างจาก SKU เกือบทั้งหมด (96.9%) — เป็นบาร์โค้ดสินค้าจริงที่ผลิต/ซื้อมา
   (เช่นแจกันชุดสำเร็จรูปที่มี barcode โรงงานติดมา) ใช่ไหม? ยืนยันว่า Barcode ควรเป็น field แยกจาก SKU
   จริง ๆ สำหรับสินค้ากลุ่มนี้?
6. Prefix `OL`/`OR`/`ORL` (§2.5) — ยืนยันว่าเป็น 3 กลุ่มสินค้าที่ตั้งใจแยกกันจริง (ไม่ใช่ error สะสม)?
   มี prefix อื่นที่คล้ายกันแบบนี้อีกไหมที่เจ้าของนึกออก (ควรระวังไว้ล่วงหน้า)?
7. Prefix `L` ที่ครอบ 8 หมวดหมู่ (§2.6) — ตั้งใจให้ `L` เป็น prefix "รวม" ที่ใช้ได้หลายหมวด หรือควรถูก
   แยกเป็นหลาย prefix ย่อยตามหมวดจริง (เช่น `L-ใบบูช`, `L-ใบ`, `L-ดอกไม้` แยกกัน)? — คำตอบนี้กำหนด
   ทิศทาง migration ของ prefix ที่ใหญ่ที่สุดในระบบ (373 SKU)
8. กลุ่ม tag ที่ดูเหมือนรหัสล็อต/รุ่น (`T1025`, `Z190625`, `Y2603` ฯลฯ) — ต้องการเก็บข้อมูลนี้เป็น field
   แยก (เช่น "วันที่รับเข้า"/"เลขล็อต") ในอนาคตไหม หรือไม่จำเป็นต้องใช้งานต่อ?
