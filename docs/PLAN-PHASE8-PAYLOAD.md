## 4. แผนหลัก — `products[]` แบบคอลัมน์ (`pv=3`)

```
เดิม:  [{sku:"OL00001", name:"…", qtyStore:5, …อีก 36 คีย์}, × 5484]
ใหม่:  { cols:["sku","name","qtyStore",…], rows:[["OL00001","…",5,…], × 5484] }
```

**ข้อดีที่ทำให้เลือกทางนี้: ไม่ต้องแก้ view สักจุดเดียว** — กางกลับเป็นรูปเดิมที่ `enrichData`
(app.jsx) แบบเดียวกับที่ `expandMonthlyCompact` ทำกับ `mo` อยู่แล้ว · call site ทั้งหมดไม่รู้ตัว

### ขั้นตอน
1. GAS: `packProducts_(products)` → `{cols, rows}` · `cols` มาจาก union ของคีย์ที่มีจริง
2. GAS: ส่งแบบคอลัมน์**เฉพาะเมื่อ `pv=3`** — `pv=2`/ไม่ส่ง = ของเดิมเป๊ะ
3. app.jsx: `expandProductsColumnar(d)` เรียกที่ต้นทาง `enrichData` · ส่ง `pv=3` ทั้งใน
   `fetchFromSheet` **และ prefetch ใน `<head>`** (สองที่ ลืมที่ใดที่หนึ่ง = ได้ก้อนใหญ่ฟรี)
4. เทสต์: กางแล้วต้องได้ object เท่าเดิม**ทุกฟิลด์ทุกตัว** (เทียบ deep-equal กับชุดเดิม)

### ⚠️ กับดัก
- **`pv` ห้ามข้าม** — `.jsx` ใช้ stale-while-revalidate โหลดแรกหลัง deploy ยังรันโค้ดเก่า
  ถ้าเปลี่ยนรูปแบบทันทีทุกคน เครื่องที่ยังเก่าจะได้ `products` ที่อ่านไม่เป็น = **จอเปล่า**
- **ค่า `undefined` กับ `null` ไม่เหมือนกัน** — `JSON.stringify` ตัดคีย์ที่เป็น `undefined` ทิ้ง
  แต่ในรูปแบบคอลัมน์ทุกแถวยาวเท่ากัน ต้องตัดสินใจว่า "ไม่มีค่า" เก็บเป็นอะไร แล้ว**กางกลับให้ตรง**
  ไม่งั้นโค้ดที่เช็ค `if (p.mo)` (แยก "ไม่มีข้อมูลขาย" ออกจาก "ขายได้ 0") จะเพี้ยนเงียบ ๆ
  → เก็บเป็น `null` แล้วตอนกาง **ไม่ต้องใส่คีย์นั้นเลย** จึงจะเท่าของเดิม
- **ลำดับ `cols` ต้องมาจาก payload** ห้าม hard-code ฝั่ง client (ซ้ำรอย stocklite)

**ผลที่คาด**: ตัดได้ราว 40-55% ของ `products[]` · **ต้องยืนยันด้วยขั้นที่ 0 ก่อน**

## 4b. คีย์ที่ตัดไปแล้ว (6 ส.ค. 2026) — ตัดได้โดยไม่ต้องรอผลวัด

สามตัวนี้พิสูจน์จากโค้ดได้ว่า **client สร้างทับ/ไม่เคยใช้อยู่แล้ว** ผลวัดบอกได้แค่ว่าประหยัด
เท่าไร ไม่ได้บอกว่าควรตัดไหม · **ไม่ต้อง gate ด้วย `pv`** เพราะเครื่องที่ยังรันโค้ดเก่าก็สร้างทับเอง

| คีย์ | ทำไมตัดได้ |
|---|---|
| `mtoGroups` (top-level) | `enrichData` (app.jsx) สร้างใหม่ทับทุกครั้ง · เก็บ product object ซ้ำอีกชุดเต็ม ๆ ใน `variants[]` · ที่จริงฝั่ง GAS คำนวณผิดมาตลอดด้วย — จัดกลุ่มด้วย `p.cat` ซึ่งฝั่ง GAS ไม่มีคีย์นี้ (มีแต่ `category`) ทุกตัวจึงตกเข้ากลุ่มเดียว |
| `color` | เป็น `null` ทุกแถวเสมอ · client เติมเองด้วย `detectColor(p.name)` เงื่อนไข `if (!p.color)` |
| `locationRaw` | (ตัดไปตั้งแต่ Phase 7.5) ไม่มีใครอ่านเลย |

**ยังไม่ตัด — ตั้งใจ:**
- `monthly: []` — ถึงจะดูตายเหมือนกัน แต่ `OverviewView` ใช้ **"มีคีย์ vs ไม่มีคีย์"** แยก
  "ไม่มีข้อมูลขาย" ออกจาก "ขายได้ 0" การตัดจะเปลี่ยนความหมายแบบไม่มี error ให้เห็น
  → ทำพร้อมงานคอลัมน์ที่จัดการ null/undefined ทั้งชุดทีเดียว
- `warehouseQty` — เท่ากับ `qtyWH` เป๊ะ และ `whQty()` fallback ไป `qtyWH` อยู่แล้ว **แต่**
  การตัดต้องแก้ assertion ใน `tests/qtyloc.test.js` ซึ่งเป็นเทสต์ที่ล็อกบั๊ก WL ไว้
  → รอทำพร้อมคอลัมน์ ตอนที่มี round-trip test รองรับแล้ว

## 5. แผนรอง (ทำต่อได้ถ้ายังไม่พอ) — เรียงตามคุ้มค่า

1. **เลิกส่งฟิลด์ที่ client คำนวณเองได้** — `qty` `isOOS` `isOversold` `qtyStatus`
   `stockValue` `stockValueWH` `stockValueStore` ล้วนได้จาก `qtyStore`/`qtyWH`/`price`
   · สูตรมีอยู่ฝั่ง client แล้วใน `fetchStockLite` (ยกมาใช้ซ้ำได้เลย)
   · ⚠️ **สูตรต้องตรงกับ `applyQtyLocToProduct_` เป๊ะ** ไม่งั้นซ้ำรอยบั๊ก WL (มีของจริงแต่โชว์ "หมด")
2. **`imageUrl` ตัด prefix ที่ซ้ำกันทุกแถว** — วัดก่อนว่า URL จาก ZORT ขึ้นต้นเหมือนกันจริงไหม
   ส่ง prefix มาครั้งเดียวใน payload แล้วแต่ละแถวเก็บแค่ส่วนท้าย
3. **ไม่ส่งสินค้าที่ไม่มีทั้งของและประวัติขาย** — ต้องถามเจ้าของก่อน (สินค้าเลิกขายยังต้องค้นเจอไหม)
4. **แบ่งก้อน** — `products[]` แยกเป็นคำขอที่สอง โหลดหน้าอื่นได้ก่อน · ซับซ้อนกว่ามาก
   เก็บไว้เป็นทางสุดท้าย

## 6. เกณฑ์ว่า "ถึงเป้าแล้ว"

วัดด้วย `loadtest.html` 15 request พร้อมกัน (เครื่อง/เน็ตเดิมกับรอบก่อน เพื่อเทียบได้):

- [ ] ได้ JSON ครบ **15/15** (ไม่มี HTML/404 เลย)
- [ ] ช้าสุด **< 15 วิ**
- [ ] `[perf] ส่งจริง` ของ variant `full` **< 2,000 KB**
- [ ] เปิดแอปจริงบนมือถือพนักงาน ไม่เห็นแถบเหลือง/แถบแดง ตลอดช่วงเช้า

⚠️ loadtest ยิงจาก **browser เดียว เน็ตเส้นเดียว** — ของจริง 15 เครื่องแยกกันจะเบากว่านี้
(ยกเว้นทุกคนอยู่ WiFi ร้านเส้นเดียวกัน ซึ่งเป็นกรณีจริง) อย่าเอาเลขนี้ไปอ้างตรง ๆ

## 7. สิ่งที่ **ห้ามทำ** (เคยพลาดมาแล้ว)

- ❌ สรุปสาเหตุจาก "ตัวเลขใกล้กัน" — Phase 7.4 เคยโทษคิวล็อกทั้งที่ไม่มี execution ไหนยาวถึง 25 วิ
  **เวลาที่ browser เห็น ≠ เวลาที่ script ใช้** ส่วนต่างอยู่ที่ขั้นดาวน์โหลด แยกสองอย่างนี้เสมอ
- ❌ ตัด payload ตาม role เพิ่ม — วัดแล้ว `lite` เล็กกว่า `full` แค่ **8%** น้ำหนักอยู่ที่
  `products[]` ซึ่งทุก role ได้เหมือนกัน
- ❌ แตะ `p.price` ที่ต้นทาง — POS/ใบเสนอราคาใช้ตัวเดียวกัน จะเพี้ยนทั้งระบบ
- ❌ ปล่อยให้ `invalidateCache_` ลืม variant/คีย์ใหม่ — role นั้นจะเห็นข้อมูลเก่าค้างหลังมีคนแก้ข้อมูล
