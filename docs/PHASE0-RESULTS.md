# Phase 0 — ใบวัดผล (กรอกตัวเลขจริงลงในนี้)

คู่กับ `docs/PLAN-PERF-LOGIN-MULTIUSER.md` · **ยังไม่แก้อะไรที่กระทบผู้ใช้เลยในเฟสนี้**
เพิ่มมาแค่เครื่องมือวัด (อ่านอย่างเดียว) + บรรทัด log ในเส้นทางที่เดิมมองไม่เห็น

> ทำไมต้องกรอก: ข้อ 1c ในแผน (“จะทำ Phase 4 ไหม”) เป็นงานเสี่ยงสูงสุดในเอกสาร
> และตัดสินจากตัวเลข 4 ตัวข้างล่างนี้ล้วน ๆ · เดาแทนการวัด = ลงแรง 3 วันผิดจุด

## ขั้นที่ 1 — trigger กินโควตาเท่าไหร่ (2 นาที)

GAS editor → เลือกฟังก์ชัน **`perfCheckTriggers`** → Run → ดู Execution log

รายงานจะบอก: trigger ที่ติดตั้งอยู่จริง + ประมาณครั้ง/วัน · ตัวที่ติดตั้งซ้ำ ·
`backfillZortOrders` ที่ควรถูกลบไปแล้ว · สถานะ flag ต่าง ๆ · โควตา LINE เดือนนี้

| กรอก | ค่า |
|---|---|
| trigger ทั้งหมดกี่ตัว | |
| รวมกี่ครั้ง/วัน | |
| มี trigger ติดตั้งซ้ำไหม | |
| `backfillZortOrders` ยังวิ่งอยู่ไหม (ควรลบถ้า `backfill_done=1`) | |

**ทำทันทีถ้าเจอ**: มีตัวซ้ำ → รัน setup ของตัวนั้นใหม่ 1 ครั้ง (มันลบตัวซ้ำให้เอง) ·
backfill ยังวิ่งทั้งที่จบแล้ว → รัน `stopBackfill()` (ได้คืน 288 execution/วันฟรี ๆ)

## ขั้นที่ 2 — สร้าง payload หนึ่งรอบใช้เวลาเท่าไหร่ (2 นาที)

GAS editor → **`perfMeasureBuild`** → Run → ดู Execution log (2 บรรทัด: `[perf] buildFullData_ …`
กับ `══ Phase 0 …`) · **อ่านอย่างเดียว ไม่เขียน cache ไม่เขียนชีต** รันซ้ำได้ไม่เสียหาย

| กรอก | ค่า (วัดจริง 5 ส.ค. 2026) |
|---|---|
| `buildFullData_` รวม | **9,807 ms** |
| ขั้นที่กินเวลามากสุด 3 อันดับ | `batchGet` 2,545 · `assemble` 1,500 · `purchases` 1,362 |
| stringify ทุก variant | 332 ms (full 121 / ops 112 / lite 99) |
| ขนาด payload: full / ops / lite | **4,576 / 4,382 / 4,200 KB** |
| ชีตสต็อก กี่แถว × กี่คอลัมน์ | 5,876 × 12 |
| **รวมที่ผู้ใช้คนแรกต้องรอ** | **≈ 10,141 ms** |

### แยกเวลาเป็นกลุ่ม (ตัวเลขที่ใช้ตัดสินใจจริง)

| กลุ่ม | ms | % | ขั้นที่รวมอยู่ |
|---|---|---|---|
| **อ่านชีต (I/O)** | **6,818** | **70%** | batchGet 2545 · purchases 1362 · qtyByLocation 1247 · mtoJobs 826 · transferHist 456 · unscanned 382 |
| `assemble` | 1,500 | 15% | **ไม่ใช่การประกอบล้วน** — มี I/O ซ่อน (ดูด้านล่าง) |
| แปลงข้อมูลสินค้า (`products`) | 1,210 | 12% | parse 5,876 แถว |
| **คำนวณจริง (`enrich`+`index`)** | **122** | **1.2%** | ← ตัวที่ Phase 4 ตั้งใจจะประหยัด |
| stringify + chunk | 332 | 3% | |

### ข้อสรุปตามตารางตัดสินใจในขั้นที่ 5

- ❌ **ไม่เข้าเงื่อนไข "MISS < 2,000 ms"** — 9,807 ms ห่างจากเกณฑ์ ~5 เท่า
- ❌ **`enrich`/`index` ไม่ได้หนัก** — 122 ms = **1.2%** ของ build
  → **Phase 4 (cache 2 ชั้น) ตัดทิ้งได้** · เป็นงานที่เอกสารระบุเองว่า "เสี่ยงสูงสุด"
  และกิน 0-3 วัน แต่สิ่งที่มันประหยัดได้จริงคือ 122 ms จาก 9,807 ms
- ✅ **เข้าเงื่อนไข "`batchGet` หนักสุด → อ่านชีตหนัก"** → ต้องลดจำนวน/ขนาดชีตที่อ่าน
- ⚠️ **stringify ไม่ใช่คอขวดฝั่ง GAS (332 ms)** แต่ **payload 4.5 MB เป็นคอขวดที่ "ท่อ"**
  ฝั่งมือถือ — และ variant ตาม role ตัดได้แค่ **8%** (4,576 → 4,200 KB) เพราะก้อนใหญ่คือ
  `products[]` ที่ทุก role ต้องใช้ → 7.4(ข) ต้องตัด "ตามแท็บ" ไม่ใช่ "ตาม role" ถึงจะได้ผล

### ของฟรีที่เจอระหว่างอ่านตัวเลข (แผนไม่มีข้อนี้)

1. **`readQtyByLocation_` = 1,247 ms อ่านชีตสต็อกซ้ำทั้งที่มีอยู่ในหน่วยความจำแล้ว**
   `stockRows` (จาก `batchGet`) มีคอลัมน์ G/H/I ที่ต้องการครบอยู่แล้ว และ `readSysQty_`
   ก็อ่าน G/H จาก `stockRows` อยู่แล้ว · คอมเมนต์ในโค้ดบอกว่าไม่รวมใน `batchGet` เพราะ
   "วันที่เป็น serial" — แต่ **ฟังก์ชันนี้ไม่อ่านคอลัมน์วันที่เลย** เหตุผลนั้นใช้กับ
   `readPurchases_` เท่านั้น
   · ⚠️ ต้องแปลงด้วย `parseQty_`/`parseNum_` (ตัดลูกน้ำให้แล้ว) ไม่ใช่ `parseInt`/`parseFloat`
   ดิบ — display value `"1,234"` เข้า `parseInt` ได้ `1` **เงียบ ๆ**
2. **`assemble` 1,500 ms ไม่ใช่ "การประกอบ object"** — มี I/O ซ่อน:
   `readStockCheckRequests_()` เปิดชีตอีกใบ · `PropertiesService` 7 รอบ ·
   `CacheService` 1 รอบ · แล้ววน `products` **10 รอบ** (4 `filter` + 6 `reduce` ใน `totals`)
   ซึ่งยุบเหลือรอบเดียวได้

## ขั้นที่ 3 — ของจริงตอนคนใช้งาน (ดูย้อนหลัง 1 วันทำงาน)

หลัง deploy รอบนี้ Executions log จะมีบรรทัดใหม่ `[perf] doGet HIT/MISS/FRESH …`
**เดิมวัดแต่ตอน build (ซึ่งเกิดน้อยที่สุด) ส่วนเส้นทาง cache hit ที่เกิดบ่อยที่สุดไม่เคยถูกวัดเลย**
— จากนี้แยกออกแล้วว่า request ที่ช้าเป็นเพราะ build ใหม่ หรือเพราะ cache เองก็ช้า

เปิด GAS editor → Executions → เลือกช่วงเวลาที่คนใช้เยอะสุด (เช่น 8:00-10:00)

| กรอก | ค่า |
|---|---|
| execution ทั้งหมดในชั่วโมงที่คนใช้เยอะสุด | |
| สัดส่วน HIT : MISS (นับจากบรรทัด `[perf] doGet`) | |
| HIT ใช้เวลาเฉลี่ยกี่ ms | |
| MISS ใช้เวลาเฉลี่ยกี่ ms (แยก `build=` กับ `shape+cache=`) | |
| มี execution ที่ error/timeout กี่ % | |

## ขั้นที่ 4 — load test เส้นฐาน (10 นาที)

เปิด **`tests/loadtest.html`** บนคอม (ดับเบิลคลิกไฟล์ก็ได้) → ใส่ URL /exec + APP_TOKEN
→ ยิง 15 request พร้อมกัน · **อ่านอย่างเดียว ไม่บันทึกอะไร**

ยิง **2 สถานการณ์** (สำคัญทั้งคู่ อย่าทำแค่อันแรก):

| # | สถานการณ์ | มัธยฐาน | ช้าสุด | ได้ HTML แทน JSON |
|---|---|---|---|---|
| A | cache อุ่น (ไม่มีใครบันทึกอะไร) | | | |
| B | **หลังมีคนกดบันทึกทันที** (สั่งของ/โอน/รับของ แล้วยิงภายใน 2-3 วิ) | | | |

**B คือตัวชี้ขาด** — เป็น cache stampede ในแผนข้อ 7.3 ที่ระบุว่าเป็น “ตัวที่จะพังก่อนเพื่อน
ตอน 15 คน” · ถ้า B ช้ากว่า A มาก หรือมี HTML โผล่แม้แต่อันเดียว = ยืนยันว่าต้องทำข้อ 7.3 จริง

## ขั้นที่ 5 — ตัดสินใจ (ทำหลังกรอกครบ)

อ่านตัวเลขแล้วเลือกทางตามตารางนี้ ไม่ต้องเดา:

| ถ้า… | แปลว่า | ทำอะไรต่อ |
|---|---|---|
| B ช้ากว่า A ชัดเจน / มี HTML โผล่ | stampede เป็นของจริง | **7.3 single-flight + stale-while-rebuild** (ลำดับ 2 ในแผน) |
| MISS รวม < 2,000 ms | build ไม่ใช่คอขวด | **ข้าม Phase 4 ไปเลย** ไปลงแรง Phase 1-3 |
| `enrich`/`index` กินเวลามากสุด | คำนวณหนัก | Phase 4 แยก cache 2 ชั้น ได้ผลเต็ม |
| `batchGet` กินเวลามากสุด | อ่านชีตหนัก | แยกชั้นช่วยน้อย → ลดจำนวน/ขนาดชีตที่อ่านแทน |
| `shape+cache` กินเวลามากสุด | payload ใหญ่เกิน | ไป **7.4(ข) ลด payload** ก่อน Phase 4 |
| เวลารวม trigger ใกล้ 90 นาที/วัน | โควตาใกล้เต็ม | ลด `drainNotiQueue` เหลือทุก 5 นาทีทันที |

## หมายเหตุเรื่องบรรทัด log ที่เพิ่มเข้าไป

- `[perf] doGet …` พิมพ์ **ทุก request ของเส้นทาง payload** ต้นทุน = `Date.now()` + `Logger.log`
  ไม่มีการอ่าน Script Property/ชีตเพิ่ม (จงใจไม่ทำสวิตช์เปิด-ปิดผ่าน Property เพราะการอ่าน
  Property ทุก request แพงกว่าตัว log ที่พยายามจะปิดเสียอีก)
- ถ้าจบ Phase 0 แล้วรู้สึกว่า log รก ลบ `perfLogDoGet_` ทิ้งได้ — เทสต์ `tests/perf-phase0.test.js`
  จะแดงเพื่อเตือนว่ากำลังถอดเครื่องมือวัดออก ตั้งใจแล้วค่อยแก้เทสต์ตาม
