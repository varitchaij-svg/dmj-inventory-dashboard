# แผน: ระบบล็อกอินพนักงาน (ระบุตัวตนรายบุคคล + ชื่อ + ตำแหน่ง)

สถานะ: ข้อเสนอ (ยังไม่ implement) · เขียนเมื่อ 2026-07-29

## 1. ปัญหาของระบบปัจจุบัน

ตอนนี้ (`LoginScreen` ใน `app.jsx` บรรทัด ~63) หน้าล็อกอินคือ **"เลือกตำแหน่ง"** ไม่ใช่ "ล็อกอิน":

- กดการ์ด หน้าร้าน/คลัง/Sale = เข้าได้เลย **ไม่มีรหัสอะไรทั้งสิ้น**
- มีแค่ `owner` ที่ต้องใส่ PIN (`OWNER_PIN` ตรวจฝั่ง GAS ผ่าน `action=verifyPin`)
- `sessionStorage.dmj_role` เก็บแค่ string role → เปิด DevTools เซ็ตเป็น `owner` ก็ได้สิทธิ์เจ้าของ
  (frontend เป็นคนตัดสินสิทธิ์ทั้งหมด — server ไม่เคยตรวจ)
- ทุก action ส่ง `actor = role` เท่านั้น → **Audit Log บอกได้แค่ "คลังสินค้า" ไม่รู้ว่าใคร**
  (ในโค้ดเขียนหมายเหตุไว้เองที่ `appsscript_complete.gs:194`)

ผลกระทบจริง: ของหาย/นับผิด/โอนผิด → สืบไม่ได้ว่าใครทำ · วัด productivity รายคนไม่ได้ ·
เตือนเฉพาะคนที่รับผิดชอบไม่ได้ (ต้องเตือนทั้งกลุ่ม)

**เป้าหมายของแผนนี้**: ให้ทุกคน (พนักงาน + เจ้าของ) มีบัญชีของตัวเอง มี **ชื่อ** และ **ตำแหน่ง**
เก็บในระบบ, `actor` เป็นรายบุคคล, และ **server เป็นคนตัดสินสิทธิ์** ไม่ใช่ frontend

## 2. LINE หรือ Google — ข้อสรุป

> ### ✅ แนะนำ: **LINE Login เป็นหลัก** + PIN สำรอง · Google เก็บไว้เป็น optional สำหรับออฟฟิศ

| หัวข้อ | LINE Login | Google Sign-In |
|---|---|---|
| พนักงานมีบัญชีอยู่แล้ว | **~100%** ทุกคนใช้ LINE อยู่แล้วบนมือถือ | ไม่แน่นอน — แรงงานต่างด้าวหลายคนไม่มี/จำรหัส Gmail ไม่ได้ |
| จำนวนขั้นตอนตอนล็อกอิน | กดปุ่มเดียว → LINE เด้งขึ้นมา → "อนุญาต" → กลับเข้าแอป (ไม่ต้องพิมพ์อะไร) | ถ้าเบราว์เซอร์ล็อกอิน Google อยู่แล้ว = กดเลือกบัญชี · **ถ้าไม่ = ต้องพิมพ์อีเมล+รหัส+2FA** |
| บน iPhone / Safari | ดี (redirect ปกติ) · ถ้าเปิดจากแชท LINE ใช้ LIFF ยิ่งลื่น | แย่สุด — Safari มักไม่มี session Google ค้างไว้ ต้องพิมพ์ทุกครั้งที่หลุด |
| ภาษา/ความคุ้นเคย | ไทย + หน้าตาที่พนักงานเห็นทุกวัน | หน้าจอ Google ภาษาอังกฤษปนไทย สับสนกว่า |
| ต่อยอดกับของที่มีอยู่ | **สูงมาก** — เรามี LINE OA + ระบบคิวแจ้งเตือนอยู่แล้ว ได้ `userId` มาแล้ว **เตือนรายบุคคลได้ทันที** (เช่น "ป้าแดง งานจัดของค้าง 3 รายการ") | ไม่ต่อยอดอะไรกับ LINE OA |
| งาน setup | สร้าง LINE Login channel ใน LINE Developers (ควรอยู่ provider เดียวกับ OA) + ใส่ callback URL | สร้าง OAuth Client ID ใน Google Cloud Console |
| ความยากฝั่งโค้ด | ปานกลาง (แลก code → token → `verify` id_token ที่ `api.line.me`) | ง่ายกว่านิดหน่อย (Google Identity Services ส่ง JWT มาให้เลย) |
| ค่าใช้จ่าย | ฟรี (LINE Login ไม่กิน quota ข้อความ) | ฟรี |

**เหตุผลตัดสิน**: ผู้ใช้หลักคือพนักงานหน้าร้าน/คลัง บางคนเป็นแรงงานต่างด้าวที่ไม่ถนัดเทคโนโลยี
สิ่งที่สำคัญที่สุดคือ **"ไม่ต้องพิมพ์อะไรเลย"** — LINE ชนะขาดข้อนี้ และยังแถม `lineUserId`
ที่ทำให้เราส่งแจ้งเตือนเจาะรายคนได้ในอนาคต (ซึ่งเป็นของที่อยากได้อยู่แล้วตาม Sprint 3)

Google ยังมีที่ทางอยู่: เจ้าของ/ฝ่ายบัญชีที่ทำงานบนคอมและมี Google account ผูกกับชีตอยู่แล้ว
→ ทำเป็น **ปุ่มที่ 2** ได้ในเฟสหลัง แต่ **ไม่ควรเป็นทางหลักของพนักงาน**

## 3. สถาปัตยกรรมที่เสนอ

```
[มือถือพนักงาน]                    [Cloudflare Pages]              [GAS + Sheets]
   กด "เข้าสู่ระบบด้วย LINE"
        │
        ├─ redirect → access.line.me (LINE ถามอนุญาต)
        │                    │
        │   ◄────────────────┘  กลับมาที่ /?code=...&state=...
        │
        └─ POST {action:"authLine", code, redirectUri}  ──────────►  แลก code → access_token
                                                                     verify id_token → sub, name
                                                                     หา/สร้างแถวในชีต "พนักงาน"
        ◄── {ok, sessionToken, staff:{name, role, status}} ─────────  ออก sessionToken (30 วัน)

   ทุก action ต่อจากนี้ ส่ง sessionToken ไปด้วย → GAS resolve เป็น {ชื่อ, ตำแหน่ง} เอง
```

### 3.1 ชีตใหม่: `พนักงาน`

| คอลัมน์ | ความหมาย |
|---|---|
| A `staffId` | รหัสภายใน (`ST0001`…) |
| B `provider` | `line` / `google` / `pin` |
| C `providerUserId` | LINE `sub` (userId) หรือ Google `sub` — **คีย์ที่ใช้จับคู่ตอนล็อกอิน** |
| D `displayName` | ชื่อที่จะขึ้นใน Audit Log (เจ้าของแก้ได้ เช่น "ป้าแดง") |
| E `lineDisplayName` | ชื่อที่ดึงมาจาก LINE ตอนสมัคร (ไว้ให้เจ้าของดูว่าใครขอเข้า) |
| F `role` | `owner` / `employee` / `warehouse` / `frontstore` / `saler` |
| G `status` | `pending` (รออนุมัติ) / `active` / `disabled` |
| H `pictureUrl` | รูปโปรไฟล์ LINE (โชว์ในหน้าจัดการพนักงาน) |
| I `createdAt` | เวลาสมัคร |
| J `lastLoginAt` | เข้าล่าสุด |
| K `note` | หมายเหตุ (กะ/สาขา/เบอร์โทร) |

### 3.2 ชีตใหม่: `เซสชัน` (หรือใช้ CacheService + Script Properties)

`token(UUID)` · `staffId` · `createdAt` · `expiresAt` · `lastSeenAt` · `revoked`
→ ล็อกเอาต์ = ตั้ง `revoked=TRUE` · เจ้าของ "เตะออกจากระบบ" ได้จากหน้าจัดการพนักงาน

> ใช้ชีตแทน Script Properties เพราะดูย้อนหลังได้ว่าใครล็อกอินจากเครื่องไหนเมื่อไหร่
> และไม่ชน quota ของ Properties ตอนพนักงานหลายคน

### 3.3 Endpoint ใหม่ใน `appsscript_complete.gs`

| action | ใคร | ทำอะไร |
|---|---|---|
| `authLine` | public | แลก `code` → `POST https://api.line.me/oauth2/v2.1/token` → verify `id_token` ที่ `https://api.line.me/oauth2/v2.1/verify` (ตรวจ `aud` = channel id, `exp`) → upsert แถวพนักงาน → ออก session |
| `authGoogle` *(เฟสหลัง)* | public | verify JWT ที่ `https://oauth2.googleapis.com/tokeninfo?id_token=` → เหมือนกัน |
| `me` | มี token | คืน `{name, role, status}` (frontend เรียกตอนเปิดแอปเพื่อ resume session) |
| `logout` | มี token | revoke session |
| `listStaff` | owner | รายชื่อพนักงานทั้งหมด (สำหรับหน้าจัดการ) |
| `saveStaff` | owner | ตั้ง `displayName` / `role` / `status` |

**Secret ใหม่ใน Script Properties** (ห้าม commit): `LINE_LOGIN_CHANNEL_ID`,
`LINE_LOGIN_CHANNEL_SECRET`, (เฟสหลัง) `GOOGLE_CLIENT_ID`

### 3.4 การบังคับสิทธิ์ฝั่ง server (สำคัญที่สุด)

เพิ่มที่ต้น `doPost` (ตอนนี้อยู่ราวบรรทัด 331 ที่ `var actor = data.actor || "ไม่ระบุ"`):

```js
var sess = resolveSession_(data.sessionToken);      // null ถ้าไม่มี/หมดอายุ/ถูก revoke
var actor = sess ? (sess.displayName + " (" + ROLE_TH[sess.role] + ")") : (data.actor || "ไม่ระบุ");
if (sess && !canDo_(sess.role, data.action)) return jsonErr_("ไม่มีสิทธิ์ทำรายการนี้");
```

- `canDo_(role, action)` = ตาราง whitelist ฝั่ง server (ล้อกับ `ROLE_TABS` ใน `app.jsx`)
- action ที่ต้องเป็น owner เท่านั้น: `saveThresholds`, `resetNegativeStock`, `deleteOrderRows`,
  `zeroStockItem`, `approveQuotation`, `voidZortQuotation`, `saveStaff`, `issueFullTaxInvoice`
- **ช่วง migration**: ถ้าไม่มี `sessionToken` ยัง**ปล่อยผ่าน**แบบเดิม (ไม่งั้นเครื่องเก่าพัง)
  → พอพนักงานย้ายมาครบแล้วค่อยพลิก Script Property `REQUIRE_LOGIN='true'` เพื่อบังคับ

### 3.5 Frontend

- `LoginScreen` ใหม่: โลโก้ + ปุ่มเขียวใหญ่เต็มความกว้าง **"เข้าสู่ระบบด้วย LINE"** (สูง ≥56px)
  ไม่มีอะไรให้พิมพ์ · ใต้ปุ่มมีลิงก์เล็ก "เข้าด้วยรหัสสำรอง" (ของเดิม เผื่อ LINE ล่ม/เครื่องมีปัญหา)
- หน้า **"รออนุมัติ"**: ล็อกอินครั้งแรก → เห็นชื่อ+รูปตัวเอง + ข้อความ "รอเจ้าของอนุมัติ
  แล้วกดปุ่มนี้อีกครั้ง" (พร้อมยิงแจ้งเตือน LINE หาเจ้าของผ่านคิว `enqueueNoti_` channel `secondary`)
- เก็บ `sessionToken` ใน `localStorage` (ไม่ใช่ `sessionStorage`) → **ไม่ต้องล็อกอินใหม่ทุกครั้งที่ปิดแอป**
  (ข้อนี้สำคัญกับ PWA บนมือถือมาก) · role/ชื่อ เก็บใน state ที่ได้จาก `me` ตอนเปิดแอป
- **แท็บใหม่ `staff` (owner เท่านั้น)**: การ์ดพนักงานพร้อมรูป LINE · แก้ชื่อ · เลือกตำแหน่ง (dropdown)
  · ปุ่ม อนุมัติ / ระงับ / เตะออกจากระบบ · โชว์ "เข้าล่าสุด"
- Header เดิมที่โชว์ตัวอักษรย่อ role → เปลี่ยนเป็น **รูปโปรไฟล์ + ชื่อจริง** (แตะ = ออกจากระบบ)

### 3.6 เจ้าของคนแรกเข้าระบบยังไง (bootstrap)

ชีต `พนักงาน` ว่าง → คนแรกที่ล็อกอินสำเร็จได้ `role=owner, status=active` อัตโนมัติ
(หรือปลอดภัยกว่า: เจ้าของเอา LINE userId ของตัวเองใส่ Script Property `OWNER_LINE_SUB` ไว้ก่อน)
หลังจากนั้นทุกคนที่เข้ามาใหม่ = `pending` เสมอ

## 4. เรื่องที่ต้องระวัง (จากบริบทหน้างานจริง)

1. **เครื่องกลาง/แท็บเล็ตที่ใช้ร่วมกัน** — ถ้าหน้าร้านใช้แท็บเล็ตเครื่องเดียวหลายคน การบังคับ
   ล็อกอินรายคนจะกลายเป็นภาระ · ทางออก: ปุ่ม "สลับผู้ใช้" ค้างไว้บนหัวจอ + จำได้ 3 คนล่าสุด
   (แตะรูปตัวเอง = เข้าเลย ไม่ต้องผ่าน LINE ใหม่ ถ้า session ยังไม่หมดอายุ)
   **ต้องถามเจ้าของก่อนว่าแต่ละจุดใช้มือถือส่วนตัว หรือเครื่องกลาง** — คำตอบเปลี่ยนดีไซน์ข้อนี้
2. **LINE Login ต้องมี callback URL แบบ https** → ใช้ `https://dmj-inventory-dashboard.pages.dev`
   ได้เลย (ห้าม redirect ตรงไปที่ URL ของ GAS — ให้หน้าเว็บรับ `code` แล้ว POST ต่อไป GAS)
3. **`state` parameter ต้องสุ่มและตรวจกลับ** (กัน CSRF) · เก็บใน `sessionStorage` ก่อน redirect
4. **GAS ตั้ง cookie httpOnly ไม่ได้** → token อยู่ใน localStorage เป็นข้อจำกัดที่ยอมรับได้
   ในบริบทนี้ (ระบบหลังร้าน ไม่มีข้อมูลการเงินลูกค้าจำนวนมาก) แต่ต้องตั้ง **อายุ 30 วัน + revoke ได้**
5. **ห้ามพัง flow เดิมระหว่างทาง** — พนักงานต้องทำงานได้ทุกวัน จึงต้องเปิดเป็นเฟส
   และมี `REQUIRE_LOGIN` เป็นสวิตช์ถอยกลับได้
6. **Audit Log ย้อนหลัง** จะยังเป็นชื่อ role อยู่ — ไม่ต้องแก้ของเก่า แค่ของใหม่เป็นชื่อคน
7. **PDPA/ความยินยอม** — เก็บชื่อ+รูป LINE ของพนักงาน ควรมีข้อความสั้น ๆ ในหน้าล็อกอินว่า
   ระบบเก็บชื่อและบันทึกการใช้งานเพื่อตรวจสอบงาน

## 5. แผนการทำเป็นเฟส

| เฟส | ขอบเขต | ผลลัพธ์ที่จับต้องได้ |
|---|---|---|
| **0** | เจ้าของสร้าง LINE Login channel + ใส่ Script Properties 2 ตัว | พร้อมต่อ |
| **1** | ชีต `พนักงาน` + `เซสชัน` · `authLine` / `me` / `logout` · LoginScreen ปุ่ม LINE · หน้า "รออนุมัติ" · ปุ่มรหัสสำรองยังอยู่ | ล็อกอินด้วย LINE ได้จริง แต่ยังไม่บังคับ |
| **2** | แท็บ `staff` (owner) — อนุมัติ/ตั้งชื่อ/ตั้งตำแหน่ง/ระงับ | เจ้าของคุมรายชื่อ + ตำแหน่งได้เอง |
| **3** | `actor` เป็นชื่อคนจริงทุก action + Audit Log แสดงชื่อ + filter รายคน | สืบได้ว่าใครทำอะไร |
| **4** | `canDo_` บังคับสิทธิ์ฝั่ง server + เปิด `REQUIRE_LOGIN='true'` | ปิดช่องโกงสิทธิ์จาก DevTools |
| **5** *(ทางเลือก)* | Google Sign-In เป็นปุ่มที่ 2 · แจ้งเตือน LINE รายบุคคล · สรุปงานรายคน (นับกี่ล็อค/โอนกี่ครั้ง) | ต่อยอด |

เฟส 1–2 คือแกนหลัก · เฟส 4 ห้ามเปิดจนกว่าพนักงานทุกคนจะย้ายมาครบ (ดูจาก `lastLoginAt` ในชีต)

## 6. คำถามที่ต้องได้คำตอบจากเจ้าของก่อนเริ่มลงมือ

1. แต่ละจุดงาน (หน้าร้าน / คลัง / Sale) ใช้ **มือถือส่วนตัวของพนักงาน** หรือ **เครื่องกลางของร้าน**
   → ถ้าเป็นเครื่องกลาง ต้องออกแบบ "สลับผู้ใช้" ให้เร็วเป็นพิเศษ
2. พนักงานทุกคน (รวมแรงงานต่างด้าว) มี LINE บนมือถือที่ใช้ทำงานครบไหม
3. ตอนนี้มีพนักงานกี่คน ตำแหน่งอะไรบ้าง — ตรงกับ 5 role เดิมไหม หรือต้องเพิ่ม (เช่น หัวหน้ากะ, บัญชี)
4. ต้องการให้ "ระงับ/ลบ" พนักงานที่ลาออกได้ทันทีจากหน้าจอไหม (ควรมี)
5. ยอมรับให้ล็อกอินค้างไว้ 30 วันได้ไหม หรืออยากให้หลุดทุกวัน/ทุกสัปดาห์

> ระบุตัวตนรายคนเป็นการเปลี่ยนวิธีทำงานของพนักงาน ไม่ใช่แค่เปลี่ยนโค้ด —
> ควรบอกทีมล่วงหน้าว่าทำเพื่อ "รู้ว่าใครทำอะไร เวลาของขาด/นับผิดจะได้ตามได้ถูกจุด"
> ไม่ใช่เพื่อจับผิด
