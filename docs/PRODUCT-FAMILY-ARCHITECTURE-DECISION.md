## 1. Family vs Prefix+Model

### 1.1 `prefix+model` เหมาะเป็น technical grouping ไหม? — **บางส่วน ไม่ใช่ทั้งหมด** ✅

จัดกลุ่มด้วย base_word (คำแรกของชื่อหลังตัดราคาออก) เทียบกับ prefix+model:

| ตัวชี้วัด | ค่า |
|---|---|
| base_word groups ที่มี ≥2 SKU (candidate "business family" จากชื่อ) | **569** |
| — ครอบมากกว่า 1 prefix | **101 (17.8%)** |
| — ครอบมากกว่า 1 category | **124 (21.8%)** |
| — มี variant-rule (สี/ขนาด) ต่างกันข้าม prefix-subgroup ของตัวเอง | **23 (4.0%)** |

✅ **สรุป**: `prefix+model` เป็น technical grouping ที่ใช้ได้ดีสำหรับ **82.2% ของกรณี** (business family
อยู่ใน prefix เดียว) — **แต่ไม่ใช่กฎสากล** 17.8% ของ "แบบสินค้าเดียวกัน" ถูกแยกข้าม prefix จริง

### 1.2 กรณี Hydrangea (ไฮเดรนเยีย) H/HB/ON/V ควรตีความอย่างไร? ✅

```
ไฮเดรนเยีย (129 SKU รวม) → H(119, ดอกไม้) · HB(8, บูช) · ON(1) · V(1)
```

🔍 **INFERENCE**: H กับ HB **ไม่ใช่ความผิดพลาดของข้อมูล** — เป็น**สินค้าคนละชนิดที่ขายจริง**: H = ไฮเดรน
เยียดอกเดี่ยว (หมวดดอกไม้), HB = ไฮเดรนเยียจัดช่อ/บูช (หมวดบูช, "B."=บูช ปรากฏในชื่อ "ไฮเดรนเยียB.")
— **นี่คือ "Product Form" คนละแบบของพืชต้นเดียวกัน ไม่ใช่ variant สี/ขนาดของสินค้าเดียวกัน** พฤติกรรม
ทางธุรกิจ (ราคา, การนับสต็อก, การขาย) ของ H กับ HB น่าจะเป็นอิสระต่อกัน — **ไม่ควรบังคับให้เป็น "1
Family" เดียวกันในระดับ transactional** แต่ควรมี**ความสัมพันธ์แบบ tag/reference** ว่ามาจากพืชชนิดเดียวกัน
(มีประโยชน์สำหรับ reporting/search — "ไฮเดรนเยียขายรวมเท่าไหร่ทุกรูปแบบ" — แต่ไม่จำเป็นสำหรับสต็อก/ราคา)

### 1.3 prefix ที่เปลี่ยนตาม product form ควรอยู่ระดับไหน? 💡

จาก 1.2: `H`/`HB`/`RT` ไม่ใช่ "variant" (สี/ขนาด) ของสินค้าเดียว — เป็น **"Product Type/Form"** คนละ
รายการที่ขายแยกกัน (คนละ SKU-line, คนละ Registry entry) **แต่เชื่อมกันด้วยแนวคิด Business Family ที่
กว้างกว่า** (ระดับ "ชนิดพืช/ดีไซน์" ไม่ใช่ระดับขาย)

### 1.4 family ที่มีหลาย category — ✅ 124 กรณี (21.8% ของ proto-family)

ตัวอย่าง: `กุหลาบ` ครอบ 3 prefix + 3 category (ดอกไม้/บูช/Realtouch — ตรงกับรูปแบบ H/HB/RT) ·
`ซิมบิเดียม` ครอบ 3 prefix + 3 category เช่นกัน — **รูปแบบซ้ำ**: พืชยอดนิยม (กุหลาบ, ไฮเดรนเยีย,
ซิมบิเดียม) มักมี 3 Form คู่ขนาน (ดอกเดี่ยว/บูช/Realtouch) ✅

### 1.5 family ที่ variant-rule ต่างกัน — ✅ พบทั้งข้าม prefix (23) และ**ภายใน prefix เดียวกัน** (ใหม่)

ทดสอบเพิ่มเติม: ภายใน**prefix เดียวกัน** (ไม่ข้าม prefix) แต่ต่าง model — variant-rule (สี vs ขนาด)
สอดคล้องกันไหม?

**4 prefix ที่มี ≥3 model แสดง mixed variant-rule ภายในตัวเอง**: `FRU`, `KB`, `L`, `LO`

⚠️ **การค้นพบใหม่ที่สำคัญที่สุดของรอบนี้ — ทำลายสมมติฐาน "prefix สะอาด = ไว้ใจได้"**: `KB`
(กุหลาบหิน) ที่เอกสารก่อนยกเป็นตัวอย่าง **"สะอาด 100%, category เดียว"** (§4 ของ forensic doc) —
รอบนี้พบว่า **model `096` ภายใน KB คือ "อากาเว่" (Agave, พืชอวบน้ำคนละสกุลกับกุหลาบหิน)** ใช้ variant
= ขนาด **S/M/L** (`KB01096`=S, `KB02096`=M, `KB03096`=L) ในขณะที่ model อื่นในกลุ่ม KB (เช่น `040`=
พิงกุย) ใช้ variant = **สี** ✅

```
KB096: KB03096="อากาเว่ L 980" · KB02096="อากาเว่ M 780" · KB01096="อากาเว่ S 480"   → variant=ขนาด
KB040: KB02040="พิงกุยเขียว 68" · KB01040="พิงกุยแดง 68"                            → variant=สี
```

✅ **สรุปเชิงสถาปัตยกรรม**: `KB` = category สะอาด 100% (กุหลาบหิน) **แต่ไม่ใช่ species-family สะอาด** —
เป็น**หมวดการนำเสนอ** ("พืชแนวหิน/สวนหิน") ที่รวมพืชหลายชนิด · **แม้แต่ prefix ที่ "ดีที่สุด" ในเอกสาร
ก่อนหน้าก็ยังพิสูจน์ว่า variant-rule ต้องผูกกับ model (Form) ไม่ใช่ prefix หรือ category** — นี่คือ
หลักฐานที่แข็งแรงที่สุดสำหรับคำตอบในหัวข้อ 2

### 💡 Hierarchy ที่เสนอจาก evidence (ปรับจาก Option B เดิม)

```
Business Family (ชนิดพืช/ดีไซน์ — เชื่อมโยงแบบ soft-reference, ไม่บังคับ)  [17.8-21.8% ของกรณีต้องใช้]
        │
        ▼
Product Type/Form  ≈ prefix+model วันนี้ (H=ดอกเดี่ยว, HB=บูช, KB096=อากาเว่ในกลุ่มหินประดับ)
        │   [หน่วยที่ transactional จริง: มีราคา/สต็อก/ชื่อของตัวเอง]
        ▼
Variant  (สี หรือ ขนาด หรือ อื่น — RULE เป็นคุณสมบัติของ Form นี้ ไม่ใช่ของ prefix/category)
        │
        ▼
SKU  (= variant instance ที่ซื้อขายได้จริง = 1 barcode)
```

⚠️ **ต่างจาก Option B เดิม (forensic doc) ตรงไหน**: เดิมเสนอ Family = prefix+model ตรง ๆ · **รอบนี้
พบว่า prefix+model ควรเรียกว่า "Product Type/Form" (หน่วย transactional) ไม่ใช่ "Family" สูงสุด** —
Family ที่แท้จริง (ระดับชนิดพืช) เป็น**ชั้นที่กว้างกว่า** และ**ไม่บังคับ** (optional grouping) เพราะ
ครอบแค่ ~18-22% ของกรณี — **ถ้าบังคับให้ทุกอย่างต้องมี Business Family จะสร้างงานเกินความจำเป็นสำหรับ
78%+ ของ catalog ที่ Form เดียวก็พอ**

## 2. Variant Ownership

**คำถาม**: variant rule ควรผูกกับ (A) Category (B) Prefix (C) Product Type/Form (D) Family (E) Variant
definition เอง?

### หลักฐานจากทุกรอบ (สะสม):

| สมมติฐาน | ทดสอบ | ผล |
|---|---|---|
| **A. Category** | 94-95% ตรงในดอกไม้/Realtouch/บูช/ไม้แซม vs 0.6-7% ในใบ/ใบบูช | ✅ ใช้เป็น **default ที่ดี** (~94%) แต่ **ไม่ authoritative** |
| **B. Prefix** | `BE005`(สี) vs `BE020`(ขนาด) — ต่างกันแม้ prefix เดียวกัน | ❌ **ตกรอบ** — prefix เดียวมีได้ทั้ง 2 กฎ |
| **C. Category** ซ้ำกับ A | — | (รวมกับ A) |
| **D. Family/Form** | `KB040`(สี) vs `KB096`(ขนาด) — **ต่างกันแม้ prefix+category เดียวกัน** | ✅ **สอดคล้องหลักฐานมากที่สุด** — ผูกที่ระดับ model/Form จึงแม่นทุกกรณีที่ตรวจสอบ |
| **E. Variant definition เอง** (เช่น code "01" ต้องแปลว่า "แดง" เสมอ) | ยืนยัน 80.8% เมื่ออยู่ใน "โหมดสี" | ✅ ใช้ได้ **เฉพาะเมื่อรู้แล้วว่าอยู่โหมดสี** — ไม่ใช่ตัวบอกโหมดเอง |

### ✅ คำตอบ: **กฎของ Variant อยู่ที่ระดับ D (Product Type/Form)** — ไม่ใช่ Category และไม่ใช่ Prefix

- **Category** ใช้เป็น **default suggestion** ได้ (~94% แม่นในหมวดดอกไม้กลุ่มใหญ่) — ประหยัดแรงตอน
  backfill/สร้างใหม่
- **แต่ต้อง override ได้ที่ระดับ Form** เพราะพิสูจน์แล้วว่ามี exception จริงแม้ใน prefix ที่ "สะอาดที่สุด"
  (`KB`) — ถ้า hardcode กฎที่ category จะทำนายผิดสำหรับ KB096 (และ FRU/L/LO ที่พบ mixed เช่นกัน)
- **Variant code meaning เอง (E)** เชื่อถือได้ **ภายใต้เงื่อนไขว่ารู้โหมดแล้ว** — ไม่ใช่ตัวชี้ขาดโหมด

💡 **RECOMMENDATION**: เก็บ `variantRule` เป็น field บน **Product Type/Form record** (1 ต่อ Form)
พร้อม default ที่ derive จาก category (ประหยัดงานกรอกสำหรับ 94% ที่ตรงกฎ) แต่ยอมให้แก้รายตัวสำหรับ
Form ที่ผิดกฎ (เช่น KB096)

## 3. Legacy Prefix — `L` และ prefix หลาย category

### 3.1 `L` ไม่ใช่แค่ "prefix กระจัดกระจาย" — เป็น **namespace ที่ชนกันจริง** ✅ (พบใหม่)

| ตัวชี้วัด | ค่า |
|---|---|
| `L` ทั้งหมด | 373 SKU, 270 model number ต่างกัน, 8 category |
| model ที่มี >1 SKU (มี "family" ภายใน L เอง) | 63 models (166 SKU) |
| model ที่มี 1 SKU (singleton) | 207 models |
| **model ที่ชื่อพืชต่างชนิดกันโดยสิ้นเชิงใช้เลขเดียวกัน** | **25 / 270 (9.3%)** |

ตัวอย่างชนกันจริง: **model `002`** = `L09002`"ลิลลี่ช่อ ส้ม" + `L02002`"**กระถินไทย**" (คนละพืชกันโดย
สิ้นเชิง — ลิลลี่=ไม้ดอก, กระถินไทย=พืชตระกูลถั่ว) ใช้เลข model เดียวกัน ✅

🔍 **INFERENCE**: `L` ทำหน้าที่เป็น **"ถังรวมชั่วคราว" (catch-all bucket)** สำหรับพืช/ใบไม้ที่ยังไม่มี
prefix เฉพาะของตัวเอง (หรือมีน้อยเกินกว่าจะแยก prefix) — เมื่อเวลาผ่านไป จำนวนชนิดใน `L` มากขึ้นจนเลข
running (จำกัดที่ 3 หลัก = 999) เริ่มถูกใช้ซ้ำข้ามชนิดพืชที่ไม่เกี่ยวข้องกัน — **นี่คือสัญญาณของ
"prefix ที่ใช้เกินขีดความสามารถของ business rule เดิม"**

### 3.2 หลักการ represent legacy SKU โดยไม่ rewrite (ตามที่สั่ง) 💡

**ห้ามเปลี่ยน SKU เดิม** — ทุก legacy SKU (รวม `L`) ยังคงเป็น string เดิม 100% ตลอดไป · สิ่งที่เพิ่มคือ
**mapping metadata แยกต่างหาก** ไม่ใช่การแก้ SKU:

```
Legacy Prefix (เช่น "L")
    │
    ├─ ไม่มีความหมายเดียวที่ชัดเจนระดับ prefix (พิสูจน์แล้ว §3.1) → ไม่สร้าง "L = Product Type" ตรงๆ
    │
    ▼
existing SKU (เช่น L00261, L09002, L02002 — คงเดิมทุกตัวอักษร)
    │
    ▼
mapped Product Type/Form metadata (เพิ่มใหม่ ต่อ SKU หรือต่อ family-key ที่ไม่ชนกัน)
    → L00261 → Form "หญ้า" (แม้ prefix จะเป็น L ก็ตาม)
    → L09002 → Form "ลิลลี่ช่อ" (model 002 ของ "กลุ่ม 1")
    → L02002 → Form "กระถินไทย" (model 002 ของ "กลุ่ม 2" — คนละ Form แม้เลข model ชนกัน)
```

💡 **หลักการสำคัญ**: เมื่อ `prefix+model` ชนกันข้ามชนิดสินค้า (เช่น L+002) **ต้องใช้ SKU เต็มตัว (ไม่ใช่
prefix+model) เป็น key ในการ map ไปหา Form ที่ถูกต้อง** — คือ **1 SKU → 1 Form เสมอ** (แม่นยำ 100%
เพราะ SKU ไม่ซ้ำ) ในขณะที่ **`prefix+model` → Form เป็นได้แค่ "ตัวช่วยจัดกลุ่มเบื้องต้น" ที่ต้องตรวจสอบ
ด้วยชื่อสินค้าประกอบเสมอสำหรับ prefix ที่มีประวัติชนกัน** (เช่น `L`, และควรเฝ้าระวัง `FRU`/`LO`/`KB`
ด้วยจากหลักฐาน §1.5)

### 3.3 prefix ที่มีหลาย category (จากรอบก่อน 54%) — ใช้หลักการเดียวกัน

ไม่ต้องแยกกรณีพิเศษ — ทุก prefix (ไม่ว่าจะสะอาดแค่ไหน) ควร map ผ่าน **SKU เต็มตัว → Form** เป็นค่า
เริ่มต้นของสถาปัตยกรรมใหม่ (ไม่ใช่แค่กรณี legacy ที่มีปัญหา) — เพราะ §1.5 พิสูจน์แล้วว่า "ดูสะอาด" ไม่ใช่
เครื่องยืนยันว่า "ปลอดภัยที่จะ derive จาก prefix อย่างเดียว"

| แหล่ง | สิ่งที่พบ | สรุป |
|---|---|---|
| **CSV filename** | `4a36c6c5-__________________________________.csv` — ส่วนชื่อไฟล์เดิมถูก**แทนที่ด้วยขีดล่างทั้งหมด**โดยระบบอัปโหลด (privacy masking) มีแค่ hash prefix `4a36c6c5-` ที่ไม่มีความหมายเชิงข้อมูล | ❓ **UNKNOWN — ไม่มีข้อมูลเหลือให้อ่านเลย** |

## 6. Critical Domain Model (แนวคิด — ไม่สร้าง schema)

```
BusinessFamily (optional, soft-reference)
  = ชนิดพืช/ดีไซน์ในความหมายกว้าง เช่น "ไฮเดรนเยีย", "กุหลาบ"
  ครอบคลุมได้หลาย ProductType/Form (H+HB+RT ของไฮเดรนเยีย)
  ไม่บังคับมี — ใช้เมื่อธุรกิจต้องการรายงาน/ค้นหาข้ามรูปแบบ

        │ 1-to-many (optional)
        ▼

ProductType/Form   ← หน่วยงานหลักที่ระบบควรจัดการจริง (≈ prefix+model วันนี้ แต่ผูกด้วย SKU ไม่ใช่แค่รหัส)
  = "แบบสินค้าที่ขายจริง" 1 รายการ เช่น "ไฮเดรนเยียดอกเดี่ยว รุ่น 041"
  มี: ชื่อฐาน, category, variantRule (สี/ขนาด/อื่น — property ของ Form นี้เอง)
  เชื่อมกับ BusinessFamily แบบ optional

        │ 1-to-many
        ▼

VariantDefinition   ← ค่าที่เลือกได้ภายใต้ variantRule ของ Form นั้น (สีจากตาราง 99 รหัส หรือ ขนาด S/M/L)

        │ 1-to-1 (แต่ละ variant selection ที่ถูกสร้างจริง = 1 แถวนี้)
        ▼

Product   ← ⚠️ ดูหัวข้อถัดไปว่า entity นี้ "มีจริง" แค่ในทางทฤษฎีหรือไม่

        │
        ▼

SKU  (= identity ที่ใช้จริงในระบบทั้งหมดวันนี้ = barcode 99.68% ของกรณี)
```

### ❓→✅ ตอบคำถามสำคัญที่สุด: **"SKU เป็น Product entity หรือเป็น identifier ของ Product Variant?"**

**SKU = identifier ของ Product Variant (ไม่ใช่ Product entity)** ✅ — หลักฐาน:

1. **SKU ไม่มี "ตัวตน" อิสระเหนือ variant** — ทุกอย่างที่ SKU มี (ชื่อ, ราคา, สต็อก) คือคุณสมบัติของ
   variant instance หนึ่งตัว (สี/ขนาดหนึ่งแบบของ Form หนึ่งอัน) ไม่ใช่คุณสมบัติของ "สินค้า" ในความหมาย
   กว้าง
2. **"Product" (ในความหมาย Form) ไม่มี record ของตัวเองเลยวันนี้** — ต้อง derive จากการ scan SKU ทุกครั้ง
   (`designInfo`/`designMatches` ใน AddProductView) — ยืนยันว่าสิ่งที่ *ควรจะเป็น* Product entity
   **ไม่มีอยู่จริงเป็นข้อมูล** มีแต่ SKU ที่เป็น leaf-level identifier
3. Barcode ≈ SKU (99.68%) ตอกย้ำว่า SKU ถูกออกแบบมาให้เป็น**หน่วยที่ซื้อขาย/สแกนได้จริง** (=variant ที่
   เจาะจงที่สุด) ไม่ใช่หน่วยที่เป็นนามธรรมกว่านั้น (Product/Family)

💡 **ผลต่อสถาปัตยกรรม**: Registry ในอนาคตต้องมี entity ระดับ **ProductType/Form** แยกจาก SKU อย่างชัดเจน
— SKU ยังคงทำหน้าที่เป็น "primary key ของ variant ที่ขายได้จริง" เหมือนเดิม เพียงแต่ไม่ควรเป็นที่เก็บ
ความหมายทางธุรกิจ (ชนิด/รูปแบบ) อีกต่อไป — ความหมายนั้นควรย้ายไปอยู่ที่ ProductType/Form record

## Architecture Decision Recommendation

### ✅ Recommended model

**Option B (ปรับปรุงแล้ว)**: แยก entity **ProductType/Form** ออกจาก SKU อย่างชัดเจน — Form เป็นหน่วย
transactional หลัก (แทนที่ "Family" ในความหมายเดิม), **Business Family เป็นชั้น optional** ที่เชื่อม
Form หลายอันเข้าด้วยกันแบบ soft-reference (ไม่บังคับ ใช้เมื่อจำเป็นสำหรับ reporting) · SKU ยังเป็น
identifier ระดับ variant เหมือนเดิม 100% ไม่เปลี่ยน

### เหตุผล (สรุปจาก evidence รวมทุกรอบ)

1. Form-level (prefix+model) ใช้ได้จริง 82% ของกรณี — ไม่ต้องรื้อทุกอย่าง
2. Business Family (กว้างกว่า) จำเป็นแค่ 18-22% — **ทำให้เป็น optional ไม่บังคับ** ประหยัดงานสำหรับ
   ส่วนใหญ่
3. Variant-rule พิสูจน์แล้วว่าต้องผูกที่ Form (ไม่ใช่ category/prefix) — แม้ prefix ที่สะอาดที่สุด (`KB`)
   ก็ยังมี exception (§1.5) — นี่คือหลักฐานใหม่ที่**ยืนยัน** ไม่ใช่แค่สนับสนุน Option B
4. SKU = variant identifier ไม่ใช่ Product entity (§6) — สอดคล้องกับทุกเอกสารก่อนหน้า

### ❌ สิ่งที่ไม่ควรทำ

- ❌ **อย่าบังคับว่า "1 Business Family = 1 กลุ่ม" ที่ทุกสินค้าต้องเข้า** — 78-82% ไม่ต้องการชั้นนี้
- ❌ **อย่าใช้ prefix+model เป็น mapping key เพียงอย่างเดียวตอน backfill** — พิสูจน์แล้วว่าชนกันได้
  (`L`, และเฝ้าระวัง `KB`/`FRU`/`LO`) → **ต้องใช้ SKU เต็มตัวเสมอ**
- ❌ **อย่า derive variantRule จาก category แล้วถือเป็นค่าสุดท้าย** — ต้องเปิดให้ override ต่อ Form
- ❌ **อย่าเปลี่ยน/rewrite SKU เดิมไม่ว่ากรณีใด** — ตามที่สั่งและตามข้อจำกัดจริง (บาร์โค้ดพิมพ์ติดของแล้ว)
- ❌ **อย่าสรุปว่าข้อมูลนี้เป็น production 100%** จนกว่าเจ้าของยืนยัน (§4 ยังเป็น UNKNOWN)

### 📋 สิ่งที่ต้องตัดสินใจก่อน implementation (business decisions ล้วน — ไม่ใช่ของสถาปนิก)

1. **Business Family boundary**: H+HB+RT ของไฮเดรนเยีย ควรนับเป็น "ครอบครัวเดียวกัน" สำหรับรายงานไหม?
   หรือแต่ละ Form อิสระจากกันโดยสิ้นเชิงในมุมธุรกิจ?
2. **`L` และ prefix ถังรวมอื่น**: ต้องการแยก `L` ออกเป็น Form ย่อยตามชนิดพืชจริง (270 Forms) หรือปล่อยไว้
   เป็น "หมวดรวมของเก่า" แล้วเริ่มมีวินัย prefix ใหม่เฉพาะสินค้าที่สร้างต่อจากนี้?
3. **KB-style exception**: prefix ที่ดูสะอาดแต่มี exception ซ่อนอยู่ (เช่น KB096) — ต้องตรวจสอบทุก
   prefix ที่เหลือ (112 ตัว) แบบเดียวกันก่อน หรือแก้เฉพาะที่เจอปัญหาจริงทีหลัง?
4. **Production data provenance** (§4): ข้อมูลชุดนี้เป็น production จริง 100% ไหม? — คำตอบนี้กำหนดว่า
   ตัวเลขทั้งหมดในเอกสารชุดนี้ (5 ฉบับ) ใช้วางแผน migration ได้ทันทีหรือต้องขอ export ใหม่ก่อน

### ❓ Evidence ที่ยังขาด

- **Provenance ที่ยืนยันได้** (§4) — เป็น UNKNOWN ที่กระทบทุกตัวเลขในเอกสารชุดนี้
- **ตรวจสอบ prefix ที่เหลือทั้งหมด** (มีแค่ 10 ตัวใน watch list ที่ตรวจละเอียด จาก 112 ตัว) — ไม่รู้ว่ามี
  KB096-style exception ซ่อนอยู่อีกกี่ตัว
- **ความถี่ที่พนักงานพึ่งพาการอ่าน SKU จริงในงานประจำวัน** (ไม่มีในข้อมูล ต้องถามตรง ๆ) — กระทบน้ำหนัก
  ระหว่าง B กับ C
