## 2. Product Name Structure

### 2.1 Grammar ของชื่อสินค้า — **มี convention จริง ชัดเจน** ✅

รูปแบบที่พบ: **`[ชื่อฐาน/ชนิด] [สี หรือ ขนาด (ถ้ามี)] [ราคาส่ง]`**

| องค์ประกอบ | หลักฐาน |
|---|---|
| **ราคาส่งท้ายชื่อ** | 93.2% ของชื่อ (4,818/5,171 standard) ลงท้ายด้วยตัวเลขราคา ✅ · อัตราส่วนราคา/col_C = 0.80 (=1/1.25) ใน 87% (จาก evidence doc) → ยืนยันว่าเลขนี้คือราคาส่งจริง |
| **ชื่อฐาน (token แรก)** | 1,040 ชื่อฐานที่ต่างกัน — เป็น "ชื่อชนิดสินค้า" (กุหลาบ, ไฮเดรนเยีย, ทิวลิป, แจกันแก้ว) ✅ |
| **สี** | อยู่กลางชื่อ (ตรงกับ variant code 94% ในหมวดดอกไม้ — ดู §5) |
| **ขนาด** | S/L/M เป็นคำแยกในชื่อ (2.6% ของ standard, กระจุกในหมวดใบ — ดู §5) |

top ชื่อฐาน: แจกันแก้ว(251) · กุหลาบB.(195) · กุหลาบRT(139) · ไฮเดรนเยีย(129) · แมคโนเลีย(103) ·
เฟิร์น(96) · ทิวลิป(84) · โบตั๋น(83) · กุหลาบ(79) · ยูคาลิปตัส(72)

### 2.2 คำตอบ: **ใช่ — ชื่อสินค้ามี convention จริง** ✅

ต่างจากที่เอกสารเดิม (`PRODUCT-NAMING-AND-SKU-ARCHITECTURE.md`) สรุปว่าชื่อเป็น "free text ล้วน" — **ข้อมูล
จริงแสดง grammar 3 ส่วนที่สม่ำเสมอ 93%** · แต่ **grammar นี้บังคับด้วยวินัยคน ไม่ใช่ระบบ** (ฟอร์มสร้าง
สินค้า `composedName` ประกอบ [ชื่อ][สี][ราคา] ให้จริง — แต่ชื่อฐานยังพิมพ์อิสระ + สินค้าที่แก้ที่ ZORT
หลุด convention ได้) → **มี convention แต่ไม่มี enforcement**

🔍 **INFERENCE**: ชื่อสินค้าปัจจุบัน**เข้ารหัสข้อมูลที่ควรเป็น structured field ไว้ในข้อความ**: ชนิด(base) +
สี/ขนาด(variant) + ราคา(price) — ข้อมูลทั้ง 3 ส่วนมีอยู่แล้วใน field อื่นด้วย (variant ใน SKU, ราคาใน
col_C) = **duplication ที่ derive ออกจากกันได้**

| Grammar | จำนวน | % | ตัวอย่าง | ตีความ |
|---|---|---|---|---|
| **A. Standard** `[A-Z]{1,3}[VV][NNN]` | 5,171 | **90.0%** | ORL00010, L00261, RT29001 | สินค้าดอกไม้/ใบ มาตรฐานบริษัท |
| **D. Suffix-letter** `[pfx][digits][S/L/M/A/B/C]` | 363 | 6.3% | G00391S, G00391L, R00012A, G00061M-1 | variant/ขนาด เข้ารหัสด้วยตัวอักษรท้าย |
| **B. Letters+digits (อื่น)** | 118 | 2.1% | P0001, BO0008, GMD000013 | รูปแบบเก่า/นำเข้า (digit ไม่ตรง 2+3) |
| **E. Full-word prefix** | 65 | 1.1% | VASE001, PACKAGE001, OASIS02, TAPE001 | อุปกรณ์/บริการ/แจกัน (prefix เป็นคำเต็ม) |
| **F. Other (มีอักขระผสม)** | 16 | 0.3% | 3D00009, 3D02008 | รูปแบบพิเศษ (เช่นตระกูล 3D) |
| **C. Numeric-only** | 14 | 0.2% | 3141748, 2815324 | รหัส ZORT auto / นำเข้า ไม่มี prefix |

✅ **มี 6 grammar คู่ขนานจริง** — มากกว่าที่เอกสารเดิมระบุ (เดิมรู้ 2-3) · grammar A ครอบงำ 90% แต่
**grammar D (suffix-letter, 6.3%) เป็นรูปแบบใหญ่อันดับ 2 ที่ไม่มีเครื่องมือไหนใน codebase parse ได้**
(`parseSkuParts` คืน null, `mtoSkuPrefix_` ตัด suffix ทิ้ง) → 363 สินค้าตกหล่นจากทุก analysis ที่พึ่ง SKU

### 3.1 Suffix-letter grammar (D) เข้ารหัสอะไร? 🔍

ตัวอย่าง `G00391S`/`G00391L`, `G00340L`/`G00340S` — S/L = ขนาด (Small/Large) ผูกกับ SKU ฐานเดียวกัน ·
`R00012A`, `C00025B`/`C00025C` — A/B/C น่าจะเป็น sub-variant · `G00061M-1` มี `-1` ต่อท้ายอีก
→ **grammar D คือ "ขนาด/sub-variant แบบที่ 2" ที่แข่งกับ variant-digit ของ grammar A** โดยไม่มี field
บอกว่าสินค้าไหนใช้แบบไหน (ดู §5.3)

### 4.1 ข้อสรุปจาก prefix forensics ✅

1. **prefix มี "วินัย" ไม่เท่ากันชัดเจน** — บางตัวสะอาด 100% single-category (HL, DEC, OR, OL) บางตัว
   กระจัดกระจาย (L=8 หมวด) บางตัวปนเปื้อนคนละชนิด (AT)
2. **prefix ที่คล้ายกัน = ความหมายต่างกันจริง** (ยืนยันจาก §PRODUCT-DATA-EVIDENCE): `OL`(มะกอก/ใบ) ·
   `OR`(กล้วยไม้ดอก) · `ORL`(ใบกล้วยไม้) — 3 กลุ่มคนละเรื่อง ตัวอักษรต่างกันแค่ 1 ตัว
3. **prefix ไม่ได้ map 1:1 กับ category** (§PRODUCT-DATA §2.6: 54% ของ prefix ครอบ >1 หมวด) — **แต่
   ก็ไม่ได้ map กับ "ชนิดพืช" 1:1 เช่นกัน** (L เป็น prefix รวม) → prefix ปัจจุบันเป็น **mix ของ 3 ตรรกะ**:
   บางตัว=ชนิดพืช (PH, SN), บางตัว=หมวดการใช้งาน (HL=แขวน, DEC=ตกแต่ง, V=แจกัน), บางตัว=ถังรวม (L)

### 5.2 code เดียวกันความหมายหลายแบบ — ✅ ยืนยัน

`variant '01'`: n=460 · 188 มีชื่อสีตรง ("แดง") · 53 มี size-marker → **01 เป็นได้ทั้งสี"แดง"และขนาด"S"**
`variant '02'`: n=282 · 8 มีชื่อสีตรง · 55 มี size-marker → **02 ส่วนใหญ่เป็นขนาด"L" ไม่ใช่สี"แดงอมม่วง"**

→ code เดียว (01, 02) มีความหมายต่างกันตาม context จริง ✅

### 5.3 variant ไม่คงที่แม้ภายใน prefix เดียวกัน ✅ — ระดับความไม่สอดคล้องที่ลึกที่สุด

prefix `BE` (เบอรี่):
- `BE005` variants = 09,01,31,20 = **สี** (ส้ม,แดง,เขียว,น้ำเงิน)
- `BE020` variants = 01(เล็ก),02(ใหญ่) = **ขนาด**

→ **ภายใน prefix เดียวกัน model ต่างกันใช้ variant คนละความหมาย** — category-level rule (§5.1) ยังไม่
ครอบทุกเคส · ความหมาย variant สุดท้ายผูกกับ **family (prefix+model) แต่ละอัน** ไม่ใช่แค่ category

### 5.4 digit-variant กับ suffix-letter เป็น business rule เดียวกันไหม? 🔍

**ไม่ใช่** — เป็นคนละกลไก: grammar A ใช้ digit ในตำแหน่งกลาง (RT**29**001), grammar D ใช้ตัวอักษรท้าย
(G00391**S**) · ทั้งคู่เข้ารหัส "ขนาด/variant" แต่**คนละไวยากรณ์ ไม่มี field บอกว่าสินค้าใช้แบบไหน** →
เครื่องมือที่ parse แบบ A จะพลาดแบบ D ทั้งหมด (363 SKU)

## 6. Barcode ✅

| ตัวชี้วัด | ค่า |
|---|---|
| แถวที่มีทั้ง sku+barcode | 5,352 |
| **barcode = sku** | 5,335 (**99.68%**) |
| **barcode ≠ sku** | **17 (0.32%)** |
| มี sku แต่ barcode ว่าง | 395 |

**barcode ≠ sku ทั้ง 17 แถว**:
- **15 แถว = prefix `V` (แจกันชุด)** — barcode เป็น**เลข 8 หลักจริง** (14452925, 14452918, ...) 🔍 น่าจะ
  เป็นบาร์โค้ดสินค้าสำเร็จรูป/แจกันที่ซื้อมามี barcode โรงงานติดมา ต่างจากดอกไม้ที่ทำ SKU เอง
- **1 แถว OC38018 → barcode OC38019** — 🔍 น่าจะพิมพ์ผิด off-by-one
- **1 แถว ORL00001 → barcode OL00001** — ⚠️ **prefix สับสน ORL vs OL** (สอดคล้องกับ §4 ว่า 2 prefix นี้
  สับสนกันได้จริง) — sku ว่า "ใบกล้วยไม้" (ORL=ใบ) แต่ barcode ใช้ OL (มะกอก)

✅ **สรุป: Barcode = SKU เกือบทั้งหมด (99.68%) — แต่ "ไม่ใช่ derived field เสมอ"** · สินค้ากลุ่มแจกัน
สำเร็จรูป (V) มี barcode อิสระจริง → **domain model ต้องรองรับ barcode เป็น field แยกได้ ไม่ hardcode =SKU**

## 8. Architecture Implication — เปรียบเทียบ 3 แนวทาง

> 💡 ทั้งหมดเป็น RECOMMENDATION — ยังไม่เลือก final

### Option A — Preserve human-readable SKU + improve metadata

| มิติ | ผล |
|---|---|
| ข้อดี | SKU เดิม/ป้ายบาร์โค้ดจริงใช้ได้ต่อ 100% · พนักงานอ่าน SKU ได้เหมือนเดิม · migration แทบเป็นศูนย์ |
| ข้อเสีย | ไม่แก้ปัญหาแกน — variant ยังกำกวม (§5.3), family ยังแตกข้าม prefix (§1.3), grammar D ยัง parse ไม่ได้ |
| Migration | 🟢 ต่ำสุด |
| Compat SKU/barcode ติดของ | ✅ สมบูรณ์ |
| Compat ZORT | ✅ ไม่แตะ |
| Compat Add Product | ✅ เพิ่ม registry ข้าง ๆ |
| พนักงาน warehouse | ✅ ไม่เปลี่ยน |
| เสี่ยงระยะยาว | 🔴 หนี้เชิงโครงสร้างสะสมต่อ — ทุกปัญหาใน §1-5 ยังอยู่ |

### Option B — Product Family เป็น entity + SKU เป็น variant identifier 💡 **แนะนำ**

| มิติ | ผล |
|---|---|
| ข้อดี | ตรงกับโครงสร้างจริงที่ข้อมูลบอก (63% เป็น multi-variant family, §1.1) · แก้ family-แตกข้าม-prefix ได้ (map หลาย SKU → 1 Family) · เก็บ variant-meaning ที่ family level (แก้ §5.3) · derive variant→สี ได้ 94% จาก category · SKU/barcode/ชื่อ เดิมไม่แตะ |
| ข้อเสีย | ต้อง backfill Family record + ตัดสินใจ variant-rule ต่อ family สำหรับเคสกำกวม (~ใบ/กุหลาบหิน) |
| Migration | 🟡 กลาง — backfill อัตโนมัติได้ 94% (prefix+model+category+color-match) เหลือ ~6% ต้องคนตรวจ |
| Compat SKU/barcode ติดของ | ✅ SKU เดิมคง — Family เป็น layer ใหม่ข้างบน |
| Compat ZORT | ✅ Family อยู่ฝั่ง ERP, ZORT เห็นแค่ SKU เดิม |
| Compat Add Product | ✅ ตรงกับ target flow ("สีใหม่ของแบบเดิม" = เลือก Family) |
| พนักงาน warehouse | ✅ SKU อ่านได้เหมือนเดิม + ได้มุมมอง "แบบ" เพิ่ม |
| เสี่ยงระยะยาว | 🟢 ต่ำ — เปิดทางไป C ได้ถ้าจำเป็น |

### Option C — Full Product Type/Family/Variant Registry

| มิติ | ผล |
|---|---|
| ข้อดี | ยืดหยุ่นสุด · reclassify ได้โดยไม่แตะ SKU · แก้ทุกปัญหาใน §1-7 |
| ข้อเสีย | SKU กลายเป็นรหัสไร้ความหมาย — พนักงานเสียความสามารถอ่าน SKU · งานเปลี่ยน UI/data มากสุด · เสี่ยงตอน rollout สูงสุด |
| Migration | 🔴 สูงสุด (แต่ไม่ต้อง regen SKU เดิม — grandfather เข้ามา) |
| Compat SKU/barcode ติดของ | ✅ ถ้าออกแบบให้ SKU เดิม valid ตลอด |
| Compat ZORT | ✅ |
| Compat Add Product | ต้องรื้อ UI เป็นฟอร์ม structured เต็ม |
| พนักงาน warehouse | ⚠️ ต้อง retrain — SKU อ่านไม่ออกอีกต่อไป |
| เสี่ยงระยะยาว | 🟢 ต่ำ (ถ้าผ่าน migration) แต่ต้นทุนเปลี่ยนสูง |

### 💡 RECOMMENDATION: **Option B**

**เหตุผลจาก evidence**:
1. ข้อมูลจริงบอกว่าธุรกิจนี้เป็น **"multi-variant family" โดยธรรมชาติ** (63%, §1.1) — Family เป็น entity
   ที่ขาดหายไปพอดี ไม่ใช่ของแปลกปลอม
2. **variant-meaning derive ได้ 94% จาก category** (§5.1) — backfill B ทำได้อัตโนมัติเกือบทั้งหมด
3. รักษาสิ่งที่พนักงานพึ่งพา (อ่าน SKU ออก) ซึ่งสำคัญกับผู้ใช้หลัก (แรงงานที่ไม่ถนัดเทคโนโลยี ตาม CLAUDE.md)
4. **A ไม่พอ** (ไม่แก้แกน), **C แพงเกินและเสี่ยงกับพนักงาน** — B คือจุดสมดุลที่ evidence สนับสนุน
5. B เป็นก้าวที่ไม่เสียของถ้าจะไป C ทีหลัง

⚠️ B ยังต้องแก้ 2 เรื่องที่ evidence ชี้ว่า category-rule ไม่พอ: **variant-rule ต้องเก็บที่ family level**
(เพราะ §5.3 BE005≠BE020) และ **ต้องมีนโยบายจัดการ grammar D (suffix-letter)** ที่ family model ไม่ครอบ
