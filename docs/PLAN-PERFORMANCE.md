# ส่วนที่ 1 — ผลตรวจโค้ด (ของที่เจอจริง)

## ✅ ของที่ทำไว้ดีแล้ว — ไม่ต้องแตะ

ก่อนจะบอกว่าอะไรพัง ต้องบอกก่อนว่ารอบก่อน ๆ ทำมาดีมาก:

- **payload แยกตาม role** (`PAYLOAD_VARIANT_DROPS_`) — ตัดก้อนที่ role นั้นไม่มีแท็บดูออกแล้ว
- **ยอดรายเดือนแบบย่อ** (`p.mo`) — กัน payload โตเองทุกเดือน + มี `pv=2` กันเครื่องค้างโค้ดเก่า
- **`batchReadFormatted_`** — อ่าน 9 ชีตในคำสั่งเดียว (เดิมกิน ~96% ของเวลา build)
- **compiled-code cache ผูก ETag** (`dmj-babel-v2`) — ไม่ compile ซ้ำถ้าไฟล์ไม่เปลี่ยน
- **prefetch ข้อมูล + JSX พร้อมกันตั้งแต่ `<head>`** — เวลา GAS เดินขนานกับการ compile
- **Recharts / qrcode / html5-qrcode / html2canvas เป็น `defer`** — ไม่ block first paint
- **แต่ละ view เรนเดอร์เฉพาะแท็บที่เปิด** (`activeTab === "x" && <View/>`) + `uM`/`uC` 189 จุด + pagination 20 แถว/หน้า
  → **runtime ต่อหน้าไม่ใช่ปัญหา** ปัญหาอยู่ที่ "เวลาก่อนแอปขึ้น" ล้วน ๆ

ข้อสรุปสำคัญ: **ความช้าที่พนักงานเจอ ไม่ได้อยู่ที่การเรนเดอร์ แต่อยู่ที่ boot + การรอข้อมูล**
คนที่เคยเสนอให้ไป virtualize list หรือ memo ทุก component — ยังไม่ต้องทำ ผลตอบแทนต่ำกว่า 4 ข้อข้างล่างมาก

## 🔴 P0 — `fresh=1` ฆ่า server cache ทิ้งทั้งหมด (หนักสุด)

**นี่คือข้อที่ตอบคำถาม "ทำไมกดเลือกตำแหน่งแล้วรอนานทุกครั้ง" ตรงที่สุด**

ฝั่ง GAS มี cache 3 นาที เขียนไว้ดีมาก:

```js
// appsscript_complete.gs:2139
const wantFresh = e && e.parameter && e.parameter.fresh === '1';
if (!wantFresh) {
  const cached = getCachedPayload_(cacheVariant);
  if (cached) { ...return cached }   // ← ทางลัด เร็วมาก
}
const data = buildFullData_();       // ← แพงสุด อ่านชีต 12 แผ่น
```

แต่ฝั่งเว็บส่ง `fresh=1` มา **ทั้งสองทาง**:

```js
// app.jsx:900  (fetchFromSheet)
'_t=' + Date.now() + '&fresh=1' + '&pv=2&role=' + ...
// Doomuenjing Dashboard.html:1264  (prefetch ใน <head>)
'_t=' + Date.now() + '&fresh=1' + '&pv=2&role=' + ...
```

**ผลคือ cache ไม่เคยถูกอ่านเลยแม้แต่ครั้งเดียว** ทุกครั้งที่:
- เปิดแอป (prefetch 1 ครั้ง + `fetchFromSheet` อีก 1 ครั้งถ้า role ไม่ตรง)
- อยู่หน้านับสต๊อก/เช็คหน้าร้าน → poll ทุก 30 วินาที
- เน็ตหลุดแล้วกลับมา (`goOnline` → `fetchFromSheet`)
- retry ตอนเน็ตช้า (3 ครั้ง)

→ `buildFullData_()` รันเต็ม ๆ ทุกรอบ อ่าน `batchGet` 9 ชีต + `readPurchases_` + `readMtoJobs_` +
`readQtyByLocation_` แยกอีก 3 รอบ **ต่อพนักงาน 1 คน ต่อการเปิดแอป 1 ครั้ง**

พนักงาน 5 คนเปิดแอปพร้อมกันตอนเข้ากะ = build เต็ม 5–10 รอบซ้อนกัน ทั้งที่ควรเป็นรอบเดียวแล้วที่เหลืออ่าน cache

### แก้ยังไง

**ลบ `&fresh=1` ออกจากทั้ง 2 จุด** เท่านั้น ไม่ต้องแตะฝั่ง GAS

**ปลอดภัยไหม — ตรวจแล้ว ปลอดภัย:**
- ทุก write function เรียก `invalidateCache_()` ใน `finally` อยู่แล้ว (ตรวจแล้ว 28 จุด)
- `doPost` เรียก `invalidateCache_(true)` ที่ต้นทาง
- `syncZortBoth` (บรรทัด 6047) เรียก `invalidateCache_()` ที่ 6127 ✅
- `syncZortToColumn_` (5217) เรียก `invalidateCache_()` ที่ 5310 ✅

→ **ทุกเส้นทางที่เขียนข้อมูล ล้าง cache ให้เองอยู่แล้ว** `fresh=1` เป็นเข็มขัดนิรภัยซ้ำซ้อน
ที่ทุกคนต้องจ่ายค่าโดยสารเต็มราคาทุกเที่ยว

**ช่องที่ข้อมูลจะเก่าได้ ≤ 3 นาที** เหลือกรณีเดียว: มีคนไปแก้ Google Sheet ด้วยมือโดยตรง
(ไม่ผ่านแอป) — ซึ่งไม่ใช่ flow ปกติ และแอปมีปุ่ม refresh อยู่แล้ว

**ถ้าอยากเก็บทางหนีไว้**: ให้เหลือ `fresh=1` เฉพาะตอนผู้ใช้กดปุ่ม refresh เอง กับตอน
`onAdded` หลังเพิ่มสินค้าใหม่ ส่วนการโหลดปกติ/poll ไม่ต้องส่ง

**ประเมินผล**: ตัดเวลารอตอนเข้าแอปลงเหลือเท่ากับเวลา network ล้วน ๆ ในกรณี cache hit
(cache hit = string replace 1 ครั้งแล้ว return — เร็วกว่า build เต็มหลายเท่า)
ตัวเลขจริงดูได้ที่ Executions log — `buildFullData_` มี `_mark()` จับเวลาแต่ละขั้นไว้แล้ว

## 🔴 P1 — โหลด Babel 2.9 MB ทุกครั้ง ทั้งที่โหลดอุ่นไม่ได้ใช้

`Doomuenjing Dashboard.html:1316`:

```html
<script src="https://unpkg.com/@babel/standalone@7.29.0/babel.min.js" integrity="..."></script>
```

เป็น `<script>` ธรรมดา **ไม่มี `defer`/`async`** → block การ parse ต่อ และ boot IIFE (บรรทัด 1318)
ต้องรอมันเสร็จก่อนเสมอ

แต่ดู `compileJsx()` (บรรทัด 1333):

```js
var resp = await (pre || fetch(src));
var etag = resp.headers.get('etag') || ...;
if (etag && typeof caches !== 'undefined') {
  var hit = await bc.match(src + '.compiled');
  if (hit && hit.headers.get('x-etag') === etag) {
    return await hit.text();   // ← คืนเลย ไม่แตะ Babel เลยแม้แต่บรรทัดเดียว
  }
}
var compiled = Babel.transform(text, {...});   // ← ใช้ Babel เฉพาะตรงนี้
```

**โหลดที่ 2 เป็นต้นไป (ไฟล์ไม่เปลี่ยน) → cache hit ทั้ง 6 ไฟล์ → `Babel` ไม่เคยถูกเรียก**
แต่เบราว์เซอร์ยัง download (service worker cache ให้แล้ว จึงไม่กินเน็ต) + **decompress + parse + eval
JavaScript 2.9 MB ทุกครั้ง** ซึ่งเป็นงาน CPU ล้วน ๆ บน main thread

บนมือถือ Android รุ่นกลางที่พนักงานใช้ ค่านี้อยู่ราว **0.5–1.5 วินาทีของจอค้าง** ต่อการเปิดแอป 1 ครั้ง
ที่ไม่ได้ใช้ประโยชน์อะไรเลย

### แก้ยังไง

โหลด Babel **แบบ lazy เฉพาะตอน cache miss**:

1. ลบ `<script src=babel.min.js>` ตัวที่ block ออก
2. เพิ่ม `ensureBabel()` — inject `<script>` แล้วคืน promise, กันเรียกซ้ำด้วยตัวแปรเดียว
3. ใน `compileJsx` ก่อนบรรทัด `Babel.transform` ให้ `await ensureBabel()`

```js
var _babelP = null;
function ensureBabel() {
  if (_babelP) return _babelP;
  _babelP = new Promise(function (res, rej) {
    var s = document.createElement('script');
    s.src = 'https://unpkg.com/@babel/standalone@7.29.0/babel.min.js';
    s.integrity = '<ค่าเดิม>'; s.crossOrigin = 'anonymous';
    s.onload = res; s.onerror = rej;
    document.head.appendChild(s);
  });
  return _babelP;
}
```

**ข้อควรระวัง**:
- ต้องคง `integrity` + `crossorigin` เดิมไว้ (security)
- โหลดแรกสุด / โหลดแรกหลัง deploy จะ **ช้ากว่าเดิมเล็กน้อย** เพราะเดิม Babel โหลดขนานกับ JSX
  ตอนนี้ต้องรอรู้ผล cache ก่อน → แก้ได้ด้วย `<link rel="preload" as="script">` ให้ Babel
  (preload ไม่ block แต่เริ่มโหลดขนานไว้) — **แนะนำให้ทำคู่กัน**
- ยังต้องเก็บ Babel ไว้ในกฎ ③ ของ `service-worker.js` (cache-first) เหมือนเดิม

**ประเมินผล**: ตัดงาน CPU ~2.9 MB ออกจาก critical path ของ "ทุกการเปิดแอปที่โค้ดไม่เปลี่ยน"
ซึ่งคือ 95%+ ของการเปิดแอปทั้งหมด

## 🟠 P2 — เขียน localStorage ทั้งก้อนแบบ synchronous ทุก 30 วินาที

`app.jsx:668`:

```js
function saveToStorage(d, source) {
  localStorage.setItem(LS_KEY, JSON.stringify(d));   // ← sync ทั้งคู่ บล็อก main thread
}
```

เรียกจาก `fetchFromSheet` ทุกครั้งที่สำเร็จ (บรรทัด 926) — รวมถึง **poll ทุก 30 วินาที**

งานย่อ payload ที่อุตส่าห์ทำใน P-perf รอบก่อน ถูกกางคืนก่อนเขียน disk พอดี

พนักงานที่ยืนนับสต๊อกอยู่ = จอกระตุกทุก 30 วินาที ตรงกับตอนกำลังพิมพ์ตัวเลข

### แก้ยังไง (เรียงจากง่ายไปยาก เลือกทำข้อเดียวก็พอ)

**ทางเลือก A (แนะนำ, ง่ายสุด)** — ไม่ต้องเซฟตอน poll
poll มีไว้ให้เห็นเลขคลังอ้างอิงล่าสุด ไม่ใช่ข้อมูลที่ต้องกู้ตอน offline
→ เพิ่ม flag `fetchFromSheet(retryLeft, {persist:false})` แล้ว interval ส่ง `persist:false`

**ทางเลือก B** — เซฟรูปย่อ
เก็บ `d.products[].mo` ไว้ (อย่า `delete`) แล้วเซฟก่อน expand หรือย่อกลับก่อนเขียน
→ ก้อนเล็กลงตามสัดส่วนเดียวกับที่ประหยัดได้ตอนส่งผ่านเน็ต
⚠️ ถ้าเลือกทางนี้ ต้องมั่นใจว่า `loadFromStorage` กางกลับให้ครบ — ตอนนี้มี `expandMonthlyCompact`
ครอบไว้แล้ว (บรรทัด 664) จึงรองรับอยู่

**ทางเลือก C** — debounce 3 วินาที + `requestIdleCallback`
กันเขียนรัวตอน fetch ซ้อน แต่ยังบล็อกจอตอนเขียนจริง

**ไม่แนะนำ**: ย้ายไป IndexedDB — async จริงแต่รื้อเยอะ ผลตอบแทนไม่คุ้มเทียบทางเลือก A

## 🟠 P3 — `_headers` สั่ง `no-cache` ให้ทุกไฟล์ รวมรูปและ lib

`_headers` ทั้งไฟล์:

```
/*
  Cache-Control: no-cache
```

`/*` = **ทุกไฟล์** รวมถึง:

| ไฟล์ | ขนาด | ควรเป็น |
|---|---|---|
| `logo.png` | **268 KB** | cache ยาว (1 ปี) |
| `html2canvas.min.js` | **196 KB** | cache ยาว |
| `icon-512.png` | 70 KB | cache ยาว |
| `icon-192.png` | 19 KB | cache ยาว |
| `.jsx` (6 ไฟล์) | 1.25 MB | **คง `no-cache` ไว้** — ETag flow ของ compiled cache พึ่งอยู่ |
| `.html` | 66 KB | **คง `no-cache` ไว้** — พก CSS ทั้งหมด ถ้า stale จะ skew กับ JSX ใหม่ |

`no-cache` ไม่ได้แปลว่า "ห้าม cache" แต่แปลว่า "ต้อง revalidate ก่อนใช้ทุกครั้ง" → ยิง
conditional request ได้ 304 กลับมา (ไม่กินแบนด์วิดท์มาก แต่**กิน round trip**) ซึ่งบนเน็ตมือถือ
ในร้านที่ latency สูง เป็นต้นทุนที่เห็นได้

### แก้ยังไง

```
/*
  Access-Control-Allow-Origin: *
  Access-Control-Allow-Methods: GET, POST, OPTIONS
  Access-Control-Allow-Headers: Content-Type
  Cache-Control: no-cache

/*.png
  Cache-Control: public, max-age=31536000, immutable

/html2canvas.min.js
  Cache-Control: public, max-age=31536000, immutable
```

⚠️ `immutable` แปลว่า **ถ้าจะเปลี่ยนรูป ต้องเปลี่ยนชื่อไฟล์** (เช่น `logo-v2.png`) ไม่งั้นเครื่องเก่าจะไม่เห็นของใหม่
เป็น trade-off ที่คุ้มสำหรับ logo/icon ที่แทบไม่เคยเปลี่ยน

**แถม (ทำพร้อมกันได้ ถูกมาก)**: `logo.png` 268 KB สำหรับโลโก้ถือว่าใหญ่ผิดปกติ
ลองบีบเป็น WebP หรือลดขนาดจริงลง น่าจะเหลือ 20–40 KB โดยตาคนดูไม่ออก

## 🟡 P4 — service worker revalidate JSX 6 ไฟล์ทุกครั้งที่เปิดแอป

`service-worker.js:88` ใช้ stale-while-revalidate กับ `.jsx`/`.js`:

```js
const networkFetch = fetch(e.request).then(...);   // ยิงเสมอ ทุกครั้ง
e.waitUntil(networkFetch.catch(() => {}));
e.respondWith(cacheP.then(c => c.match(e.request)).then(cached => cached || networkFetch));
```

จอขึ้นเร็ว (ได้จาก cache) ✅ แต่ background ยิง **6 request ขนานกัน** ซึ่ง**แย่งแบนด์วิดท์กับ
request ข้อมูลจาก GAS** ที่อยู่บน critical path จริง ๆ — บนเน็ตร้านที่ไม่แรง อันนี้เห็นผล

**ข้อเสนอ**: throttle การ revalidate — เก็บ timestamp ใน Cache API แล้วข้ามการยิงถ้าเช็คไปแล้ว
ภายใน N นาที (เช่น 10 นาที)

⚠️ **ความเสี่ยง**: หลัง deploy โค้ดใหม่ เครื่องจะช้าเห็นของใหม่ขึ้นอีก → ต้องคู่กับการ bump
`CACHE_NAME` ทุกครั้งที่ deploy (ซึ่งทำอยู่แล้ว มี comment เตือนบนสุดของไฟล์)
**ควรทำหลัง P0–P3 และหลังวัดผลแล้วว่ายังช้าอยู่** ไม่ใช่ทำพร้อมกัน

`p.imageUrl` มาจาก ZORT CDN ตรง ๆ (`pickZortImage_` → `imagepath`) ไม่มีการย่อ

จุดที่ใส่ `loading="lazy"` แล้วมีแค่ **15 จุด** จากที่ใช้ `imageUrl` ทั้งหมดหลายสิบจุด
และหลายจุดใช้ `backgroundImage: url(...)` ซึ่ง **lazy ไม่ได้เลย** (เช่น `views-main.jsx:847, 2348, 5428`)

หน้าที่ลิสต์สินค้า 20 การ์ด = โหลดรูปเต็มขนาด 20 รูปพร้อมกัน

**ข้อเสนอ (2 ขั้น)**:
1. **ขั้นที่ทำได้เลย** — เปลี่ยน `backgroundImage` เป็น `<img loading="lazy" decoding="async">`
   ในจุดที่เป็น thumbnail 38–44px + เพิ่ม `loading="lazy"` ให้ `<img>` ที่ยังไม่มี
2. **ขั้นที่ต้องตรวจก่อน** — ZORT CDN รองรับ query param ย่อรูปไหม (เช่น `?w=88`)
   **ยังไม่รู้ ต้องทดลองยิงดูก่อน ห้ามเดา** ถ้ารองรับ จะลดขนาดโหลดได้หลายเท่า
   ถ้าไม่รองรับ ทางเลือกคือทำ proxy ย่อรูปที่ Cloudflare Pages Function (มี infra อยู่แล้ว)

## ปัญหาปัจจุบัน

**เจ้าของมี 25 แท็บ กระจาย 6 หมวด** (`OWNER_GROUPS` ใน `app.jsx:60`) —
ถ้าอยากรู้ว่า "วันนี้ร้านเป็นยังไง" ต้องเปิดหลายแท็บแล้วประกอบภาพเอง:

|---|---|

| ใครมาทำงานบ้าง | `atttoday` |

และ `OverviewView` เอง (`views-main.jsx:1020–2915`, ~1,900 บรรทัด) เป็นหน้า **วิเคราะห์ย้อนหลัง**
— YoY, เลือกปี/ไตรมาส/เดือน, กราฟรายวัน, forecast — ซึ่งดีมากสำหรับ "นั่งวิเคราะห์"
แต่ตอบไม่ได้ว่า **"ตอนนี้มีอะไรที่ฉันต้องจัดการ"**

## ข้อเสนอ: หน้า "วันนี้" (Today) — แท็บใหม่ ตัวแรกของเจ้าของ

**หลักคิด**: หน้านี้ไม่ใช่หน้าวิเคราะห์ แต่เป็น **"หน้าที่บอกว่าต้องทำอะไรบ้าง"**
ทุกบล็อกบนหน้านี้ **แตะแล้วพาไปหน้าที่แก้เรื่องนั้นได้** — ไม่มีตัวเลขที่ดูได้อย่างเดียว

```
┌─────────────────────────────────────┐
│ 📅 ศุกร์ 31 ก.ค. 2026               │
├─────────────────────────────────────┤
│ 💰 ยอดขายวันนี้                      │
│    ฿48,200  ▲12% จากศุกร์ที่แล้ว     │
│    38 บิล · เฉลี่ย ฿1,268/บิล        │  → แตะ = pos
├─────────────────────────────────────┤
│ ⚠️ ต้องจัดการ  (3)                   │
│  🔴 ของค้างส่ง 6 รายการ  ค้าง 2 วัน  │  → orders
│  🟠 ใกล้หมด 12 SKU (A-class 4)      │  → stock
│  🟡 ใบเสนอราคาค้าง 4 ใบ  เกิน 7 วัน │  → quotefollowup
├─────────────────────────────────────┤
│ 👥 วันนี้เข้างาน 5/7                  │
│    หน้าร้าน 3 · คลัง 2 · พัก 1       │  → atttoday
│    ⚠️ ยังไม่เข้า: สมชาย, นก           │
├─────────────────────────────────────┤
│ 📦 สต๊อก                             │
│    ของจม ฿182,000 (จม >2 เดือน)     │  → deadstock
│    ล็อคครบกำหนดนับ 8 ล็อค            │  → stockcount
├─────────────────────────────────────┤
│ 📈 เดือนนี้ vs เดือนที่แล้ว           │
│    ฿1.02M ▲8%  · เหลืออีก 0 วัน      │  → overview
└─────────────────────────────────────┘
```

### ทำไมออกแบบแบบนี้

1. **"ต้องจัดการ" อยู่บนสุด และมีเลขกำกับ** — เจ้าของเห็นทันทีว่าวันนี้มีอะไรเสี่ยงพัง
   ไม่ต้องไล่เปิด 6 แท็บ
2. **ทุกบล็อกกดได้** — ตรงกับ convention ของโปรเจกต์ที่ห้ามทำอะไรที่ดูได้อย่างเดียว
3. **ไม่มีกราฟบนหน้านี้** — กราฟหมายถึงต้องรอ Recharts (defer) โหลด และเจ้าของเปิดหน้านี้
   ตอนอยากได้คำตอบเร็ว ไม่ใช่ตอนอยากนั่งดู → กราฟอยู่ที่ `overview` เหมือนเดิม
4. **เทียบ "ศุกร์ที่แล้ว" ไม่ใช่ "เมื่อวาน"** — ร้านนี้ยอดขายขึ้นกับวันในสัปดาห์
   เทียบเมื่อวาน (พฤ. vs ศ.) ให้ข้อสรุปผิด
5. **ใช้ข้อมูลที่มีอยู่แล้วทั้งหมด** — ไม่ต้องเพิ่มชีต ไม่ต้องเพิ่ม endpoint หนัก

### แหล่งข้อมูลต่อบล็อก (ตรวจแล้วว่ามีจริง)

| ของค้างส่ง | `data.orders` filter `status==="รอ"` | มีแล้ว (banner ใน CategoryView ใช้อยู่) |

ขึ้นทีหลังพร้อม skeleton — ห้ามรอครบทุกแหล่งแล้วค่อยวาด ไม่งั้นหน้านี้จะกลายเป็น
"หน้าที่ช้าที่สุดในระบบ" ซึ่งขัดกับจุดประสงค์

2. **ฝั่งเว็บ** — เปิด DevTools > Performance บนมือถือจริงของพนักงาน (ไม่ใช่ desktop throttle)
   วัด 3 ค่า: เวลาถึง first paint, เวลาถึงแอปกดได้, ระยะที่ main thread ถูกบล็อก
3. **ของจริงที่สุด** — จับเวลาด้วยนาฬิกา: กดไอคอนบนหน้าโฮม → ถึงตอนกดสั่งของได้
   ก่อนแก้ vs หลังแก้ บนเครื่องพนักงานเครื่องเดิม เน็ตร้านเดิม

## ของที่ยังไม่รู้ — ต้องถามเจ้าของ/ตรวจก่อนลงมือ

1. **ยอมให้ข้อมูลเก่าได้ ≤ 3 นาที ไหม** (P0) — ปกติไม่มีผล เพราะทุก write ล้าง cache เอง
   จะเก่าเฉพาะกรณีมีคนแก้ Google Sheet ด้วยมือโดยตรง
2. **ZORT CDN ย่อรูปด้วย query param ได้ไหม** (P5.2) — ยังไม่รู้ ต้องทดลองยิงก่อน ห้ามเดา
3. **หน้า "วันนี้" อยากได้บล็อกไหนเพิ่ม/ตัดออก** — แบบข้างบนเป็นข้อเสนอเริ่มต้น
   เจ้าของรู้ดีที่สุดว่าตัวเองเปิดแอปมาเพื่อดูอะไรก่อน
4. **`logo.png` 268 KB มีไฟล์ต้นฉบับความละเอียดสูงเก็บไว้ไหม** — จะได้บีบจากต้นฉบับ
   ไม่ใช่บีบจากไฟล์ที่บีบแล้ว
