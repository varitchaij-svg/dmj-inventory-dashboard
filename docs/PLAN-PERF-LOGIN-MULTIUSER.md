# แผนปรับปรุง: ล็อกอิน · ใช้งานหลายคนพร้อมกัน · ความเร็ว/ความแม่นยำ

ตรวจทั้งระบบ ส.ค. 2026 — **ยังไม่ลงมือแก้** เอกสารนี้คือแผนให้เจ้าของเลือกว่าจะทำอะไรก่อน

> **ปรับแผนรอบ 2** — รอบแรกโฟกัสที่ "การดึงข้อมูล" อย่างเดียว แล้วพบทีหลังว่า
> อาการ "หลายคนใช้พร้อมกันแล้วติด" ตัวจริงอยู่ที่ **ฝั่งบันทึกข้อมูล** (ข้อ 1 ด้านล่าง)
> ซึ่งแก้ง่ายกว่าและได้ผลตรงกว่าทุกข้อในแผนเดิม จึงย้ายขึ้นมาเป็นอันดับแรก

## สรุปสั้นที่สุด

อาการ "อืด" มาจาก 4 เรื่องที่ทับกัน เรียงตามความสำคัญที่ตรวจเจอจริง:

1. **ล็อกกลางตัวเดียวของทั้งระบบ ถูกถือไว้ระหว่างรอ ZORT/LINE ตอบ** →
   ตอนมีคนบันทึกงาน คนอื่นทั้งร้านต้องรอ หรือโดนเด้ง "ระบบกำลังบันทึกข้อมูลอื่นอยู่"
2. **ยิงถี่เกินจำเป็น** — 1 เครื่องยิง GAS ~150–380 ครั้ง/ชม. โดยได้ข้อมูลเดิมกลับมา
3. **ทุกการบันทึกล้าง cache ของทั้งร้าน** → คนถัดไปต้อง build payload ใหม่ทั้งก้อน
4. **เครื่องผู้ใช้ประมวลผลข้อมูลทั้งก้อนซ้ำทุก 30 วิ** → มือถือค้างเป็นจังหวะ

## Phase 0 — วัดก่อนแก้ (ครึ่งวัน, ต้องทำก่อนทุกข้อ)

ของที่มีอยู่แล้วและใช้ได้เลย:

| เครื่องมือ | ดูอะไร | อยู่ที่ไหน |
|---|---|---|
| `logPayloadSizes_` | ขนาด payload แต่ละก้อน | Executions log |
| `_ms` ใน `buildFullData_` | เวลาที่ใช้ต่อขั้น (batchGet/products/enrich/…) | Executions log |
| Executions list | จำนวน/เวลา/error ต่อชั่วโมง | GAS editor → Executions |

**ต้องได้ตัวเลขจริง 4 ตัวก่อนเริ่ม Phase 3**
- payload กี่ MB ต่อ role · `buildFullData_` ครั้งหนึ่งกี่วินาที (และเวลาไปอยู่ขั้นไหน)
- execution/ชม. ช่วงคนใช้พร้อมกันมากสุด · มี error/timeout กี่ %

**ตรวจ trigger ที่ตั้งไว้ด้วย (สำคัญ — อาจเป็นตัวกินโควตาเงียบ ๆ)**

| trigger | ความถี่ | ต่อวัน | หมายเหตุ |
|---|---|---|---|
| `drainNotiQueue` | ทุก 1 นาที | 1,440 | จับล็อกกลางทุกครั้ง (ดูข้อ 1.1) |
| `backfillZortOrders` | ทุก 5 นาที | 288 | **ลบตัวเองเมื่อ `backfill_done='1'`** — เช็คว่ายังวิ่งอยู่ไหม |
| `syncZortBoth` / `syncZortSales` | ทุก 2 ชม. | 12+12 | ล้าง cache ทั้งร้านทุกครั้ง = ตกอยู่กลางเวลาทำงาน |

บัญชี Gmail ธรรมดามีเพดาน **เวลารวม trigger 90 นาที/วัน** — ถ้าเต็ม trigger จะเงียบไปทั้งวัน
โดยไม่มีอะไรเตือน · ถ้า Phase 0 พบว่าใกล้เต็ม: ลด `drainNotiQueue` เหลือทุก 5 นาที
และปิด `backfillZortOrders` ถ้า backfill จบแล้ว

## Phase 1 — ปลดล็อกฝั่ง "บันทึกข้อมูล" ⭐⭐ ทำก่อนสุด (ผลตรงที่สุด/เสี่ยงต่ำ)

GAS มีล็อกกลางแค่ **ตัวเดียวต่อทั้งสคริปต์** (`LockService.getScriptLock()`) — ไม่มีล็อกแยกราย SKU
ทุกฟังก์ชันที่เขียนข้อมูลใช้ตัวเดียวกันหมด ดังนั้น "ใครถือล็อกนานเท่าไหร่ = ทั้งร้านรอเท่านั้น"

### 1.1 `drainNotiQueue` ถือล็อกไว้ตอนยิง LINE — **ทุก 1 นาที**

```
drainNotiQueue():  tryLock(5000) → อ่านชีตคิว → pushOrderBatch_ → linePush_ → UrlFetchApp(LINE)
                   └──────────────── ถือล็อกตลอดช่วงนี้ ────────────────┘
```
ยิง LINE ครั้งหนึ่งใช้ ~0.3-2 วิ (ถ้า LINE ช้า/timeout ยาวกว่านั้นมาก) และเกิด **ทุกนาที**
→ ในจังหวะนั้นใครกดสั่งของ/โอน/รับของ/บันทึกล็อค จะรอ หรือโดนเด้ง
"ระบบกำลังบันทึกข้อมูลอื่นอยู่" · **เกิดได้แม้มีคนใช้อยู่คนเดียว**

**แก้**: อ่านคิว + มาร์คแถวเป็น "กำลังส่ง" ใต้ล็อก → **ปล่อยล็อก** → ค่อยยิง LINE →
จับล็อกสั้น ๆ อีกทีเพื่อบันทึกผล · (ล็อกมีไว้กันสอง drain ทับกันเท่านั้น ไม่ได้กันอะไรมากกว่านั้น)

### 1.2 งานสต็อกถือล็อกไว้ตอนยิง ZORT

`deductStock` · `confirmStockCount` · `zeroStockItem_` เรียก `pushStockToZort_()`
(ยิง `UrlFetchApp` ไป ZORT) **ขณะถือล็อกอยู่** — ZORT ตอบช้า 1-5 วิเป็นปกติ

พนักงานคลังกดยืนยันนับสต็อก 1 ครั้ง = ทั้งร้านหยุดรอ 1-5 วิ · คนหน้าร้านที่กดพร้อมกัน
เจอ `tryLock(8000)` หมดเวลาแล้วขึ้น error ทั้งที่ไม่ได้ยุ่งกับสินค้าตัวเดียวกันเลย

**แก้ที่เสนอ — เข้าคิวแทนการยิงสด** (ใช้แพทเทิร์นเดียวกับคิวแจ้งเตือน LINE ที่มีอยู่แล้ว):
- เขียนชีตเสร็จใต้ล็อก → **เข้าคิว "รอ push ZORT"** → ปล่อยล็อก → ตอบผู้ใช้ทันที
- trigger (หรือท้าย request ถัดไป) ดึงคิวไปยิง ZORT
- **ผลพลอยได้**: ผู้ใช้ได้คำตอบเร็วขึ้น 1-5 วิทุกครั้งที่บันทึกสต็อก

> ⚠️ **เหตุผลที่ต้องเป็น "คิว" ไม่ใช่แค่ "ปล่อยล็อกก่อนยิง"**
> `pushStockToZort_` ส่ง **ยอดคงเหลือแบบ absolute** (set ทับ) ไม่ใช่ส่วนต่าง —
> ถ้าปล่อยล็อกแล้วยิงขนานกัน สองคำสั่งบน SKU เดียวกันอาจไปถึง ZORT สลับลำดับ
> → ZORT ค้างค่าผิด และเพราะ **ZORT เป็น source of truth** ค่าผิดนั้นจะถูก sync
> กลับมาทับชีตในอีก 2 ชม. **โดยไม่มี error ให้เห็นเลย** · คิวทำให้การยิงเรียงลำดับเสมอ

### 1.3 ผลที่คาดจาก Phase 1

อาการ "กดแล้วค้าง / ขึ้นระบบกำลังบันทึกข้อมูลอื่นอยู่ / สั่งของแล้วแดง" ควรลดลงชัดเจน
โดย **ไม่ต้องแตะ cache หรือ payload เลย** — แก้ 2 จุด เสี่ยงต่ำ

## Phase 2 — ลดจำนวน/ขนาดการดึงข้อมูล ⭐

### 2.1 `action=ping` — ถามว่า "มีอะไรเปลี่ยนไหม" แทนดึงทั้งก้อน

แท็บ `stockcount`/`frontstore` ดึง **payload ทั้งก้อนทุก 30 วิ** (`app.jsx:1087`)
ทั้งที่เกือบทุกครั้งข้อมูลไม่เปลี่ยน

```
doGet action=ping → { ts: dmj_last_write_ts }
```
- อ่าน Script Properties อย่างเดียว **ไม่แตะชีต ไม่แตะ cache** (~50-100 ms)
- frontend: poll `ping` · `ts` เปลี่ยนเมื่อไหร่ค่อยดึงจริง

> **พูดให้ตรง**: ping **ไม่ได้ลดจำนวน request** (ยังยิงเท่าเดิม) แต่ลด
> **เวลาที่ GAS ใช้ต่อ request** และ **ปริมาณข้อมูลที่ส่งลงมือถือ** ลงเกือบทั้งหมด
> — ซึ่งคือตัวที่ทำให้คิวยาวและเน็ตมือถืออืด ไม่ใช่จำนวนครั้ง

### 2.2 หยุด poll เมื่อผู้ใช้ไม่ได้ดูอยู่

ทุก interval เช็คแค่ `navigator.onLine` — เครื่องที่เปิดค้างไว้ในกระเป๋า (Android)
ยิงต่อทั้งวัน · เพิ่ม `!document.hidden` + ดึงทันทีตอนกลับมา
(โครงนี้มีอยู่แล้วใน `NotiBell` — เอามาใช้ให้ครบ)

### 2.3 กระดิ่งที่ปิดอยู่ ต้องไม่เสียของฟรี

`listInappNotiHandler_` เรียก `resolveSession_` (อ่าน 2 ชีต + เขียน 1 เซลล์) **ก่อน**
เช็คว่าระบบเปิดไหม → ร้านที่ยังไม่เปิดใช้ก็จ่ายเต็มทุก 25 วิ · **สลับลำดับ 2 บรรทัด**

### 2.4 จังหวะ poll

| ที่ | ตอนนี้ | เสนอ |
|---|---|---|
| กระดิ่ง | 25 วิ | 60 วิ + ดึงตอนกลับมาที่แอป |
| orders | 15 วิ ดึงจริง | ping 15 วิ → ดึงจริงเมื่อเปลี่ยน (คงความไวไว้) |
| stockcount/frontstore | 30 วิ ทั้งก้อน | ping 30 วิ → ดึงจริงเมื่อเปลี่ยน |

## Phase 3 — ให้เครื่องผู้ใช้ไม่ค้าง (อาการ "แอปหน่วง" ที่รู้สึกได้ตรง ๆ)

ทุกครั้งที่ได้ payload (รวมทุก poll 30 วิ) เครื่องทำครบชุด:
`JSON.parse` → `expandMonthlyCompact` (สร้าง object ~สินค้า×เดือน ต่อรอบ) →
`enrichData` (วนสินค้าทั้งหมดหลายรอบ) → `JSON.stringify` → `localStorage.setItem`

**แก้**
- **ข้ามทั้งชุดถ้า `d.lastModified` เท่าเดิม** — ทำคู่กับ ping แล้วแทบไม่เข้า path นี้อีก
- **เขียน localStorage แบบหน่วง** (ทุก 2-5 นาที / ตอนปิดแอป) ไม่ใช่ทุก poll
- เก็บ localStorage เป็นรูปแบบย่อ (`mo`) แล้วกางตอนใช้
- (ทางเลือกภายหลัง) ย้าย parse/enrich ไป Web Worker

## Phase 4 — cache ที่ไม่พังทั้งก้อนเวลามีคนบันทึกงาน

### 4.1 ปัญหา

`doPost` เรียก `invalidateCache_(true)` ก่อนทุก action ที่แก้ข้อมูล → ล้าง cache **ทุก variant**
→ ใครโหลดถัดไปต้อง `buildFullData_()` ใหม่หมด · ร้านที่มีคน 5-6 คนบันทึกงานตลอด
cache แทบไม่เคยอยู่ครบ 3 นาที · **`syncZortBoth`/`syncZortSales` ก็ล้างทุก 2 ชม. ด้วย**

### 4.2 ⚠️ ยังไม่ควรตัดสินใจวิธีแก้ตอนนี้

แผนรอบแรกเสนอ "แยก cache 2 ชั้น (หนัก/สด)" ไปเลย ซึ่ง**เร็วเกินไป** — วิธีที่ถูกขึ้นกับ
ตัวเลขจาก Phase 0:

| ถ้า Phase 0 บอกว่า… | วิธีที่ควรใช้ |
|---|---|
| เวลาหมดไปกับ `enrich`/วนสินค้า | **แยก 2 ชั้น** (ชั้นหนักไม่ต้องคำนวณใหม่) — ได้ผลเต็ม |
| เวลาหมดไปกับ `batchGet` (อ่านชีต) | แยกชั้นช่วยน้อย เพราะยังต้องอ่านชีต "สด" อยู่ดี → ควรลดจำนวนชีตที่อ่าน/ลดขนาดชีตแทน |
| build เร็วอยู่แล้ว (< 2-3 วิ) | **ไม่ต้องทำ Phase นี้เลย** — ไปลงแรงที่ Phase 1-3 คุ้มกว่า |

ถ้าสุดท้ายเลือกแยก 2 ชั้นจริง **ต้องมีตารางชัดเจนว่า action ไหนล้างชั้นไหน + meta-test
บังคับว่า action ใหม่ทุกตัวต้องมี entry** — เดาผิดข้างล้างน้อยไป = คนเห็นข้อมูลเก่าค้าง
โดยไม่มีอะไรเตือน ซึ่งเป็นบั๊กที่หาสาเหตุยากที่สุดในระบบนี้ (**เป็นงานเสี่ยงสูงสุดในเอกสารนี้**)

## Phase 5 — ล็อกอิน / session

### 5.1 `resolveSession_` แพงเกินจำเป็น

ต่อ 1 request: อ่านชีต "เซสชัน" ทั้งใบ → **เขียน `lastSeenAt` ลงเซลล์** → สแกนชีต "พนักงาน"
→ อ่าน 11 คอลัมน์ · เรียกจาก **ทุก doPost** + กระดิ่ง + ⭐ผู้ดูแลสินค้า + รูปลงเวลา + audit log

**แก้**: cache `{staffId, role, name, status}` ใน CacheService (คีย์ = แฮชของ token)
+ เขียน `lastSeenAt` เฉพาะเมื่อค่าเดิมเก่ากว่า 10 นาที
- **แนะนำ TTL 5 นาที** และให้ `saveStaff`/`logout` **ลบคีย์นั้นทันที** → การถอดสิทธิ์
  ผ่านหน้าจอ "พนักงาน" มีผลทันทีอยู่ดี · ช่องว่าง 5 นาทีเหลือแค่กรณีแก้ชีตด้วยมือ
  (เดิมผมตั้งเป็นคำถามให้เจ้าของเลือก — จริง ๆ มีทางที่ได้ทั้งสองอย่าง ไม่ต้องแลก)

### 5.2 เปิดแอปต้องรอ `me` ก่อนถึงจะเห็นอะไร

`authPhase === "checking"` โชว์แต่วงกลมหมุน — GAS เพิ่งตื่นก็รอยาว
**แก้**: จำ staff ล่าสุดไว้ → เข้าหน้าจอทำงานได้เลย แล้วเช็ค `me` เบื้องหลัง ไม่ตรงค่อยเด้งออก
(ปลอดภัยเพราะสิทธิ์จริงบังคับที่ server อยู่แล้ว — หน้าจอที่เห็นก่อนไม่ได้ให้สิทธิ์อะไรเพิ่ม)

### 5.3 ปุ่มล็อกอิน LINE ยิง `lineLoginMeta` ทุกครั้งที่กด

เพิ่มเวลารอ 1 รอบเน็ตก่อน redirect · มี cache `LINE_CHANNEL_KEY` อยู่แล้ว → ใช้ค่า cache ก่อน

### 5.4 ลงเวลา — ต้นทุนโตขึ้นทุกวัน

`readAttEvents_` อ่าน **ชีตลงเวลาทั้งใบ (17 คอลัมน์ × ทุกแถวตั้งแต่เริ่มใช้)** เพื่อหาแค่
"วันนี้ของคนเดียว" · ~22,000 แถว/ปี และโตต่อไปเรื่อย ๆ
- **แก้ไขข้อมูลรอบแรก**: ผมเคยเขียนว่า "แท็บลงเวลาเป็นแท็บแรกที่ทุก role เปิดเจอ" — **ผิด**
  แอปเปิดที่ `categories` (owner) / `overview` (role อื่น) · แท็บลงเวลาแค่อยู่ซ้ายสุดในแถบเมนู
  → ต้นทุนนี้จ่ายเฉพาะตอนคนกดเข้าแท็บลงเวลา (ซึ่งก็คือทุกเช้าตอนตอกบัตร) **ไม่ใช่ทุกครั้งที่เปิดแอป**
  จึงสำคัญน้อยกว่าที่แผนรอบแรกบอก → เลื่อนไปทำทีหลัง (แต่ต้องทำ ก่อนชีตโตกว่านี้)

## Phase 6 — "แม่นยำขึ้น"

### 6.1 conflict ปลอมเมื่อหลายคนทำงานพร้อมกัน

`shouldRejectConflict_` เทียบกับ `dmj_last_write_ts` ซึ่งเป็น timestamp **ระดับทั้งระบบ**
→ A บันทึก SKU หนึ่ง แล้ว B กดบันทึก **คนละ SKU** ก็โดนปฏิเสธ · ยิ่งคนเยอะยิ่งเจอบ่อย
- แยก timestamp ตาม "กลุ่มข้อมูล" (สต็อก/ออเดอร์/ล็อค/ลงเวลา) แล้วเทียบเฉพาะกลุ่มที่เกี่ยว

### 6.2 ข้อมูลเก่าค้างได้ถึง 3 นาที

แก้ชีตด้วยมือไม่ล้าง cache · `ping` + ป้าย "ข้อมูล ณ HH:MM" บนหัวจอ ทำให้ผู้ใช้รู้ว่า
กำลังดูของเมื่อไหร่ — ดีกว่าไล่ทำให้สดตลอดแล้วช้าลง

### 6.3 ตรวจแล้วไม่มีปัญหา

- payload แยกตาม role + cache แยก variant — ครบ ไม่มีข้อมูลรั่วข้าม role
- การเขียนแถวพร้อมกัน — `LockService` ครอบครบทุกเส้นทางแล้ว (`handleOrder_` เป็นตัวสุดท้ายที่เพิ่งเติม)
  · ปัญหาที่เหลือคือ **ถือล็อกนานเกินไป** ไม่ใช่ไม่มีล็อก (Phase 1)

## ลำดับที่แนะนำ

| ลำดับ | งาน | แรง | ผล | เสี่ยง |
|---|---|---|---|---|
| 1 | Phase 0 วัด + ตรวจ trigger | ครึ่งวัน | รู้ว่าต้องแก้อะไรจริง | ไม่มี |
| 2 | **Phase 1 ปลดล็อกฝั่งบันทึก** | 1-1.5 วัน | **แก้อาการ "กดแล้วติด/แดง" ตรงจุด** | ต่ำ |
| 3 | Phase 2 ping + หยุด poll ตอนไม่ได้ดู | 1 วัน | GAS เบาลงมาก, เน็ตมือถือประหยัด | ต่ำ |
| 4 | Phase 3 ไม่ประมวลผลซ้ำ + หน่วง localStorage | ครึ่งวัน | มือถือไม่ค้างทุก 30 วิ | ต่ำ |
| 5 | Phase 5.1-5.3 session cache + เปิดแอปไม่ต้องรอ | 1 วัน | ทุก request ที่ล็อกอินเร็วขึ้น | ต่ำ-ปานกลาง |
| 6 | Phase 4 cache (เลือกวิธีตามผล Phase 0) | 0-3 วัน | อาจไม่ต้องทำเลย | **สูง** |
| 7 | Phase 6.1 conflict แยกกลุ่ม · 5.4 ลงเวลา | 1-2 วัน | เตือนชนกันน้อยลง | ปานกลาง |

**ชุดที่คุ้มที่สุด = ลำดับ 1-4 (≈3 วัน) เสี่ยงต่ำทั้งหมด** และครอบคลุมอาการที่พี่เจอจริงทุกข้อ
— ทำแล้ววัดผล ค่อยตัดสินใจว่าจะเอา Phase 4/6 ไหม

## เหลือให้เจ้าของตัดสินใจแค่ 2 ข้อ

1. **กระดิ่ง 25 วิ → 60 วิ** รับได้ไหม (แจ้งเตือนช้าลง ~35 วิ)
2. **pre-compile JSX ตอน deploy** — โหลดครั้งแรกหลัง deploy เร็วขึ้นชัดเจน แต่**ขัดกับ
   สถาปัตยกรรม "ไม่มี build step"** ที่ตั้งใจไว้แต่แรก (แก้ไฟล์แล้วต้องรอ Action เสร็จก่อน
   ถึงจะเห็นผล) · **ไม่ทำก็ได้ ไม่กระทบข้ออื่นเลย**

(ข้อ TTL session ที่เคยถาม — ตัดออกแล้ว มีทางที่ไม่ต้องแลกอะไร ดู 5.1)
