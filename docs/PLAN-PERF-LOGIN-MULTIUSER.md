# แผนปรับปรุง: ล็อกอิน · ใช้งานหลายคนพร้อมกัน · ความเร็ว/ความแม่นยำ

ตรวจทั้งระบบ ส.ค. 2026 — **ยังไม่ลงมือแก้** เอกสารนี้คือแผนให้เจ้าของเลือกว่าจะทำอะไรก่อน

## สรุปสั้นที่สุด

อาการ "อืด" ไม่ได้มาจากจุดเดียว แต่มาจาก **3 ชั้นที่ทับกัน**:

1. **ยิงถี่เกินจำเป็น** — เปิดแอปทิ้งไว้ 1 เครื่องยิง GAS ~150–380 ครั้ง/ชม. โดยที่
   ส่วนใหญ่ได้ข้อมูล "เหมือนเดิมเป๊ะ" กลับมา · หลายเครื่องพร้อมกัน = GAS คิวยาว
   → ตอบช้า และบางครั้งตอบเป็นหน้า HTML (ต้นเหตุแถบแดงที่เจอ)
2. **ทุกคำสั่งที่บันทึกข้อมูล ล้าง cache ของทั้งร้าน** → คนถัดไปที่โหลดต้องสร้าง
   payload ใหม่ทั้งก้อน (อ่าน 11 ชีต + ประมวลผลสินค้า ~5,600 ตัว) · ยิ่งหลายคนทำงาน
   พร้อมกัน cache ยิ่งแทบไม่ได้ใช้ ทุกคนเลยเจอเส้นทางช้าตลอด
3. **เครื่องผู้ใช้ทำงานหนักซ้ำทุก 30 วิ** — กาง/แปลง/เขียนข้อมูลทั้งก้อนลง
   localStorage ทุกครั้งที่ poll → มือถือค้างเป็นจังหวะ (อาการ "แอปหน่วง")

ส่วนล็อกอินไม่ได้ "พัง" แต่ **ช้าเพราะทุก request ที่มี session ต้องอ่าน+เขียนชีต 3-4 รอบ**
และตอนเปิดแอปต้องรอ `me` ตอบก่อนถึงจะเห็นหน้าจอ

## Phase 0 — วัดก่อนแก้ (ครึ่งวัน, ต้องทำก่อนทุกข้อ)

แก้โดยไม่วัด = ไม่รู้ว่าอันไหนได้ผลจริง · ของที่มีอยู่แล้วและใช้ได้เลย:

| เครื่องมือ | ดูอะไร | อยู่ที่ไหน |
|---|---|---|
| `logPayloadSizes_` | ขนาด payload แต่ละก้อน + ขนาด `products[].mo` | Executions log |
| `_ms` ใน `buildFullData_` | เวลาที่ใช้ต่อขั้น (batchGet/products/enrich/…) | Executions log |
| Executions list | จำนวน execution ต่อชั่วโมง + เวลาเฉลี่ย + อันที่ error | GAS editor → Executions |

**สิ่งที่ต้องได้จากเฟสนี้ (ตัวเลขจริง ไม่ใช่เดา)**
- payload กี่ MB ต่อ role · build ครั้งหนึ่งกี่วินาที · cache hit rate คร่าว ๆ
- execution/ชม. ในเวลาทำงานจริง (เช้า 9–11 น. ที่คนใช้พร้อมกันมากสุด)
- มี execution ที่ error/timeout กี่ %

**เพิ่มของใหม่ 1 อย่าง**: `action=perfProbe` (doGet, owner เท่านั้น) คืน
`{buildMs, payloadBytes, cacheAge, sessionRows, attendanceRows, notiRows}`
— ดูสุขภาพระบบได้จากมือถือโดยไม่ต้องเปิด GAS editor

> ⚠️ **เช็คด้วยว่าเกินโควตา trigger หรือยัง** — `drainNotiQueue` ตั้งไว้ทุก 1 นาที
> = 1,440 ครั้ง/วัน · บัญชี Gmail ธรรมดามีเพดาน **เวลารวมของ trigger 90 นาที/วัน**
> ถ้าแต่ละรอบใช้ ~4 วิ ก็เต็มโควตาพอดี → trigger อื่น (sync ZORT/แจ้งเตือน) เงียบไปทั้งวัน
> **ถ้าเจอว่าเต็ม ให้ลดเหลือทุก 5 นาที ทันที** (คิวแจ้งเตือนช้าลง 5 นาทีไม่กระทบงานจริง)

## Phase 1 — ลดจำนวนการยิง (ผลไวสุด/เสี่ยงต่ำสุด) ⭐ ทำก่อน

### 1.1 `action=ping` — ถามว่า "มีอะไรเปลี่ยนไหม" แทนการดึงทั้งก้อน

ตอนนี้แท็บ `stockcount`/`frontstore` ดึง **payload ทั้งก้อนทุก 30 วิ** (`app.jsx:1087`)
ทั้งที่ 9 ใน 10 ครั้งข้อมูลไม่เปลี่ยนเลย

```
doGet action=ping → { ts: dmj_last_write_ts, ok:true }
```
- อ่านจาก Script Properties อย่างเดียว **ไม่แตะชีตเลย** (~50-100 ms เทียบกับหลายวินาที)
- frontend: poll `ping` ทุก 20-30 วิ · `ts` เปลี่ยนเมื่อไหร่ค่อยดึง payload จริง
- **ผลที่คาด: การยิงหนักลดลง ~80-90%** ในแท็บที่ poll (ทุกเครื่องรวมกัน)
- ใช้ซ้ำได้กับ orders poll (15 วิ) และกระดิ่งด้วย

### 1.2 หยุด poll เมื่อผู้ใช้ไม่ได้ดูอยู่

ทุก interval ตอนนี้เช็คแค่ `navigator.onLine` — เครื่องที่เปิดแอปค้างไว้ในกระเป๋า
(Android ไม่แช่แข็ง timer เหมือน iOS) ยังยิงต่อทั้งวัน
- เพิ่มเงื่อนไข `!document.hidden` ทุกที่ + ดึงทันทีตอนกลับมา (`visibilitychange`)
  — โครงนี้มีอยู่แล้วใน `NotiBell` (ui.jsx:377) เอามาใช้ให้ครบทุกจุด

### 1.3 ปรับจังหวะให้สมจริง

| ที่ | ตอนนี้ | เสนอ | เหตุผล |
|---|---|---|---|
| กระดิ่ง (`ui.jsx:326`) | 25 วิ ทุกแท็บ | 60 วิ (+ ดึงตอนกลับมาที่แอป) | แจ้งเตือนช้าลง 35 วิ ไม่กระทบงาน |
| orders (`app.jsx:1076`) | 15 วิ | ping 15 วิ → ดึงจริงเมื่อเปลี่ยน | คลังต้องเห็นไว — คงความไวไว้ด้วย ping |
| stockcount/frontstore | 30 วิ ทั้งก้อน | ping 30 วิ → ดึงจริงเมื่อเปลี่ยน | เหมือนกัน |

### 1.4 กระดิ่งที่ปิดอยู่ ต้องไม่เสียของฟรี

`listInappNotiHandler_` เรียก `resolveSession_` (อ่าน+เขียนชีต 3-4 รอบ) **ก่อน**
เช็คว่าระบบเปิดอยู่ไหม → ร้านที่ยังไม่เปิดใช้ก็จ่ายค่าเต็มทุก 25 วิ
- สลับลำดับ: เช็ค `inappNotiEnabled_()` ก่อน แล้วค่อย resolve session (แก้ 2 บรรทัด)

**รวม Phase 1: แก้ ~5 จุด · เสี่ยงต่ำ · คาดว่าลดโหลด GAS ได้เกินครึ่ง**

## Phase 2 — ทำให้ session ไม่แพง (ผลชัดกับทุกคนที่ล็อกอิน)

### 2.1 ปัญหา

`resolveSession_` (`appsscript_complete.gs:374`) ต่อ **1 request**:
1. อ่านชีต "เซสชัน" ทั้งใบ (`getRange(2,1,last-1,6)`) — โตขึ้นทุกการล็อกอิน ไม่มีเพดาน
2. **เขียน** `lastSeenAt` ลงเซลล์ (บรรทัด 386) ← เขียนชีตทุกครั้งที่มีคนกดอะไรก็ตาม
3. สแกนชีต "พนักงาน" หา staffId (`findStaffRowById_`)
4. อ่าน 11 คอลัมน์ของแถวนั้น

เรียกจาก: **ทุก doPost** + กระดิ่ง + ⭐ผู้ดูแลสินค้า + รูปลงเวลา + audit log
→ กระดิ่งอย่างเดียว = อ่าน 2 ชีต + เขียน 1 เซลล์ **ทุก 25 วิ ต่อเครื่อง**

### 2.2 ทางแก้

- **cache session ใน CacheService** คีย์ = แฮชของ token, เก็บ `{staffId, role, name, status}`
  TTL 5-10 นาที → request ส่วนใหญ่ไม่ต้องแตะชีตเลย
  · ล็อกเอาต์/เปลี่ยน role/ระงับพนักงาน → ลบคีย์นั้นทิ้งทันที (`saveStaff`/`logout` เรียกเอง)
  · ⚠️ **จุดที่ต้องระวัง**: ถอดสิทธิ์คนแล้วเขายังใช้ได้อีกไม่เกิน TTL — ยอมรับได้ที่ 5 นาที
    ถ้าเจ้าของไม่ยอมรับ ให้ลด TTL เหลือ 60 วิ (ยังตัดโหลดได้เกิน 95%)
- **เขียน `lastSeenAt` แบบหน่วง** — เขียนก็ต่อเมื่อค่าเดิมเก่ากว่า 10 นาที
  (ใช้ดูว่า "ใครยังใช้งานอยู่" ความละเอียดระดับนาทีไม่มีประโยชน์)
- **ล้างเซสชันหมดอายุให้ถี่ขึ้น** — ตอนนี้ล้างวันละครั้ง (22:00) ใน `dailyAttendanceMaintenance`
  ยังพอ แต่ต้องมีเพดาน: ถ้าชีตเกิน ~2,000 แถวให้ตัดของเก่าทิ้งเลย

### 2.3 ลงเวลาก็มีปัญหาเดียวกัน

`readAttEvents_` อ่าน **ชีตลงเวลาทั้งใบ (17 คอลัมน์ × ทุกแถวตั้งแต่เปิดใช้)**
เพื่อหาแค่ "วันนี้ของคนเดียว" · พนักงาน 10 คน × 6 ครั้ง/วัน = ~22,000 แถว/ปี และโตต่อไปเรื่อย ๆ
- เก็บ index "แถวแรกของวันนี้" ไว้ใน Script Property แล้วอ่านเฉพาะช่วงท้าย
  หรือขึ้นชีตใหม่รายปี (`ลงเวลา 2026`) — **แท็บลงเวลาเป็นแท็บแรกที่ทุก role เปิดเจอ**
  จึงเป็นค่าใช้จ่ายที่ทุกคนจ่ายทุกเช้า

## Phase 3 — cache ที่ไม่พังทั้งก้อนเวลามีคนบันทึกงาน ⭐ ผลเยอะสุด

### 3.1 ปัญหา

`doPost` เรียก `invalidateCache_(true)` (บรรทัด 1801) **ก่อนทุก action ที่แก้ข้อมูล** →
ล้าง payload cache **ทุก variant** · หลังจากนั้นใครโหลดก่อนต้อง `buildFullData_()` ใหม่หมด
(อ่าน 9 ชีตผ่าน batchGet + purchases/qtyLoc/mtoJobs อีก + วนสินค้า 5,600 ตัว)

ร้านที่มีคน 5-6 คนบันทึกงานตลอด = cache **แทบไม่เคยอยู่ครบ 3 นาที**
→ ทุกคนเจอเส้นทางช้าเกือบทุกครั้ง

### 3.2 ทางแก้ที่เสนอ (เรียงจากง่าย→ได้ผลมาก)

**(ก) แยก cache เป็น 2 ชั้น: "ของหนักที่ไม่ค่อยเปลี่ยน" กับ "ของสด"**

| ชั้น | มีอะไร | เปลี่ยนเมื่อไหร่ | TTL |
|---|---|---|---|
| หนัก | products, monthly/daily sales, purchases, monthLabels | sync ZORT (ทุก 2 ชม.) / เพิ่มสินค้า / นับสต็อก | 30-60 นาที |
| สด | orders, shipments, mtoJobs, storage, frontStoreQty | ทุกครั้งที่มีคนสั่ง/โอน/รับของ | 60 วิ |

- `doGet` ต่อ 2 ชั้นเข้าด้วยกันแล้วส่ง (การต่อ string ถูกกว่าการ build ใหม่มาก)
- write ส่วนใหญ่ (สั่งของ/โอน/รับของ/ปิดงาน) แตะแค่ชั้น "สด" → **ชั้นหนักอยู่ยาว**
- ⚠️ **ต้องมีตารางชัดเจนว่า action ไหนล้างชั้นไหน** และ default = ล้างทั้งคู่
  (เดาผิดข้างล้างน้อยไป = คนเห็นข้อมูลเก่าโดยไม่มีอะไรเตือน — บั๊กที่หายากที่สุด)
  → ต้องมี meta-test บังคับว่า action ใหม่ทุกตัวต้องมี entry ในตารางนี้

**(ข) build แล้วแจกทุก variant ในรอบเดียว** — ทำอยู่แล้ว (บรรทัด 2210) ✅ ไม่ต้องแก้

**(ค) ถ้ายังช้าอยู่: cache ชั้นหนักลง Script Property/ชีตแทน CacheService**
CacheService หายได้เองโดยไม่บอก (Google เคลียร์เมื่อไหร่ก็ได้) — ชั้นหนักที่ build แพง
ควรมีที่เก็บที่ไม่หายง่าย · เก็บเป็นชีตซ่อน 1 ใบ (`_cache_payload`) แล้วอ่านทีเดียว

## Phase 4 — ทำให้เครื่องผู้ใช้ไม่ค้าง (อาการ "แอปหน่วง" ที่รู้สึกได้ตรง ๆ)

### 4.1 ปัญหา

ทุกครั้งที่ได้ payload (รวมทุก poll 30 วิ) `app.jsx` ทำครบชุด:
1. `JSON.parse` ทั้งก้อน
2. `expandMonthlyCompact` — **สร้าง object `{month,qty,sales}` ใหม่ทุกเดือน × สินค้าทุกตัว**
   (5,600 ตัว × ~30 เดือน ≈ **170,000 object ต่อรอบ**)
3. `enrichData` — วนสินค้าทั้งหมดอีกหลายรอบ (tags/สี/deadMonths/MTO groups)
4. `JSON.stringify` ทั้งก้อน → `localStorage.setItem` (บล็อก main thread)

บนมือถือพนักงานคือหน้าจอค้างเป็นจังหวะทุก 30 วิ

### 4.2 ทางแก้

- **ข้าม step 2-4 ถ้าข้อมูลไม่เปลี่ยน** — เทียบ `d.lastModified` กับที่ถืออยู่ ถ้าเท่ากัน
  ทิ้งผลไปเลย (ทำคู่กับ `ping` ใน Phase 1 แล้วแทบไม่ต้องเข้า path นี้อีก)
- **เขียน localStorage แบบหน่วง** — เก็บทุก ๆ 2-5 นาที หรือตอนปิดแอป
  ไม่ใช่ทุก poll · localStorage มีไว้กันเปิดแอปแล้วจอว่างตอนเน็ตไม่มา ไม่ต้องสดขนาดนั้น
- **เก็บ localStorage เป็นรูปแบบย่อ (`mo`)** แล้วค่อยกางตอนใช้ — ประหยัดทั้งพื้นที่และเวลาเขียน
- (ทางเลือก) ย้าย parse/enrich ไป Web Worker — ได้ผลดีแต่แก้เยอะ เก็บไว้ทีหลัง

### 4.3 เวลาโหลดครั้งแรก (Babel)

`.jsx` ~1.3 MB ถูก compile ในเบราว์เซอร์ทุกครั้งที่ cache หาย (`dmj-babel-*`)
— **โหลดแรกหลัง deploy ทุกครั้งช้าเพราะข้อนี้**
- ทางแก้จริงคือ pre-compile ตอน deploy (GitHub Action → เสิร์ฟ `.js` ที่ compile แล้ว)
  แต่ **ขัดกับสถาปัตยกรรม "ไม่มี build step" ที่ตั้งใจไว้** (CLAUDE.md)
- **ต้องให้เจ้าของตัดสินใจ** — ทำแล้วโหลดแรกเร็วขึ้นชัดเจน แลกกับต้องพึ่ง build pipeline
  (แก้ไฟล์แล้วต้องรอ Action เสร็จก่อนถึงจะเห็นผล) · ถ้าไม่เอา ก็ข้ามข้อนี้ได้ ไม่กระทบข้ออื่น

## Phase 5 — ล็อกอินให้ลื่นขึ้น

### 5.1 เปิดแอปแล้วต้องรอ `me` ก่อนถึงจะเห็นอะไร

`authPhase === "checking"` โชว์แต่วงกลมหมุน (`app.jsx:1394`) จนกว่า `me` จะตอบ
— ถ้า GAS เพิ่งตื่น (cold start ~25 วิ) พนักงานเห็นจอหมุนเปล่า ๆ

**เสนอ**: จำ staff ล่าสุดไว้ใน localStorage → เปิดแอปมาเข้าหน้าจอทำงานได้เลย
แล้วเช็ค `me` เบื้องหลัง ถ้าไม่ตรง (ถูกถอดสิทธิ์/หมดอายุ) ค่อยเด้งออก
- ปลอดภัยเพราะ **สิทธิ์จริงบังคับที่ server อยู่แล้ว** (`canDoOrNull_`) หน้าจอที่เห็นก่อน
  ไม่ได้ให้สิทธิ์อะไรเพิ่ม
- ต้องระวัง: คนที่ถูกระงับจะเห็นหน้าจอแวบหนึ่งก่อนถูกเด้ง — รับได้

### 5.2 ปุ่มล็อกอิน LINE ยิง `lineLoginMeta` ทุกครั้งที่กด

`startLineLogin` (`app.jsx:1195`) fetch ก่อนแล้วค่อย redirect — เพิ่มเวลารอ 1 รอบเน็ต
และถ้าเน็ตสะดุดตรงนั้น = กดแล้วไม่ไปไหน
- มี channelId cache อยู่แล้ว (`LINE_CHANNEL_KEY`) → **ใช้ค่าใน cache ก่อน ยิงเช็คทีหลัง**

### 5.3 ของที่ทำไว้ดีแล้ว ไม่ต้องแตะ

- login handoff (iOS PWA เด้งไป Safari) — ครบแล้ว
- prefetch payload ใน `<head>` พร้อม role — ครบแล้ว
- เตือนเมื่อเปิดในเบราว์เซอร์ของแอป LINE — เพิ่งทำ

## Phase 6 — "แม่นยำขึ้น" (ตัวเลขตรงและไม่เตือนผิด)

### 6.1 conflict ปลอม เมื่อหลายคนทำงานพร้อมกัน

`shouldRejectConflict_` เทียบกับ `dmj_last_write_ts` ซึ่งเป็น **timestamp ระดับทั้งระบบ**
→ A บันทึกหน้าร้าน SKU หนึ่ง แล้ว B ที่เปิดหน้าจอค้างไว้เกิน 5 วิ กดบันทึก **คนละ SKU**
ก็โดนปฏิเสธ ทั้งที่ไม่ได้ชนกันจริง · ยิ่งคนเยอะยิ่งเจอบ่อย
- **เสนอ**: เก็บ timestamp แยกต่อ "กลุ่มข้อมูล" (สต็อก/ออเดอร์/ล็อค/ลงเวลา) แล้วเทียบ
  เฉพาะกลุ่มที่เกี่ยวกับ action นั้น · ทางที่ง่ายกว่า: เทียบระดับ SKU สำหรับงานนับสต็อก

### 6.2 ข้อมูลเก่าค้างได้ถึง 3 นาที

TTL cache = 180 วิ · แก้ชีตด้วยมือ (ไม่ผ่านแอป) ไม่ล้าง cache → เห็นช้าได้ถึง 3 นาที
- `ping` (Phase 1) + timestamp บนหัวจอ "ข้อมูล ณ HH:MM" ทำให้ผู้ใช้รู้ว่ากำลังดูของเมื่อไหร่
  ดีกว่าทำให้สดตลอดแล้วช้าลง

### 6.3 ของที่ตรวจแล้วไม่มีปัญหา

- การเขียนแถวพร้อมกัน — `LockService` ครอบครบทุกเส้นทางที่เขียนสต็อก/ล็อค/โอน/ลงเวลาแล้ว
  (`handleOrder_` เป็นตัวสุดท้ายที่ยังขาด เพิ่งเพิ่มไปเมื่อกี้)
- payload แยกตาม role + cache แยก variant — ครบแล้ว ไม่มีข้อมูลรั่วข้าม role

## ลำดับที่แนะนำ + ผลที่คาด

| ลำดับ | งาน | แรง | ผลที่คาด | ความเสี่ยง |
|---|---|---|---|---|
| 1 | Phase 0 วัด + เช็คโควตา trigger | ครึ่งวัน | รู้ว่าต้องแก้อะไรจริง | ไม่มี (อ่านอย่างเดียว) |
| 2 | Phase 1 `ping` + หยุด poll ตอนไม่ได้ดู | 1 วัน | **ลดโหลด GAS 60-90%** | ต่ำ |
| 3 | Phase 4.2 ไม่ประมวลผลซ้ำเมื่อข้อมูลไม่เปลี่ยน | ครึ่งวัน | มือถือไม่ค้างทุก 30 วิ | ต่ำ |
| 4 | Phase 2 cache session | 1 วัน | ทุก request ที่ล็อกอินเร็วขึ้นชัด | ปานกลาง (TTL สิทธิ์) |
| 5 | Phase 3 cache 2 ชั้น | 2-3 วัน | โหลดข้อมูลเร็วขึ้นมากตอนหลายคนใช้ | **สูง** (ข้อมูลเก่าค้างถ้าตารางผิด) |
| 6 | Phase 5 ล็อกอินลื่น | 1 วัน | เปิดแอปเห็นจอทำงานทันที | ต่ำ-ปานกลาง |
| 7 | Phase 6 conflict แยกกลุ่ม | 1-2 วัน | เตือนชนกันน้อยลง | ปานกลาง |
| — | Phase 4.3 pre-compile JSX | 1 วัน | โหลดแรกเร็วขึ้นมาก | **ต้องเจ้าของตัดสินใจ** (เลิก no-build) |

**ทำแค่ลำดับ 1-3 (≈2 วัน) น่าจะแก้อาการ "อืด" ที่รู้สึกได้ไปเกินครึ่งแล้ว** โดยแทบไม่มีความเสี่ยง
— แนะนำให้ทำชุดนี้ก่อน วัดผล แล้วค่อยตัดสินใจว่าจะไปต่อ Phase 3/5 ไหม

## สิ่งที่ต้องให้เจ้าของตัดสินใจ

1. **TTL cache session** — 5 นาที (เร็วสุด) หรือ 60 วิ (ถอดสิทธิ์มีผลไวกว่า)
2. **pre-compile JSX ตอน deploy** — เอาความเร็วโหลดแรก แลกกับต้องมี build step
3. **กระดิ่ง 25 วิ → 60 วิ** — รับได้ไหมที่แจ้งเตือนช้าลง ~35 วิ
4. **`drainNotiQueue` ทุก 1 นาที → 5 นาที** — ถ้าโควตา trigger เต็ม (Phase 0 จะบอก)
